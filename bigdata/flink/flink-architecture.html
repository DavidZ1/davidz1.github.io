核心组件详解
💻
Client（客户端）
不属于运行时，负责作业提交
Client 是用户与 Flink 集群交互的入口，它本身不参与实际计算。
  • 解析用户的 DataStream / Table API 代码，生成 StreamGraph
  • 将 StreamGraph 优化为 JobGraph（合并算子链）
  • 将 JobGraph 及 Jar 包序列化后提交给 Dispatcher
  • 可通过 CLI / REST API / Web UI 操作
🎯
JobManager（作业管理节点）
Master 节点，协调整个作业生命周期
JobManager 是 Flink 集群的大脑，包含多个核心子组件：
  • Dispatcher：接收 Job 提交，持久化 JobGraph，为每个 Job 启动一个 JobMaster
  • JobMaster：负责单个作业的全生命周期管理，将 JobGraph → ExecutionGraph
  • Scheduler：决定 Task 的调度策略与执行顺序
  • CheckpointCoordinator：周期性触发分布式快照，协调所有 TM 完成 Checkpoint
  • BlobServer：负责 Jar 包、配置等文件的分发存储
⚙️
ResourceManager（资源管理器）
负责 TaskManager Slot 的申请与释放
ResourceManager 是 Flink 集群的资源调度中心，屏蔽底层资源系统差异。
  • 管理所有 TaskManager 及其 Task Slot 的注册与状态
  • 接收 JobMaster 的 Slot 请求，将合适的 Slot 分配给对应 Job
  • 在 YARN/K8s 模式下，负责向外部资源系统申请启动新的 TaskManager
  • 监控 TaskManager 心跳，处理 TM 的注册/注销/超时
🔧
TaskManager（任务执行节点）
Worker 节点，真正执行计算任务的地方
TaskManager 是 Flink 的工作节点，包含若干 Task Slot。
  • Task Slot：资源隔离单元，每个 Slot 持有固定比例的 JVM 内存
  • Operator Chain：将多个算子串联在同一线程中执行，减少网络开销
  • Network Stack：管理 Task 之间的数据传输（基于 Netty + Credit-based 流控）
  • Memory Manager：管理 Managed Memory（用于排序、哈希、State 等）
  • 定期向 JobManager 上报心跳、Task 状态
📊
执行图谱（Graph 体系）
四层图结构表达计算逻辑
Flink 将用户程序逐层转化为可执行的物理计划：
  • StreamGraph：用户 API 直接生成，描述算子拓扑与逻辑连接
  • JobGraph：合并可 chain 的算子，减少序列化开销
  • ExecutionGraph：并行化 JobGraph，每个并发生成一个 ExecutionVertex
  • Physical Graph：最终部署到 TaskManager 的实际任务实例
🛡️
高可用 & Checkpoint
保障作业容错与状态一致性
Flink 通过多重机制保障系统可靠性：
  • ZooKeeper/K8s HA：JobManager Leader 选举，避免单点故障
  • Checkpoint：基于 Chandy-Lamport 算法的分布式快照，定期持久化全局状态
  • Savepoint：用户手动触发的 Checkpoint，支持作业升级/迁移
  • State Backend：HashMapStateBackend（内存）或 RocksDBStateBackend（磁盘）
完整任务提交流程
01
用户编写并提交程序 User → Client
用户通过 DataStream API / Table API / SQL 编写 Flink 作业代码，调用 env.execute() 触发提交。Client 解析整个算子 DAG，在本地构建 StreamGraph（纯逻辑拓扑，包含所有算子节点和边）。
02
生成 JobGraph 并提交 Client → Dispatcher
Client 将 StreamGraph 进行算子链（Operator Chain）合并优化，生成 JobGraph（减少不必要的序列化/反序列化）。随后将 JobGraph + 用户 Jar 包打包，通过 HTTP REST 接口发送至 JobManager 的 Dispatcher。
03
Dispatcher 持久化 & 创建 JobMaster Dispatcher → JobMaster
Dispatcher 接收 JobGraph 后，将其持久化到高可用存储（ZooKeeper/K8s）以支持故障恢复。然后为该作业创建一个专属的 JobMaster 实例，将作业的完整管理权移交给 JobMaster。
04
生成 ExecutionGraph & 申请资源 JobMaster → ResourceManager
JobMaster 将 JobGraph 并行展开，生成 ExecutionGraph（每个算子按并行度拆分为多个 ExecutionVertex）。随后向 ResourceManager 发送 Slot 请求，申请执行任务所需的计算资源。
05
ResourceManager 分配 / 启动 TaskManager ResourceManager → TaskManager
ResourceManager 检查是否有空闲的 Task Slot。
• 有空闲 Slot：直接将 Slot offer 给 JobMaster
• 无空闲 Slot：向外部系统（YARN/K8s）申请启动新的 TaskManager 进程，等待 TM 注册后再分配 Slot
06
TaskManager 注册 & Slot 分配确认 TaskManager → ResourceManager → JobMaster
新启动的 TaskManager 向 ResourceManager 完成注册，汇报其拥有的 Slot 数量。ResourceManager 将 Slot 信息转发给 JobMaster，JobMaster 通过 RPC 直接与 TaskManager 通信，确认 Slot 分配（Offer Slot / Allocate Slot）。
07
Task 部署 & 启动执行 JobMaster → TaskManager
JobMaster 将 ExecutionGraph 中的每个 Task（含算子代码、状态描述、网络连接信息）序列化，通过 RPC 发送给对应的 TaskManager，TaskManager 将 Task 提交到对应的 Slot 线程中开始执行。同一 Slot 内的多个算子组成 Operator Chain，在同一线程中运行以减少开销。
08
作业运行 & 持续监控 TaskManager ↔ JobMaster（持续）
作业开始正常处理数据流。运行期间：
• TaskManager 定期向 JobMaster 发送心跳 + Task 状态
• CheckpointCoordinator 周期性向所有 Source Task 注入 Barrier，触发分布式 Checkpoint
• 发生 Task 失败时，JobMaster 根据重启策略决定是否重启，并从最近的 Checkpoint 恢复状态
• 作业完成后，JobMaster 通知 ResourceManager 释放所有 Slot，TM 资源归还
💡 Session vs Per-Job vs Application 模式：在 Session 模式下，Dispatcher 和 ResourceManager 是预先启动的共享集群；在 Per-Job 模式下，每个作业独占一套 JobManager；在 Application 模式下，用户 main() 方法直接在 JobManager 端执行，Client 无需下载依赖，大幅降低网络传输压力。
四层图转化关系
① StreamGraph

由用户 API 直接生成，描述逻辑算子拓扑。每个 Transformation 对应一个节点，保留完整语义信息，尚未考虑并行度和资源。

② JobGraph

将满足条件的相邻算子合并为 OperatorChain，减少数据序列化与传输。在 Client 端生成并提交至集群，是跨网络传输的基本单位。

③ ExecutionGraph

JobGraph 按并行度展开后的物理拓扑。每个 JobVertex 对应若干 ExecutionVertex（= 并行度 × 1），包含完整的调度和执行状态机。

④ Physical Graph

最终部署在 TaskManager 上的运行实例。每个 ExecutionVertex 变为一个运行中的 Task，通过 Network Buffer 实现 Task 间数据流转。
