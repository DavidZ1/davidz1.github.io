RocksDB 结构性文件
完全解析

每个 Flink subtask 背后运行一个独立 RocksDB 实例，实例目录下存在 5 类文件。它们职责截然不同，对 Checkpoint 大小的影响也相差数量级。点击下方标签逐一深入。

SST
.sst
Sorted String Table
核心数据载体 · 不可变 · 有序键值对集合

SST 是 RocksDB 的核心存储单元：一个写入后永不修改的有序 KV 集合文件。所有数据最终都沉淀在 SST 中，通过 Compaction 将多个小 SST 合并为更大、更有序、更压缩的 SST，旧文件被删除。

与 Flink Checkpoint 的关系
  • 增量 CK 维护每个 subtask 的 SST 文件引用链，每次 CK 只上传上次之后新增的 SST 文件
  • 扩容后（p=2→4）新 subtask 是全新 RocksDB 实例，没有任何历史引用链，首次 CK 等同全量上传所有 SST（伪全量陷阱）
  • 并行度翻倍后每个实例的数据量减半，L0 文件数难以触发 compaction 阈值，导致更多碎片化 SST 进入 CK
  • SST 是 CK 体积的绝对主体（~95%），优化 CK 大小的核心就是减少 SST 总量
!
扩容后首次 CK 必然是伪全量
等待 3~5 个 CK 周期后，新 subtask 建立引用链，CK 大小会逐渐回落至正常增量水平。若持续不回落，则是数据倾斜或 state 泄露。
WAL
.log
Write-Ahead Log
预写日志 · 崩溃恢复防线 · 不进入 Checkpoint

WAL 是崩溃恢复的最后防线。每条写入操作在进入内存 MemTable 之前，必须先顺序追加写入 WAL 文件。进程崩溃重启后，通过重放 WAL 恢复 MemTable 中尚未刷盘的数据，保证 durability。

Sync 策略对比
策略描述持久性吞吐量Flink 推荐
sync_every_write 每条写入立即 fsync 最强 最低 仅极端场景
group_commit 攒批后 fsync，平衡持久性与吞吐 强 中等 ✓ 推荐
no_sync 依赖 OS 缓冲，崩溃可能丢数据 弱 最高 不推荐
与 Flink Checkpoint 的关系
  • WAL 完全不写入 Flink Checkpoint，对远端 CK 大小零影响
  • WAL 的作用是 RocksDB 自身的崩溃恢复，与 Flink 的 CK 恢复机制是两套独立体系
  • 并行度翻倍后 4 个实例并发写 WAL，本地磁盘 I/O 压力翻倍，可能拖慢 MemTable flush 速度，间接影响 CK 耗时
  • 调优方向：增大 write_buffer_size（减少 flush 频次）或开启 allow_concurrent_memtable_write
//
关键区分
WAL 影响的是本地磁盘占用和写入延迟，CK 影响的是远端存储大小和恢复时间。排查 CK 大小异常时，WAL 不在优化路径上。

MANIFEST
版本变更账本 · VersionEdit 追加日志 · 类比 Git commit log

MANIFEST 是 RocksDB 的版本控制账本，以追加写方式记录每一次 SST 文件的增删（称为 VersionEdit），维护从初始状态到当前状态的完整变更历史。启动时重放全部 VersionEdit，在内存中重建 VersionSet（所有 SST 的当前布局索引）。

MANIFEST 膨胀与轮换机制
属性说明
写入格式追加写日志（append-only），与 WAL 同格式，不可原地修改
膨胀原因每次 SST 变更都追加一条记录，长期运行后文件持续增大
轮换机制超过 max_manifest_file_size（默认 1 GB）时，生成新 MANIFEST 并原子更新 CURRENT
启动开销MANIFEST 越大，启动时重放 VersionEdit 的耗时越长
CK 中的角色恢复方依赖 MANIFEST 重建 SST Level 布局，是增量 CK 的必要元数据
与 Flink Checkpoint 的关系
  • Flink 增量 CK 每次全量上传 MANIFEST（不做增量），恢复方需要完整的 VersionEdit 历史才能重建 SST 布局
  • 并行度 p=2→4，MANIFEST 文件数从 2 变为 4，总体积翻倍（仍在 MB 量级，远小于 SST）
  • MANIFEST 体积随运行时间增长，长期运行的任务 MANIFEST 可能达到数十 MB，此时对 CK 大小的贡献才变得可见
  • 调优：设置合理的 max_manifest_file_size 控制轮换频率，避免单个 MANIFEST 过大

OPTIONS 文件
配置参数快照 · ini 风格 · 人类可读 · 诊断利器

OPTIONS 是整个 RocksDB 实例全部配置参数的文本快照，记录数据库打开时所有关键参数，包括列族配置、压缩算法、Compaction 策略、block cache 大小等。每次数据库打开写一个新版本，最多保留 2 个历史版本。

典型文件内容与关键参数解读
# OPTIONS 文件（ini 风格，人类可读）

[Version]
  rocksdb_version=8.x.x
  options_file_version=1.1

[DBOptions]
  max_background_jobs=4          # 后台 compaction + flush 线程总数
  bytes_per_sync=1048576        # WAL 异步 sync 粒度
  use_direct_io_for_flush=false  # 是否绕过 OS page cache

[CFOptions "default"]            # Flink 默认只有 default column family
  write_buffer_size=67108864    # 64 MB — MemTable 大小，决定 flush 频率
  max_write_buffer_number=2     # 最多同时存在的 MemTable 数量
  compression=kLZ4Compression   # L0-L2 压缩算法
  bottommost_compression=kZSTD  # L3+ 更高压缩比

  # ── Compaction 参数 ──
  level0_file_num_compaction_trigger=4   # L0 文件数触发 compaction 阈值
  level0_slowdown_writes_trigger=20      # 触发写入限速
  level0_stop_writes_trigger=36          # 触发写入停止
  target_file_size_base=67108864        # L1 单个 SST 目标大小 64 MB
  max_bytes_for_level_base=268435456   # L1 总大小上限 256 MB
  max_bytes_for_level_multiplier=10     # 每层容量 ×10
与 Flink Checkpoint 的关系
  • OPTIONS 进入 CK 主要用于配置校验：恢复时对比当前参数与历史参数，避免不兼容配置导致数据损坏
  • OPTIONS 体积极小（<50 KB），即使并行度翻倍后数量 ×2，对 CK 总大小影响完全可以忽略（KB 量级）
  • 修改 Flink 的 RocksDBStateBackend 参数后，下次数据库打开时会生成新版本 OPTIONS，记录最新配置
  • OPTIONS 是排查问题的第一手资料：从 CK 中还原 OPTIONS 文件，即可查看任务历史配置参数

CURRENT 文件
启动入口指针 · 单行文件 · ~16 bytes · 崩溃安全

# CURRENT 更新流程（MANIFEST 轮换时）
1. 写入新文件  → MANIFEST-000043（包含完整 VersionEdit 历史）
2. 写入临时文件 → CURRENT.new（内容: "MANIFEST-000043\n"）
3. 原子重命名  → rename("CURRENT.new", "CURRENT")
   └─ POSIX 保证此操作原子性：要么成功，要么保持旧值
4. 删除旧文件  → MANIFEST-000042（可安全删除）

# 崩溃场景分析
- 崩溃在步骤2前：CURRENT 仍指向 MANIFEST-000042，完整可用
- 崩溃在步骤3前：CURRENT.new 存在但 CURRENT 未变，重启后清理 .new 即可
- 崩溃在步骤4前：CURRENT 已指向新 MANIFEST，旧 MANIFEST 残留但不影响正确性
与 Flink Checkpoint 的关系
  • CURRENT 进入 CK 作为恢复时的唯一启动入口，没有它 RocksDB 实例无法打开
  • 文件大小仅 ~16 字节，并行度翻倍后 4 个 CURRENT 合计不超过 128 字节，对 CK 大小贡献绝对为零
  • Flink CK 恢复流程：读 CURRENT → 定位 MANIFEST → 重放 VersionEdit → 重建 VersionSet → 挂载 SST
  • CURRENT 文件损坏等同于整个 RocksDB 实例不可打开（可通过手动写入正确的 MANIFEST 文件名修复）

优化闭环：从大到小逐层排查
  • 第一优先级 — SST：等待增量 CK 稳定（3~5 个周期）；排查数据倾斜；开启 State TTL；调整 write_buffer_size 和 compaction 参数
  • 第二优先级 — MANIFEST：若任务运行时间极长且 MANIFEST 超过数十 MB，可设置 max_manifest_file_size 触发轮换
  • 不需要优化 — OPTIONS / CURRENT：体积贡献在 KB/字节量级，任何优化都是过度工程
  • 独立维度 — WAL：若本地磁盘 I/O 是瓶颈，可调整 sync 策略和 write_buffer_size，但这与 CK 大小无关
//
结论
CK 大小从 8 GB → 15 GB，几乎全部来自 SST 文件的伪全量上传和碎片化，元数据文件（MANIFEST × 2、OPTIONS × 2、CURRENT × 2）贡献的额外体积合计不超过 1 MB。优化路径清晰：先让增量 CK 稳定，再解决数据倾斜，最后调整 compaction 参数。
