01 / OVERVIEW

Schema Evolution 核心设计

Paimon 的 Schema 信息存储在独立的 schema/ 目录，与数据文件解耦。每次 DDL 变更生成新版本 Schema，历史 DataFile 保持不变，读取时按 Schema ID 动态适配字段映射。

schema-0 原始版本
▸order_idBIGINT PK
▸user_idBIGINT
▸amountDECIMAL(10,2)
▸statusSTRING
✕remarkSTRING
schema-1 变更后版本
▸order_idBIGINT PK
▸user_idBIGINT
~amountDECIMAL(12,2) ↑精度
~order_statusSTRING ✎重命名
+citySTRING 新增
+created_atTIMESTAMP 新增
KEY DESIGN
Schema 文件（schema/schema-N）以 JSON 格式存储字段列表、主键、分区信息、表属性。读取时，Paimon 对比 DataFile 所属的 Schema ID 与当前最新 Schema，自动进行字段投影与填充：新增字段读旧文件时返回 null / 默认值，删除字段读旧文件时被忽略。
02 / SUPPORTED DDL OPERATIONS

支持的 DDL 操作全览

Paimon 支持丰富的在线 Schema 变更操作，所有操作均为元数据层面的原子更新，不需要重写历史数据文件。

ADD COLUMN

新增列

在表末尾或指定位置添加新列，可设默认值。历史 DataFile 读取时该列返回 null 或默认值。支持嵌套类型（ROW、ARRAY、MAP）内部新增子字段。

DROP COLUMN

删除列

逻辑删除列（仅更新 Schema 元数据），历史 DataFile 中该列数据仍存在但不再被读取。注意：主键列和分区列不可删除，删除后需等待 Compaction 才能真正释放存储空间。

RENAME COLUMN

列重命名

修改列名，Schema 中记录原列名到新列名的映射关系（通过 Column ID 追踪）。历史文件仍用旧列名存储，读取时按 Column ID 自动对齐，上层查询用新名称即可。

CHANGE TYPE

修改类型

仅支持安全的向上兼容类型转换（如 INT→BIGINT、FLOAT→DOUBLE、增大精度）。不兼容的转换（如 STRING→INT）会被拒绝。读取旧文件时自动隐式转换，无数据丢失风险。

SET PROPERTY

修改表属性

在线修改表的配置参数（如 write-buffer-size、snapshot.num-retained.max），立即生效，无需重启作业。

ADD COMMENT

添加注释

为表或列添加文档注释，注释信息存储在 Schema JSON 中，可被 Hive Metastore、数据治理平台等工具读取展示，便于数据资产管理。

DDL 操作 — Flink SQL 完整示例
-- 新增列（在 status 列之后）
ALTER TABLE orders ADD city STRING COMMENT '城市' AFTER status;

-- 新增列并设默认值（Paimon 0.7+）
ALTER TABLE orders ADD is_deleted BOOLEAN DEFAULT FALSE;

-- 列重命名
ALTER TABLE orders RENAME status TO order_status;

-- 修改列类型（安全向上转换）
ALTER TABLE orders MODIFY amount DECIMAL(12, 2);     -- ✓ 精度扩大
ALTER TABLE orders MODIFY user_id BIGINT;              -- ✓ INT → BIGINT
-- ALTER TABLE orders MODIFY amount INT;            -- ✗ 精度缩小，拒绝执行

-- 删除列
ALTER TABLE orders DROP remark;

-- 在线修改表配置（立即生效，无需重启）
ALTER TABLE orders SET (
  'snapshot.num-retained.max' = '30',
  'write-buffer-size'         = '256 mb'
);

-- 查看所有历史 Schema 版本
CALL sys.schema_changes('my_catalog.my_db.orders');
03 / TYPE COMPATIBILITY MATRIX

类型转换兼容矩阵

并非所有类型转换都被允许，Paimon 严格遵循"只允许安全的向上兼容转换"原则，防止数据精度丢失或语义变化。

⚠ 条件支持说明
INT→DECIMAL 要求目标精度足以容纳 INT 范围（DECIMAL(10,0) 以上）；BIGINT→DOUBLE 存在精度损失风险（DOUBLE 只有 15~16 位有效数字）；DECIMAL 扩精度只允许增大整数位数（p 增大），小数位数（s）不可变更。这些转换 Paimon 会执行但建议谨慎评估后使用。

MySQL CDC 整库同步 — Schema Change 配置
-- MySQL CDC 整库同步，开启 Schema Change 自动同步
-- 支持自动同步的 DDL：ADD COLUMN / DROP COLUMN / RENAME COLUMN / MODIFY COLUMN

bin/flink run \
  -c org.apache.paimon.flink.action.FlinkActions \
  paimon-flink-action-*.jar \
  mysql_sync_database \
  --warehouse   hdfs:///warehouse/paimon \
  --database    ods_mysql \
  --mysql-conf  hostname=mysql-host \
  --mysql-conf  database-name=source_db \
  --table-conf  changelog-producer=input \
  --table-conf  schema-change.add-column=true    -- 允许自动加列
  --table-conf  schema-change.drop-column=false  -- 不自动删列（推荐谨慎）
  --table-conf  schema-change.rename-column=true -- 允许列重命名

-- 不支持自动同步的 DDL（需手动处理）：
--   DROP TABLE / TRUNCATE TABLE
--   修改主键 / 修改分区字段
--   不兼容的类型变更（如 VARCHAR→INT）
BEST PRACTICE
生产环境建议将 schema-change.drop-column 设为 false，防止上游误删列导致 Paimon 同步删除造成数据丢失。删列操作建议手动评估下游影响后再执行。
05 / TAG & VERSION MANAGEMENT

Tag 标签与版本管理

Paimon 的 Tag 机制允许对特定 Snapshot 打标签，实现业务级别的版本管理与数据回溯，是生产数据质量保障的重要手段。

①
CREATE TAG

创建 Tag

对任意 Snapshot 创建具名 Tag，Tag 会阻止对应 Snapshot 及其依赖的 DataFile 被 GC 清理，相当于给该时间点的数据状态打上"永久书签"。支持手动创建和按时间自动创建。

②
TAG TIME TRAVEL

基于 Tag 的时间旅行查询

查询时通过 Tag 名称指定历史版本，语义比 Snapshot ID 更友好（如 2024-01-01 而非 snapshot-42）。适合按日/周打标，用于历史对账和数据审计。

③
ROLLBACK TO TAG

回滚到 Tag 版本

当数据质量问题出现时，可将表回滚到最近的可信 Tag 版本。回滚操作原子执行，LATEST 指针切回指定 Tag 对应的 Snapshot，后续写入从该点继续，问题数据被跳过。

④
AUTO TAG

自动定期打 Tag

配置 tag.automatic-creation=process-time 后，Paimon 按时间间隔自动创建 Tag，结合 tag.num-retained-max 控制保留数量，实现自动快照版本管理。

Tag 操作完整示例
-- 创建 Tag（基于最新 Snapshot）
CALL sys.create_tag('my_catalog.my_db.orders', 'daily-2024-01-01');

-- 创建 Tag（指定 Snapshot ID）
CALL sys.create_tag('my_catalog.my_db.orders', 'release-v2.1', 42);

-- 基于 Tag 做时间旅行查询
SELECT * FROM orders /*+ OPTIONS('scan.tag-name' = 'daily-2024-01-01') */;

-- 回滚到 Tag 版本（危险操作，会丢弃 Tag 之后的所有写入）
CALL sys.rollback_to_tag('my_catalog.my_db.orders', 'daily-2024-01-01');

-- 删除 Tag
CALL sys.delete_tag('my_catalog.my_db.orders', 'daily-2024-01-01');

-- 查看所有 Tag
SELECT * FROM orders$tags;

-- 自动定期打 Tag（建表时配置）
-- 'tag.automatic-creation' = 'process-time'  按时间自动创建
-- 'tag.creation-period'    = '1 d'           每天打一次 Tag
-- 'tag.num-retained-max'   = '14'            最多保留 14 个 Tag
06 / IMPACT ON READERS

Schema 变更对各类读取的影响

不同 Schema 变更操作对正在运行的流式作业、批量查询、下游 OLAP 引擎的影响各不相同，提前了解可以做好变更窗口规划。

DDL 操作Flink 流作业（读）Flink/Spark 批查询Hive / Trino是否需要重启
ADD COLUMN 自动感知，新列返回 null立即可见新列需刷新元数据缓存 无需重启
DROP COLUMN 该列从结果中消失，需检查下游依赖立即不可见需刷新元数据缓存 建议重启验证
RENAME COLUMN 通过 Column ID 自动对齐，无感知使用新列名查询需更新查询中的列名引用 无需重启
CHANGE TYPE 自动隐式转换，注意精度变化立即使用新类型需验证类型兼容性 建议重启验证
SET PROPERTY 写入参数立即生效，读取无影响无影响无影响 无需重启
DANGER ZONE
修改主键列或分区列是 Paimon 不支持的操作，也是最危险的需求。若业务确实需要变更主键，唯一安全方式是：① 创建新表（新主键定义）→ ② 全量迁移数据 → ③ 切换上游写入指向 → ④ 下线旧表。整个过程需要精心设计数据双写和流量切换窗口。
07 / COMMON PITFALLS

Schema 变更常见陷阱

Schema Evolution 功能强大，但在生产环境操作不当仍然可能引发数据质量问题。以下是最常见的几类陷阱。

🔗
下游视图未同步更新

在 Paimon 表新增列后，基于该表创建的 Flink SQL View 或 Hive View 仍使用旧 Schema。需手动 DROP + CREATE VIEW，或在查询时显式写列名而非 SELECT *。

💾
删列后存储未立即释放

DROP COLUMN 仅更新 Schema 元数据，历史 DataFile 中被删除列的数据仍然占用磁盘。只有等待 Full Compaction 重写所有文件后，存储空间才能真正释放。

🔄
partial-update 与新增列冲突

使用 partial-update Merge Engine 时，新增列若没有对应的写入流，会一直保持 null。需确保所有写入流都感知新列并写入正确默认值。

⏰
Tag 阻止快照 GC

大量 Tag 的存在会阻止对应 Snapshot 的 GC，导致存储持续增长。必须配合 tag.num-retained-max 设置上限，避免无限堆积历史版本。

📐
CDC 类型不兼容导致作业失败

MySQL 将 VARCHAR(100) 改为 VARCHAR(50)（缩小），Paimon 拒绝该变更并抛出异常，导致 CDC 作业停止。需在 MySQL DDL 变更前确认 Paimon 的兼容性。

🧩
Spark 读取时 Schema 不一致

Spark 默认缓存 Schema 信息，若 Paimon Schema 在 Spark Session 运行期间发生变更，可能读到旧 Schema。建议在 Schema 变更后重新创建 Spark Session 或执行 REFRESH TABLE。
