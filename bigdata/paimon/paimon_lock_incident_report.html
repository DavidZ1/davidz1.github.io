实时写入卡死的真凶
不是数据冲突，是一把泄漏的 Hive 锁

单 Flink 任务写 8 张 Paimon 表，唯独 ods_icv_can_e16reev 的 Global Committer 长期卡在初始化，最终因 8 分钟拿不到 HMS 表锁而失败。本报告还原从误导性报错到根因的完整链路，并给出在 COS 存储下保留 Hive Catalog 的根治配置。

故障级别 P2 · 单表链路中断 发生时间 2026-06-17 08:06 组件 Flink + Paimon + Hive Catalog + COS 状态 根因已定位 · 待配置上线
00

一句话结论Executive Summary

报错顶层的「multiple jobs commit conflict」是 Paimon 的通用包装语，不是真因。真因藏在堆栈最底层：上一个实例在持有该表提交锁的瞬间非优雅退出，锁泄漏在 Hive Metastore；而 HMS 没有运行锁回收，死锁永不释放——新实例恢复时申请同一张表的锁，等满默认 8 分钟超时后失败。

修复方向

保留 Hive Catalog（COS 必须有锁、且需 HMS 同步元数据给 Hive 外部表），把修复落在 HMS 端的锁回收（housekeeping / reaper） 与 优雅停止 上。Paimon 端配置无需改动。

01

故障现象Symptom

  • 一个 Flink 任务消费 Kafka，写入 8 张 Paimon 表（每张约 210 字段），上层创建 Hive 外部表读取。
  • 其余 7 张表写入正常，唯独 ods.ods_icv_can_e16reev 异常。
  • 算子 Global Committer: ods_icv_can_e16reev +- Writer 长期停留在 INITIALIZING 状态。
  • 最终在恢复阶段抛出提交失败异常。关键堆栈（精简）如下。
# 顶层：通用包装语，具有误导性
Commit failed after ... with 10 retries,
  there maybe exist commit conflicts between multiple jobs.
  ...
Caused by: Exception occurs when committing snapshot #181 ... kind APPEND.
  Cannot clean up because we can't determine the success.
Caused by: Acquire lock failed for table ods.ods_icv_can_e16reev
  (lockId=958737) after 485079ms. Final lock state: WAITING
  at org.apache.paimon.hive.HiveCatalogLock.lock(HiveCatalogLock.java:125)
  at ...CommitterOperator.initializeState(CommitterOperator.java:147)
第一个信号

485079ms ≈ 8.08 分钟，正好是 Paimon lock.acquire-timeout 的默认值（480000ms）。提交本身没失败——是拿不到锁，等满超时被迫放弃。

02

影响范围Impact

  • 受影响：仅 ods_icv_can_e16reev 一张表的实时写入链路中断，下游 Hive 外部表数据停更。
  • 未受影响：同任务内其余 7 张表正常——因为 Paimon 的提交锁是按表粒度，各表各自申请、互不干扰。
  • 失败模式：响亮、可恢复（有明确报错，清锁即恢复）。这一点在后文 COS 决策中是重要对照。
03

根因分析Root Cause Chain

从现象到根因，是一条因果链。两个红/橙节点是断裂点——其中橙色为最终根因。

1
Global Committer 卡 INITIALIZING，最终提交失败
触发点在 initializeState → recover → filterAndCommit，即作业重启/恢复时重放 snapshot #181 的提交。
2
顶层「multiple jobs commit conflict」误导
Paimon 在任何提交失败时都会套这句通用语，并非真的存在多作业数据冲突。
3
真实信号：拿不到锁，等满 8 分钟默认超时
485079ms ≈ lock.acquire-timeout 默认值。问题是「锁」，不是「数据」，更不是 210 字段宽表。
4
断裂点①：上个实例持锁瞬间非优雅退出 → 锁泄漏
崩溃时恰好持有 ods_icv_can_e16reev 的提交锁（其余 7 张已提交完释放），unlock() 没机会执行，锁残留在 HMS。
5
断裂点②（根因）：HMS 未回收死锁 ROOT CAUSE
Paimon 的 Hive 锁不发心跳，依赖 HMS 的 reaper 回收死锁。HMS 的 housekeeping/reaper 未开启或链路中无进程运行它，死锁永久 ACQUIRED。
6
结果：新实例申请同表锁 → WAITING 至超时 → 单表链路中断
为什么只有一张表

提交锁按表粒度、短时持有。上次崩溃的瞬间只可能持有一张表的锁，恰好是它。210 字段宽表与本故障无关，纯粹是锁问题，不必往 schema 方向排查。

04

机制原理：这把锁到底是什么Mechanism

是什么锁

开启 lock.enabled 且用 Hive Catalog 时，Paimon 走 HiveCatalogLock，底层调 HMS 的 lock() Thrift API，请求体是一把 EXCLUSIVE / TABLE 级锁：

LockComponent(type=EXCLUSIVE, level=TABLE, dbname=ods, tablename=ods_icv_can_e16reev)

它复用了 Hive ACID 的锁子系统（HIVE_LOCKS 表、TxnHandler），但 Paimon 只把它当一把分布式互斥锁用，不是真开 Hive 事务。锁粒度按表，所以 8 张表互不影响。

用来做什么

保护 snapshot commit 的临界区。Paimon 是乐观并发 + 文件式快照，一次提交做三件事：读当前最新 snapshot id → 占用 snapshot-(N+1) → 把临时文件 rename 成 snapshot-N。核心约束是同一个快照编号全局只能有一个写成功。这把锁负责把「读 latest → 占 N → 落文件」整段串行化，保证快照编号单调、提交不互相覆盖。

什么时候释放

  • 正常：一次提交拿一次锁（按 checkpoint），finally { unlock() } 立即释放，持锁仅几十毫秒到几秒。
  • 异常但 JVM 存活：finally 照样 unlock，能正常释放。
  • JVM 在持锁瞬间猝死（kill -9 / OOM / TM crash）：unlock 跑不到 → 锁泄漏。Paimon 不发心跳，只能靠 HMS reaper（按 hive.txn.timeout）回收——reaper 不工作即永久泄漏。
05

关键决策：COS 上为何不能换 filesystem catalogWhy Not Filesystem Catalog

排查中曾观察到「换成 filesystem catalog 就正常」。这是一个危险的幸存者偏差，必须纠正。

Paimon 官方约束

Paimon 靠文件系统 rename 提交快照，在 HDFS 上原子安全；但对象存储（OSS/S3/COS）的 RENAME 没有原子语义，必须配置 Hive 或 JDBC metastore 并开启 lock.enabled，否则有丢快照的风险。在 COS 上，这把锁不是可选项，而是对象存储缺失的原子 rename 的替代品。

filesystem catalog 在 COS 上「看起来正常」，只是因为你是单写，还没触发并发提交去抢同一个快照。一旦出现重启时新旧实例重叠、新增 compaction 作业、或任何第二个 writer——COS 上没锁就会静默丢/覆盖快照。

Hive 锁泄漏（本案）

响亮 · 报错明确 · 可恢复（清锁即可）。

COS + filesystem 无锁冲突

安静 · 无报错 · 数据不可恢复。

注：新版 Paimon 已在检测到底层为对象存储时自动启用 catalog lock（社区 PR #3954），正是为堵这个坑。结论：在 COS 上 filesystem catalog 是唯一应明确避免的选项——它是用一个「响亮可修」的错误换一个「沉默致命」的错误。

06

解决方案Resolution

杠杆在 HMS，不在 Paimon。Paimon 端锁配置其实已生效（日志里已拿到 lockId），真正缺的是 HMS 没有回收泄漏的锁。

① 即时恢复 — 清掉当前残留锁

SHOW LOCKS ods.ods_icv_can_e16reev EXTENDED;
-- 确认那条 ACQUIRED 死锁的 host 对应的作业确实已死后：
DELETE FROM HIVE_LOCKS
  WHERE HL_TABLE='ods_icv_can_e16reev' AND HL_LOCK_STATE='a';
-- ⚠ 删前务必先 SHOW LOCKS 确认持有者真死，别误删活作业的锁

② 根治 — HMS 端开启锁回收（最关键）

改 hive-site.xml / metastore-site.xml，重启 HMS：

hive.support.concurrency=true
hive.txn.manager=org.apache.hadoop.hive.ql.lockmgr.DbTxnManager
hive.txn.timeout=300                          # 秒，超此时长无心跳的锁判定为死
hive.metastore.housekeeping.threads.on=true   # 最关键：开它才有 reaper（Hive3: metastore.housekeeping.threads.on）
hive.timedout.txn.reaper.interval=180s        # reaper 扫描间隔
hive.compactor.initiator.on=true             # 通常与 housekeeping 一并开
非显而易见的关键点

回收死锁的 reaper（AcidHouseKeeperService）需要有进程在跑它。Hive3 独立 HMS 中它随 housekeeping.threads.on 启动；Hive2 中通常跑在 HiveServer2 里。而本链路是 Paimon 直连 HMS、无 HiveServer2——若集群是 Hive2 且无任何组件运行 reaper，死锁将永不回收，这正是 8 分钟等满仍未释放的根因。必须先确认 Hive 版本，并确保确有进程运行 reaper。

③ Paimon 端 — 确认即可（已就位）

CREATE CATALOG paimon WITH (
  'type'='paimon', 'metastore'='hive',
  'uri'='thrift://<hms>:9083',
  'warehouse'='s3://<bucket>/<path>',   -- COS endpoint 已配
  'lock.enabled'='true',
  'lock.type'='hive',
  'lock.acquire-timeout'='60000'     -- 可调小，让卡死快速失败重试（非治本）
);
07

复发预防清单Prevention Checklist

HMS housekeeping / reaper 已开启且确有进程在运行按 Hive 版本核对参数前缀（hive.* vs metastore.*）与 reaper 运行位置
停作业统一使用 stop-with-savepoint禁止 kill -9 / 直接停集群——硬杀即在 HMS 留锁
检查 Flink restart 策略，避免新旧实例长时间并存本次根因大概率即旧 attempt 未死干净、新 attempt 抢同表锁
监控告警：HIVE_LOCKS 中长期处于 ACQUIRED 的锁把锁泄漏从「事后排查」前移到「主动发现」
验证闭环：模拟 kill → 锁残留 → 等过 txn.timeout → 锁被自动回收能自动清掉才算真正配好，否则只是没复现
守住底线：COS 上永不使用 filesystem catalog / 永不关闭锁对象存储缺原子 rename，无锁 = 静默丢快照
08

决策备选对比Alternatives Considered

方案结论理由 / 代价
保留 Hive Catalog
+ 修 HMS 锁回收		采用改动最小、最贴合现状；保留 HMS 自动同步元数据（Hive 外部表读所依赖）；既不丢对象存储安全性也不丢元数据便利。
换 filesystem catalog否决COS 无原子 rename，无锁会静默丢快照；当前「正常」只是单写幸存者偏差。
换 JDBC(MySQL) catalog 锁备选MySQL 锁更可控、不依赖 Hive ACID housekeeping；代价是失去 Hive 自动元数据同步，需自管外部表。
单写 + 关闭锁
(lock.enabled=false)		不建议需保证永远单写且重启绝不重叠；而「重启重叠」正是本次诱因，COS 上失败后果是不可恢复的数据损坏。
09

方法论沉淀Principles

贝叶斯 · 用新证据更新根因

「单任务」→ 排除多作业并发；「7/8 正常」→ 锁定单表锁泄漏；「底座是 COS」→ 直接否决 filesystem catalog。每一条新事实都在重排根因概率，而非推翻重来。

奥卡姆 · 最简解释优先

不被顶层「multiple jobs conflict」误导，最简且自洽的解释是「单表死锁泄漏 + reaper 缺失」，直指堆栈最底层那一行，无需引入更复杂的假设。

失败模式权衡 · 一条值得记住的原则

在分布式存储里，响亮且可恢复的失败，优于安静且不可恢复的失败。Hive 锁泄漏会报错、能清掉；COS 无锁丢快照不报错、不可逆。选型时优先保留「会报错」的那条路。

待确认项

当前 Hive 版本（2.x / 3.x）——它决定 HMS housekeeping 参数前缀（hive.* vs metastore.*）以及 reaper 的运行位置。确认后即可锁定第 06 节的精确配置项。
