02 / FILE ORGANIZATION

磁盘目录结构详解

理解 Paimon 如何在文件系统上组织数据，是优化查询性能和运维管理的基础。

PAIMON TABLE DIRECTORY STRUCTURE 
── my_database/my_table/
   ├── schema/                         # 表结构定义
   │   └── schema-0                    # JSON 格式，含字段、分区、主键信息
   │
   ├── snapshot/                       # 快照管理
   │   ├── LATEST                      # 指向最新快照 ID 的文件
   │   ├── EARLIEST                    # 最早保留的快照 ID
   │   ├── snapshot-1                  # 快照元数据 JSON
   │   └── snapshot-N
   │
   ├── manifest/                       # Manifest 文件索引
   │   ├── manifest-list-{uuid}-0      # Manifest List，引用多个 Manifest
   │   └── manifest-{uuid}             # 记录 DataFile 的增删操作
   │
   └── bucket-0/                       # 按 Bucket 分布的数据目录
       ├── data-{uuid}-0.parquet       # Level-0 数据文件（增量写入）
       ├── data-{uuid}-1.parquet       # Level-1 数据文件（Compaction 后）
       └── index/                      # 可选：二级索引、Bloom Filter
KEY INSIGHT
Manifest 文件是 Paimon 实现 ACID 事务的核心 —— 每次 Commit 生成一个新 Snapshot，Snapshot 指向 Manifest List，Manifest List 记录本次写入新增/删除了哪些 DataFile，形成完整的事务日志链。
03 / LSM-TREE INTERNALS

LSM-Tree 存储结构

Primary Key Table 基于 LSM-Tree（Log-Structured Merge Tree）实现，这是 Paimon 支持高吞吐写入与实时更新的关键所在。

L0
WRITE BUFFER → FLUSH

Level 0 — 增量数据文件

Writer 直接将数据写入内存 MemTable，达到阈值后 Flush 为 Level-0 的 .parquet 文件。L0 文件之间键范围可能重叠，写入速度最快但查询需要扫描多个文件。每个 Checkpoint 触发一次 Flush。

L1
MINOR COMPACTION

Level 1 — 首次合并

当 L0 文件数量超过阈值（默认 num-sorted-run.compaction-trigger = 5），触发 Minor Compaction，将多个 L0 文件合并、排序、去重后写入 L1。L1 文件内键有序，无重叠。

LN
MAJOR COMPACTION

Level N — 分层合并

数据逐层向下 Compaction，每层容量是上层的 10 倍。最终在高 Level 的文件数量少、键范围大、无重叠，查询时只需读取少量文件，point lookup 性能极优。

⊕
MERGE ENGINE

Merge Engine — 多版本合并策略

Paimon 支持三种合并引擎：
• deduplicate（默认）保留最新版本
• partial-update 按列合并更新
• aggregation 聚合累加（SUM/MAX/MIN）

PERFORMANCE TRAP
L0 文件数量过多会导致读放大（Read Amplification）严重。生产环境中需监控 num-sorted-run.stop-trigger 指标，必要时调大 write buffer size 或开启异步 Compaction。
04 / FILE FORMATS

文件格式选型指南

Paimon 支持多种列存格式，选择合适的格式对查询性能和存储效率有决定性影响。

格式 压缩比 读性能 写性能 嵌套结构 适用场景
Parquet ★★★★☆ ★★★★★ ★★★★☆ 完整支持 OLAP 查询，Spark 生态
ORC ★★★★★ ★★★★☆ ★★★☆☆ 完整支持 Hive 生态，高压缩比
Avro ★★★☆☆ ★★★☆☆ ★★★★★ 完整支持 流式写入，Schema Evolution
Parquet 内部结构（Row Group → Column Chunk → Page）

│                    Parquet File                          │

-- 利用 Column Pruning + Predicate Pushdown
-- Paimon 读取时只扫描必要列，并用 Statistics 跳过不满足条件的 Row Group
SELECT user_id, SUM(amount) FROM orders
WHERE event_date = '2024-01-01'
GROUP BY user_id;
-- ↑ 只读 user_id + amount 两列，其余列完全跳过
05 / SNAPSHOT MECHANISM

Snapshot 快照机制

Snapshot 是 Paimon ACID 事务和时间旅行查询的基础，理解其生命周期是进行精确数据管理的关键。

📸

Snapshot 结构

每个 Snapshot JSON 包含：快照 ID、提交时间戳、操作类型（APPEND/OVERWRITE/COMPACT）、Manifest List 路径、统计信息（rowCount, fileCount）、Schema ID 引用。

⏱️

时间旅行查询

通过快照 ID 或时间戳回溯历史数据。Flink/Spark 均支持 scan.snapshot-id 和 scan.timestamp-millis 参数实现精确的历史版本查询。

🔄

快照过期策略

通过 snapshot.num-retained.min/max 和 snapshot.time-retained 控制保留数量和时长。过期 Snapshot 引用的 DataFile 会被 GC 清理。

🔀

增量读取模式

流式消费者可以基于 Snapshot 增量读取变更数据，支持 latest、earliest、from-snapshot 等多种起始位置策略，类似 Kafka 的 offset 管理。

06 / BEST PRACTICES

关键调优要点

基于存储架构理解，这些配置参数对生产环境性能有决定性影响。

01
Bucket 数量设计

按主键哈希分桶，建议 Bucket 数 = 总数据量(GB) / 单文件目标大小(128MB)，避免小文件问题

02
Compaction 策略

批量导入场景关闭自动 Compaction，写完后手动触发 ALTER TABLE COMPACT 一次性整理

03
分区裁剪利用

查询 WHERE 条件尽量包含分区列，Paimon 可直接跳过无关分区目录，避免全表扫描

04
写入缓冲调优

write-buffer-size 增大减少 Flush 频率，但会增加内存占用，需结合 TM 内存综合考量

05
Lookup Join 优化

维表场景使用 Paimon Lookup Join，利用本地 RocksDB 缓存，避免频繁远程读取

06
快照 GC 监控

定期检查 snapshot/ 目录文件数量，过多未清理的快照会导致 Manifest 链过长，影响 Commit 性能
