01 / DESIGN PHILOSOPHY

流批一体的设计哲学

传统湖仓方案中，流处理引擎和批处理引擎操作不同的存储，数据一致性是噩梦。Paimon 通过统一存储格式和事务语义，让流批共用同一张表成为现实。

⚡

流处理视角（Streaming）

  • Flink Streaming Job 持续写入，每次 Checkpoint 形成一个 Snapshot
  • 写入路径：MemTable → Flush → Level-0 → Compaction，全程异步不阻塞主链路
  • 下游流式消费者以 Snapshot 为单位增量读取，延迟可低至秒级
  • 支持 Exactly-Once 语义：Checkpoint 与 Snapshot Commit 原子绑定
  • 写入并发度与 Bucket 数量对应，天然支持水平扩展
🗂️

批处理视角（Batch）

  • Spark / Hive / Flink Batch 读取同一份 Parquet/ORC 文件，无需转换
  • 批量写入走 BulkWrite 路径，绕过 MemTable 直接生成 DataFile 提升吞吐
  • 基于 Snapshot 隔离：批量读取锁定特定快照，与流式写入互不干扰
  • 分区裁剪、列裁剪、统计信息下推，批量扫描性能与原生列存持平
  • 支持 OVERWRITE 覆盖写：整分区或整表替换，原子可见
CORE INSIGHT
Paimon 的关键创新是：写入路径（流 vs 批）不同，但存储格式与读取协议完全统一。Snapshot 机制是两条路径的汇合点 —— 无论流式 Commit 还是批量 Commit，最终都产生一个不可变的 Snapshot，下游读取者无需区分数据来源。
02 / STREAMING WRITE PATH

流式写入全链路

从 Flink Source 到 Paimon Commit，流式写入经历多个精心设计的阶段，每个阶段都服务于低延迟与高吞吐的双重目标。

PHASE 01
数据接入

Flink Source 算子（CDC / Kafka / 自定义）将数据发送给 Writer 算子。Writer 按主键哈希将记录路由到对应 Bucket，保证同一主键始终由同一 Writer 处理，避免并发写入冲突。

Key Hash RoutingBucket 亲和性
PHASE 02
MemTable 缓冲

每个 Writer 维护一个堆内 MemTable（默认 64MB，可通过 write-buffer-size 调整）。记录按主键在内存中排序并合并（提前去重），减少后续 Flush 的文件数量。MemTable 满或 Checkpoint 触发时执行 Flush。

In-Memory SortPre-Mergewrite-buffer-size
PHASE 03
Flush to L0

MemTable 异步序列化为 Level-0 DataFile（Parquet/ORC），写入对应 Bucket 目录。Flush 过程不阻塞主链路（异步线程池），但会占用磁盘 I/O。每次 Flush 生成一个或多个 DataFile，同时更新内存中的 FileStoreCommit 缓冲区。

Async FlushLevel-0 File非阻塞主链路
PHASE 04
Compaction

独立的 Compaction 线程（或单独的 Compaction Job）将 L0 文件合并为更高 Level，减少读放大。流式场景默认使用异步 Compaction，不影响写入吞吐，但会引入一定的读延迟。可配置 num-sorted-run.compaction-trigger 控制触发阈值。

Async CompactionLevel Merge读放大控制
PHASE 05
Checkpoint Commit

Flink Checkpoint 完成时，Committer 算子（单并发）收集所有 Writer 的 CommitMessage，原子写入新 Snapshot 文件。Snapshot 写入成功 = 数据对外可见。若 Checkpoint 失败，所有 DataFile 被视为无效，下次 Checkpoint 前的孤儿文件由 GC 清理。

Exactly-Once原子 CommitSnapshot 可见性
FLINK SQL — 流式写入关键配置
-- 典型流式写入作业配置
INSERT INTO dwd_orders
SELECT order_id, user_id, amount, status, event_time
FROM ods_orders
/*+ OPTIONS(
  'write-buffer-size'                = '256 mb',   -- MemTable 上限
  'num-sorted-run.compaction-trigger'= '5',        -- L0 文件数触发 Compaction
  'num-sorted-run.stop-trigger'      = '10',       -- 超过则暂停写入等待 Compaction
  'write-thread-num'                 = '2',        -- 异步 Flush 线程数
  'commit.force-compact'             = 'false'     -- Checkpoint 时不强制 Compact
) */;

SET 'execution.checkpointing.interval' = '60s';
SET 'execution.checkpointing.mode'     = 'EXACTLY_ONCE';
03 / BATCH WRITE PATH

批量写入路径与优化

批量场景（Spark 导入、Flink Batch、离线数据回填）走完全不同的写入路径，绕过流式管控机制，追求最大吞吐。

📦

BulkWrite 路径

  • 直接在 Task 本地排序后生成 DataFile，跳过 MemTable 的内存缓冲阶段
  • 利用外部排序（External Sort）处理超过内存的大数据量，不受 write-buffer-size 限制
  • 所有 Task 完成后统一 Commit，生成单个 Snapshot，不产生中间可见状态
  • 写入完成后建议手动触发 ALTER TABLE COMPACT 整理文件
🔄

OVERWRITE 语义

  • 整分区覆盖写：先标记旧分区所有 DataFile 为删除，再写入新文件，原子切换
  • 支持 Dynamic Partition 覆盖（自动推断被影响的分区）
  • INSERT OVERWRITE 期间，其他读取者仍看到旧 Snapshot，写完后原子切换可见
  • 配合 snapshot.num-retained.min 保留足够快照供回滚
批量写入 & OVERWRITE 示例
-- Flink Batch 模式全量初始化
SET 'execution.runtime-mode' = 'BATCH';

INSERT INTO dw_user_profile
SELECT * FROM source_hive_table WHERE dt = '2024-01-01';

-- 分区覆盖写（每日调度 T+1 回刷）
INSERT OVERWRITE dw_orders
PARTITION (dt = '2024-01-01')
SELECT * FROM ods_orders WHERE dt = '2024-01-01';

-- 写完后手动触发 Compaction（降低小文件数量）
CALL sys.compact(
  'my_catalog.my_db.dw_orders',
  'dt=2024-01-01'  -- 只整理指定分区
);

05 / WATERMARK & OUT-OF-ORDER

Watermark 与乱序事件处理

流式场景中事件乱序不可避免，Paimon 通过与 Flink Watermark 机制的深度集成，在写入侧和读取侧双重保障时序正确性。

── 时间轴事件分布与 Watermark 示意

e1·10:00
e2·10:02
e3·09:58 迟到
e4·10:05
e5·09:50 丢弃
WM = 10:03
▼
正常事件（紫色）

事件时间 > Watermark，在窗口计算期限内，正常参与聚合计算，写入 Paimon 后按事件时间分区。

迟到事件（橙色）

事件时间略早于 Watermark，在允许的延迟窗口内（allowedLateness），触发窗口修正，Paimon 通过 sequence.field 保证不被旧值覆盖。

过时事件（红色）

事件时间远早于 Watermark，超过最大允许延迟，由 Flink 直接丢弃。可通过侧输出流（Side Output）捕获并单独处理或写入异常表。

sequence.field — 防止乱序写入覆盖新版本
-- 场景：Kafka 消费到的消息可能乱序，需要防止旧版本覆盖新版本

CREATE TABLE user_profile (
  user_id     BIGINT,
  name        STRING,
  level       INT,
  update_time TIMESTAMP(3),
  PRIMARY KEY (user_id) NOT ENFORCED
) WITH (
  'merge-engine'   = 'deduplicate',
  'sequence.field' = 'update_time'  -- 以 update_time 决定版本新旧
  -- 若写入记录的 update_time ≤ 已有记录，则忽略该写入
);

-- 乱序写入演示：
-- 写入 user_id=1, update_time=10:05  → 生效 ✓
-- 写入 user_id=1, update_time=10:02  → 忽略 ✗（旧版本）
-- 写入 user_id=1, update_time=10:08  → 生效 ✓（更新版本）
CAUTION
sequence.field 要求该字段的值必须严格单调（不能回绕）。若使用业务时间字段，需确保上游不会产生未来时间戳（如系统时钟偏移），否则会导致后续合法更新被永久忽略。
06 / UNIFIED SCENARIOS

流批协同典型场景

Paimon 流批一体能力在实际架构中催生了多种新型数据处理模式，打破了传统 Lambda 架构的复杂性。

01

替代 Lambda 架构

同一张 Paimon 表由 Flink 实时写入，Spark 定期修正（批量覆盖），查询层无需区分实时层和批处理层。一套存储代替传统 Speed + Batch + Serving 三层架构。

02

实时 + 历史混合查询

OLAP 引擎（StarRocks / Doris）通过外表直读 Paimon，同时覆盖 T+0 实时数据和 T-N 历史数据，报表不再需要双源合并逻辑，查询简洁且一致性有保障。

03

流式 Lookup Join 维表

维度表存储在 Paimon，主流程 Flink 作业通过 Lookup Join 查询最新维度值。Paimon 本地 RocksDB 缓存维表数据，避免高频远程读取，延迟可控在毫秒级。

04

分层物化视图

ODS → DWD → DWS 每层均用 Paimon 表存储，流式 Flink 作业链式处理，批量 Spark 作业定期全量修正。每层独立快照，回溯和重算精确到分区粒度。

07 / PERFORMANCE REFERENCE

关键性能参数参考

合理配置这些参数，可以在写入吞吐、读取延迟、资源消耗之间取得最优平衡。数值为社区典型生产实践参考，需根据实际数据量和集群规格调整。

write-buffer-size（MemTable 大小）64MB ~ 512MB
推荐 256MB，过小增加 Flush 频率，过大增加 OOM 风险。调大前确保 TM heap 充足。
num-sorted-run.compaction-trigger（L0 触发阈值）5 ~ 10
默认 5，过大会导致读放大，过小频繁 Compaction 影响写吞吐。流式场景建议 5~8。
target-file-size（DataFile 目标大小）64MB ~ 256MB
默认 128MB，对应 Parquet Row Group 分布。批量场景可调大至 256MB，减少文件数量。
Checkpoint 间隔（流式写入可见延迟）30s ~ 300s
Checkpoint 间隔 = 数据可见最大延迟。实时性要求高可设 30~60s，稳定性优先设 120~300s。
TUNING STRATEGY
流批一体场景下，建议将 Compaction 任务拆分为独立 Flink Job（写入 Job 设置 write.compaction-skip=true），避免 Compaction 与写入竞争 CPU/IO 资源，两者分别独立扩容，整体吞吐可提升 30%~50%。
