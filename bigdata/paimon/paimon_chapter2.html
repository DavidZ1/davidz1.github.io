01 / CHANGELOG ROW TYPES

Changelog 四种行类型

Paimon 用四个行类型标记（RowKind）表达数据库的所有变更语义，这是实现流式精确语义处理的基石。

+I
INSERT（插入）
全新记录插入。对应数据库 INSERT 操作，或 UPDATE 之后的新值（配合 -U 使用）。Append-Only 表仅支持此类型。
-D
DELETE（删除）
记录删除。对应数据库 DELETE 操作。下游算子需要根据主键找到该记录并撤销，是实现精确聚合的关键。
-U
UPDATE_BEFORE（更新前值）
UPDATE 操作中被修改前的旧值。与 +U 配对出现，用于下游撤回旧聚合结果，常见于 CDC 摄取完整 UPDATE 事件。
+U
UPDATE_AFTER（更新后值）
UPDATE 操作中修改后的新值，替换旧记录。Primary Key Table 写入时以主键为准 Upsert，无需 -U 即可正确更新。
CHANGELOG EVENTS — MySQL UPDATE 示例 
-- MySQL 执行: UPDATE orders SET amount=200 WHERE id=1001
-- Flink CDC 解析后生成如下两条 Changelog 记录:

┌─────────────────────────────────────────────────────────┐
│  RowKind │   id   │  amount  │  status   │  updated_at  │
├─────────────────────────────────────────────────────────┤
│    -U    │  1001  │   100    │  PENDING  │  2024-01-01  │  ◄ 旧值（撤回）
│    +U    │  1001  │   200    │  PENDING  │  2024-01-01  │  ◄ 新值（写入）
└─────────────────────────────────────────────────────────┘

-- Paimon Primary Key Table 仅需 +U，内部按主键 Upsert:
-- 写入时自动合并（Merge Engine: deduplicate），保留最新值
-- 若 changelog-producer = 'full-compaction'，则同时生成 -U/+U 供下游流读
DESIGN INSIGHT
Paimon 的 Primary Key Table 写入时只需 +I 和 +U，但读取时（流式消费）可以产出完整的四种 RowKind，这是通过 Compaction 过程中对比相邻版本实现的。写入语义与读取语义分离是 Paimon 的核心设计之一。
02 / CHANGELOG PRODUCER

Changelog 产出模式

Paimon 提供三种 changelog-producer 策略，决定下游流式消费者能读到什么粒度的变更事件。

── none（默认）── 仅写入，不产出 Changelog
Writer
→
Paimon Table
→
下游只能全量读（Batch）
── input ── 透传上游 Changelog（适合 CDC 链路）
CDC Source (+I/-D/+U/-U)
→
Paimon Table
→
下游读到完整 4 种 RowKind
── full-compaction ── Compaction 时对比版本产出 Changelog（延迟较高）
任意 Writer
→
Paimon Table
→
Compaction 比对
→
完整 Changelog 输出
── lookup ── 写入时查 RocksDB 旧值，实时产出（低延迟，高成本）
Writer
→
Lookup 本地 RocksDB
→
Paimon Table
→
实时 Changelog
DDL — 配置 changelog-producer 
CREATE TABLE orders (
  order_id   BIGINT,
  user_id    BIGINT,
  amount     DECIMAL(12, 2),
  status     STRING,
  PRIMARY KEY (order_id) NOT ENFORCED
) WITH (
  'connector'             = 'paimon',
  'changelog-producer'    = 'input',         -- 透传上游 CDC 事件
  'merge-engine'          = 'deduplicate',   -- 主键去重，保留最新
  'write-buffer-size'     = '256 mb',
  'num-sorted-run.compaction-trigger' = '5'
);
IMPORTANT
lookup 模式会在每个 TM 本地维护 RocksDB 状态，写入延迟最低但磁盘和内存开销最高。full-compaction 模式无额外开销但存在分钟级延迟，适合离线+准实时混合场景。
03 / CDC SOURCE INGESTION

多源 CDC 接入架构

Paimon 原生支持通过 Flink CDC 接入多种数据库，无需中间 Kafka 即可实现数据库变更到湖仓的直接同步。

MySQL

MySQL / MariaDB

基于 Debezium 解析 Binlog，支持全量初始化 + 增量 CDC 无缝衔接。支持多表同步、整库同步，可自动建表到 Paimon Catalog。

Binlog 全量+增量 整库同步 Schema Change
Postgres

PostgreSQL

基于 WAL（Write-Ahead Log）解析，需开启 wal_level = logical。支持 pgoutput / decoderbufs 插件，表级别精确订阅。

WAL Logical pgoutput decoderbufs
Mongo

MongoDB

基于 Change Streams 实现，支持 Oplog 全量读取，文档级别变更捕获。嵌套 JSON 结构自动展平或保留为 MAP 类型写入 Paimon。

Change Streams Oplog JSON Flatten
Kafka

Kafka (Debezium / Canal)

消费 Kafka 中已经由 Debezium 或 Canal 产出的 CDC 消息，通过 Flink Kafka Source 解析后写入 Paimon，适合已有 Kafka 中间层的企业架构。

Debezium JSON Canal JSON Ogg JSON
Flink CDC — MySQL 整库同步到 Paimon（Action Jar 方式） 
## 推荐方式：使用 Paimon Action Jar，无需写 Flink SQL
bin/flink run \
  -c org.apache.paimon.flink.action.FlinkActions \
  paimon-flink-action-*.jar \
  mysql_sync_database \
  --warehouse hdfs:///warehouse/paimon \
  --database  ods_mysql \
  --mysql-conf hostname=mysql-host \
  --mysql-conf port=3306 \
  --mysql-conf username=root \
  --mysql-conf password=secret \
  --mysql-conf database-name=source_db \
  --catalog-conf metastore=hive \
  --catalog-conf uri=thrift://hive-metastore:9083 \
  --table-conf   changelog-producer=input \
  --table-conf   merge-engine=deduplicate \
  --including-tables 'orders|users|products'  -- 正则过滤
SCHEMA EVOLUTION
Paimon 的 MySQL CDC 整库同步支持自动感知上游 DDL 变更（加列、改类型），通过 --mysql-conf scan.incremental.snapshot.chunk.size 控制全量阶段的并行切片大小。DDL 变更事件会先暂停 DML 消费，等待 Schema 变更完成后恢复，保证数据一致性。
04 / CONSUMER POSITION

消费位移与读取模式

Paimon 流式读取的起点由 scan 相关参数精确控制，理解不同模式的语义差异是构建可靠数据链路的关键。

scan.mode 语义 适用场景 时效性
default 首次全量扫描，之后增量消费新 Snapshot 初始化数仓，全量+增量一体 取决于 Compaction
latest 跳过历史，从当前最新 Snapshot 开始读 只关心新增变更，不需历史数据 实时
latest-full 先读一次完整快照，再持续增量消费 下游需要完整状态初始化 初始化后实时
from-snapshot 从指定 snapshot-id 开始增量消费 精确断点续传、回溯特定版本 由 snapshot 决定
from-timestamp 从指定时间戳对应的 Snapshot 开始消费 按时间回溯、故障恢复 由时间点决定
compacted-full 等待下一次 Full Compaction 完成后再全量读 需要干净、无重叠的数据快照 Compaction 完成后
Consumer ID — 持久化消费位移 
-- 使用 consumer-id 将消费进度持久化到 Paimon 元数据
-- 即使 Flink Job 重启，也能从上次消费的 Snapshot 继续

SELECT * FROM orders
/*+ OPTIONS(
  'scan.mode'      = 'latest-full',
  'consumer-id'    = 'dwd_orders_consumer_001',   -- 唯一消费者 ID
  'consumer.expiration-time' = '7 d'              -- 位移保留 7 天
) */;

-- 查看消费位移状态（存储在 table 目录下 consumer/ 子目录）
-- consumer/consumer-dwd_orders_consumer_001
-- 内容: {"nextSnapshotId": 42, "consumerId": "dwd_orders_consumer_001"}
05 / END-TO-END PIPELINE

端到端 CDC 同步链路

以 MySQL → Paimon ODS → DWD 实时处理为例，梳理完整的数据流转过程与关键配置节点。

①
SOURCE

MySQL Binlog 采集

开启 MySQL binlog_format=ROW 和 binlog_row_image=FULL，确保捕获完整的行级别前后镜像。Flink CDC Source 并行度建议设为 1（全量阶段），增量阶段可适当提高。

②
ODS LAYER

写入 Paimon ODS 层

使用 changelog-producer=input，原样保存上游 CDC 事件（含 RowKind）。开启 sequence.field 或 rowtime 保证乱序事件的正确合并顺序。

③
DWD LAYER

流式读取 ODS 写入 DWD

从 ODS 表以流模式消费，指定 consumer-id 持久化位移。在 Flink 作业中进行清洗、字段标准化，产出宽表写入 DWD 层 Paimon 表（可选 partial-update 合并多流）。

④
ADS LAYER

实时 OLAP 查询

DWD 层数据通过 StarRocks / Doris 外表或 Trino 直接查询，利用 Paimon 的 Primary Index 和 Bloom Filter 实现高效 point lookup。Compaction 后数据可达到分钟级的查询新鲜度。

⑤
MONITORING

监控与断点续传

通过 Flink Web UI 监控 Changelog 消费延迟（source.records.lag 指标）。利用 Paimon consumer-id 机制，Job 异常重启后自动从最后消费的 snapshot-id 继续，无需人工干预。

06 / COMMON PITFALLS

CDC 接入常见问题

生产环境中 CDC 链路最容易踩的几个坑，提前了解可以节省大量排查时间。

⚡
Binlog 过期导致全量重读

MySQL Binlog 默认保留 7 天，若 Flink Job 停止超过该时长，增量位置失效，需重新全量初始化。建议延长 expire_logs_days 或使用 GTID 模式提升稳定性。

🔄
sequence.field 设置不当

网络抖动或并行写入可能导致事件乱序。若不配置 sequence.field，旧版本数据可能覆盖新版本，造成数据回退。建议使用 update_time 或 Binlog Position 作为序列字段。

📦
全量初始化期间 Binlog 积压

大表全量阶段耗时长（数小时），期间 Binlog 持续产生。Flink CDC 会缓存这段 Binlog，全量完成后追齐增量。若 Binlog 量太大，需评估 TM 磁盘容量，或考虑分批初始化策略。

🗂️
缺少主键或主键不稳定

Paimon Primary Key Table 要求写入数据有确定的主键。若上游表主键包含 UUID、随机字段，会导致 LSM-Tree 文件数暴增、Compaction 效率低下，应在接入层做主键清洗或改用 Append-Only Table。

⏱️
full-compaction 延迟误判

full-compaction 模式的 Changelog 延迟等于 Compaction 触发间隔，默认可达数分钟，不适合秒级延迟要求的场景，应改用 lookup 或 input 模式。

🧹
consumer-id 泄漏

废弃的消费者 ID 会一直阻止对应 Snapshot 被 GC，导致旧文件无法清理，存储持续膨胀。定期检查 consumer/ 目录，清理无用的 consumer-id，或设置 consumer.expiration-time 自动过期。

PRODUCTION CHECKLIST
生产部署 CDC 链路前，务必确认：① MySQL binlog_row_image=FULL ② 网络带宽评估（全量阶段） ③ Paimon 表配置 sequence.field ④ 设置合理的 snapshot 保留策略 ⑤ 配置 consumer-id 并设置过期时间 ⑥ 监控 Flink Checkpoint 耗时（反映写入压力）
