02 — 三种表类型深度对比
主键表
Primary Key Table
基于 LSM-Tree 实现，主键唯一，支持 Upsert/Delete。适合实时更新场景，如维表、宽表构建。
UPSERT DELETE CDC
追加表
Append-only Table
无主键约束，数据只追加，吞吐量极高。适合日志、埋点等不需要更新的高频写入场景。
INSERT APPEND
变更日志表
Changelog Table
保留完整变更历史（+I/-D/+U/-U），消费方可获取精确变更流，是构建实时数仓的关键。
+I -D +U / -U
03 — 六大核心概念
🗂
Snapshot 快照
每次写入产生一个 Snapshot，包含完整的元数据引用。读操作基于 Snapshot 实现隔离，是时间旅行和增量读取的基础。
snapshot-{id}.json
🌿
Branch & Tag
Tag 是对 Snapshot 的命名引用（类似 Git tag），Branch 是独立的演化分支，支持数据的版本管理与回滚。
数据版本控制
📐
Bucket 分桶
数据按 bucket-key 哈希分桶，决定数据的物理分布。Fixed-bucket 固定数量，Dynamic-bucket 自动扩展，影响并发度与 Compaction 策略。
数据分布单元
🔄
Compaction
后台合并小文件，将多个 Level-0 文件向高层合并，减少读放大。支持 Full Compaction 与 Sort Compaction 两种模式。
LSM 合并机制
🧩
Catalog 元数据
支持 FilesystemCatalog、HiveCatalog 和 PaimonCatalog，统一管理 Database、Table 的元数据，与计算引擎解耦。
元数据中枢
⚙️
Merge Engine
决定相同主键数据如何合并：deduplicate（取最新）、partial-update（字段级合并）、aggregation（聚合）、first-row（保留首行）。
主键合并策略
04 — LSM-Tree 存储结构详解
05 — 进阶知识要点
KP-01
为什么 Paimon 选择 LSM-Tree 而非 Copy-on-Write？
LSM 写友好（顺序写 MemTable）+ 后台异步 Compaction，适合高频 Upsert 场景。Iceberg/Delta 的 CoW 每次 Upsert 需重写整个文件，小数据量更新代价极高。Paimon 在流式实时更新场景中因此有明显优势。
KP-02
Partial Update 与 Aggregation Merge Engine 的核心差异
partial-update 允许多流写入同一张表的不同字段列（宽表合并），每次只更新指定字段，null 保留旧值。aggregation 则对数字字段做 sum/max/min 等聚合，适合实时指标累计场景，但回撤处理需特别关注。
KP-03
Dynamic Bucket vs Fixed Bucket 选型策略
Dynamic Bucket（bucket=-1）自动扩缩，适合主键分布不均匀的场景，但跨 bucket 操作有额外开销。Fixed Bucket 并发度固定，适合数据量可预估的场景。生产环境建议先评估数据量增长曲线再决策。
KP-04
Changelog 的三种产生方式及其性能影响
① 源端 CDC 直接产生（推荐）；② Lookup Changelog Generator（查旧值，有 IO 开销）；③ Input Changelog（输入流自带 +I/-D）。选择错误会导致下游消费脏数据或大量回撤，需深刻理解业务语义。
KP-05
Schema Evolution 的边界与限制
Paimon 支持 ADD/DROP/RENAME COLUMN 及部分类型提升（int→long），但不支持收窄类型（bigint→int）。Primary Key 列和 Partition Key 列不可变更。执行 Schema 变更时旧 SST 文件不会立即重写，依赖 Compaction 完成物理迁移。
