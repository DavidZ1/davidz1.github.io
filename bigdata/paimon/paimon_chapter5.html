01 / CORE TUNING PARAMETERS

核心调优参数详解

这些参数决定了 Paimon 写入吞吐、读取延迟和资源消耗的基本面貌，是调优的第一步。每个参数的调整都是一组 trade-off，需结合实际场景权衡。

write-buffer-size
64 mb
推荐范围：128mb ~ 512mb
每个 Writer Task 的 MemTable 上限。调大可减少 Flush 频率，降低 L0 文件数，但会增加内存占用。流式场景推荐 256mb，批量写入可调至 512mb。
写吞吐 ↑ 内存 ↑ 读延迟 ↓
num-sorted-run.compaction-trigger
5
推荐范围：5 ~ 10
L0 文件数超过该阈值触发 Minor Compaction。调小频繁 Compaction 有损写吞吐；调大则 L0 文件堆积，读放大严重。流式高频写入建议 5~8。
写吞吐 ↑↓ 读放大 ↑↓ CPU ↑↓
num-sorted-run.stop-trigger
10
推荐范围：trigger × 2
L0 文件数超过该值时，Writer 暂停写入等待 Compaction 追上。这是防止读放大失控的最后防线，触发过频说明 Compaction 资源不足。
写暂停风险 读质量保障
target-file-size
128 mb
推荐范围：64mb ~ 256mb
Compaction 后每个 DataFile 的目标大小。批量分析场景可调至 256mb，减少文件数提升扫描效率；流式频繁写入场景保持 128mb 平衡写放大。
文件数 ↓ 扫描效率 ↑ 写放大 ↑
snapshot.num-retained.min/max
10 / 无限
推荐：min=10, max=50~100
控制保留的快照数量。min 保障下游消费者有足够的追赶时间；max 防止 Manifest 链过长影响 Commit 性能。两者之间保持合理间距。
存储占用 时间旅行范围
snapshot.time-retained
1 h
推荐范围：1h ~ 24h
按时间保留快照，确保在该时间窗口内的任意时刻都可以做时间旅行查询。与 num-retained 取最大值，两者共同决定 GC 边界。
存储占用 ↑ 回溯能力 ↑
TUNING PRINCIPLE
调优顺序建议：① 先确定业务对写入延迟的容忍度（决定 Checkpoint 间隔）→ ② 根据 TM 可用内存设定 write-buffer-size → ③ 观察 L0 文件数监控曲线，调整 compaction-trigger → ④ 最后微调 target-file-size 和 snapshot 保留策略。避免同时调整多个参数，难以归因效果。
02 / COMPACTION STRATEGIES

Compaction 策略深度解析

Compaction 是 Paimon 性能调优最核心的环节，不同场景需要选择不同的 Compaction 部署模式和触发策略。

MODE 01
同步 Compaction

写入 Job 内部同步执行 Compaction，Compaction 与写入共享 TM 资源。配置简单，适合数据量小、写入 TPS 低的场景。Compaction 耗时会直接影响写入吞吐，在流量峰值时可能导致 Checkpoint 超时。

配置简单 峰值抖动风险 适合低 TPS
MODE 02
异步 Compaction

写入 Job 跳过 Compaction（设置 write.compaction-skip=true），独立部署 Compaction Job 异步处理。写入与 Compaction 资源完全隔离，互不影响。生产高 TPS 场景的推荐方式，两个 Job 可独立扩缩容。

资源隔离 高 TPS 推荐 需维护两个 Job
MODE 03
批量后 Compact

批量导入完成后，手动触发 Full Compaction 一次性整理所有文件。适合 T+1 数据仓库场景：夜间批量导入，完成后执行 Compact，白天查询享受最优读性能。

离线批量推荐 读性能最优 需调度脚本
MODE 04
按分区 Compact

只对指定分区执行 Compaction，避免全表整理的高代价。适合按天分区的数据仓库：每天对前一天分区执行一次 Full Compact，当天分区保持流式写入状态，不影响实时链路。

精细化控制 减少 IO 分区表专用
异步 Compaction Job 部署示例
── 方案一：写入 Job 跳过 Compaction
INSERT INTO dwd_orders
SELECT * FROM ods_orders
/*+ OPTIONS(
  'write.compaction-skip' = 'true'   -- 写入 Job 不做 Compaction
) */;

── 方案一：独立 Compaction Job（持续运行，后台异步整理）
bin/flink run \
  -c org.apache.paimon.flink.action.FlinkActions \
  paimon-flink-action-*.jar \
  compact \
  --warehouse  hdfs:///warehouse/paimon \
  --database   my_db \
  --table      dwd_orders \
  --mode       continuous   -- 持续监听，有新 L0 文件就 Compact

── 方案二：按分区手动触发（适合批量导入后整理）
CALL sys.compact(
  'my_catalog.my_db.dwd_orders',
  'dt=2024-01-01',        -- 仅整理该分区
  'order_id'              -- 指定排序键（可选，加速 point lookup）
);

── 方案三：全表 Full Compaction（将所有数据整理到最高 Level）
CALL sys.compact('my_catalog.my_db.dwd_orders');
03 / SMALL FILE GOVERNANCE

小文件问题诊断与治理

小文件是 Paimon 生产环境最常见的性能瓶颈之一，理解其根源并采取针对性措施，是运维工程师的必备技能。

01

根因：Checkpoint 过于频繁

每次 Checkpoint 都会将 MemTable Flush 为 L0 文件。Checkpoint 间隔 30s 意味着每个 Bucket 每 30s 产生一个文件，长时间运行后 L0 文件堆积。解决：适当延长 Checkpoint 间隔至 60~120s，或增大 write-buffer-size 减少 Flush 次数。

02

根因：Bucket 数量过多

Bucket 数设置过大而实际写入量小，导致每个 Bucket 的文件极小。例如设了 100 个 Bucket 但每天只有 10GB 数据，平均每 Bucket 只有 100MB，远低于 target-file-size。解决：按实际数据量重新规划 Bucket 数，目标每个 Bucket 数百 MB 到数 GB。

03

根因：Compaction 滞后

Compaction 资源不足，L0 文件产生速度快于 Compaction 消化速度，导致文件持续积压。解决：部署独立 Compaction Job，分配足够 CPU/内存资源，或调低 compaction-trigger 更积极地触发合并。

04

根因：动态分区写入倾斜

按时间动态分区时，新分区刚创建只有少量数据，每次 Flush 都生成极小文件。解决：对历史分区定期执行 compact，只让当前活跃分区保持小文件状态，历史分区应是整理好的大文件。

小文件诊断 — 查询文件分布状态
-- 查看表的文件分布情况（按 Level 汇总）
SELECT
  partition,
  bucket,
  level,
  COUNT(*) AS file_count,
  SUM(file_size_in_bytes) / 1024/1024 AS total_mb,
  AVG(file_size_in_bytes) / 1024/1024 AS avg_mb
FROM my_table$files
GROUP BY partition, bucket, level
ORDER BY file_count DESC
LIMIT 20;

-- 关注：file_count 高 + avg_mb 低 = 小文件问题
-- 目标：level=0 的文件数 < compaction-trigger × bucket数

-- 查看 Snapshot 数量（过多会影响 Manifest 解析性能）
SELECT COUNT(*) AS snapshot_count
FROM my_table$snapshots;

-- 查看 Consumer 消费进度
SELECT * FROM my_table$consumers;
04 / GC & STORAGE MANAGEMENT

GC 机制与存储运维

Paimon 的 GC（垃圾回收）依赖快照过期机制自动清理无用文件，但生产环境中各种因素可能阻止 GC 正常工作，需要主动运维。

①

触发条件：Snapshot 过期

每次新 Snapshot Commit 时，Paimon 检查是否有 Snapshot 超过 num-retained.max 或 time-retained 阈值。满足条件的 Snapshot 标记为"候选删除"，但不立即删除。

snapshot.num-retained.max = 50
②

阻塞检查：Consumer 与 Tag

过期 Snapshot 被删除前，会检查是否有活跃 Consumer 的消费位置指向该 Snapshot，以及是否有 Tag 引用它。任一条件满足都会阻止该 Snapshot 及其 DataFile 被 GC。这是最常见的"存储越来越大"根因。

SELECT * FROM my_table$consumers; — 检查僵尸 Consumer
③

引用计数归零：文件进入删除队列

Snapshot 被所有 Consumer 越过且无 Tag 引用后，其持有的 DataFile 引用计数归零。Paimon 将这些文件路径写入 Manifest 的删除记录，等待实际文件系统删除。

④

孤儿文件清理：expire_snapshots

正常 GC 流程之外，可能存在孤儿文件（Checkpoint 失败留下的未提交 DataFile）。使用 expire_snapshots 或 remove_orphan_files 定期清理。

CALL sys.remove_orphan_files('my_catalog.my_db.orders', '2024-01-01 00:00:00')
⑤

存储监控与告警

建议对 Paimon 表目录设置存储用量告警，当增长速率异常时触发人工检查。常见原因：Consumer 消费停滞、Tag 未清理、Compaction 未执行导致 L0 文件堆积、孤儿文件积累。

hdfs dfs -du -h -s /warehouse/paimon/my_db.db/orders/
GC 运维操作手册
── 1. 手动触发快照过期清理
CALL sys.expire_snapshots(
  'my_catalog.my_db.orders',
  30,           -- 保留最近 30 个快照
  '1 h'          -- 保留最近 1 小时内的快照
);

── 2. 清理孤儿文件（谨慎：仅清理超过指定时间的文件）
CALL sys.remove_orphan_files(
  'my_catalog.my_db.orders',
  '2024-01-01 00:00:00'  -- 清理该时间点之前创建的孤儿文件
);

── 3. 清理过期 Consumer（阻止 GC 的僵尸消费者）
CALL sys.expire_consumers(
  'my_catalog.my_db.orders',
  '3 d'  -- 清理 3 天未更新的 Consumer
);

── 4. 查看存储空间占用分布
SELECT
  partition,
  SUM(file_size_in_bytes) / 1024/1024/1024 AS size_gb,
  COUNT(*) AS file_count
FROM orders$files
GROUP BY partition
ORDER BY size_gb DESC;
05 / MONITORING METRICS

生产监控指标体系

建立完善的监控告警体系是 Paimon 稳定运行的基础，以下是最关键的监控维度和推荐告警阈值。

指标分类指标名称含义告警阈值异常原因
写入健康 compaction.levels.num-sorted-run 当前 L0 文件数 > stop-trigger 的 80% Compaction 跟不上写入
writer.flush-time MemTable Flush 耗时 > 5s 磁盘 IO 瓶颈
commit.duration Snapshot Commit 耗时 > Checkpoint 间隔的 30% Manifest 链过长
读取健康 scan.split-time Split 生成耗时 > 30s 文件数过多，Manifest 解析慢
source.records.lag 流式消费延迟（条数） > 10 万 下游消费能力不足
存储健康 snapshot.count 当前 Snapshot 总数 > 200 GC 被阻止，Consumer 僵尸
storage.size.growth-rate 存储增长速率 持续 1h 超过预期 200% 孤儿文件积累或 GC 失效
Compaction compaction.duration 单次 Compaction 耗时 > 10min 单文件过大或资源不足
MONITORING SETUP
Paimon 的 Flink 作业指标通过 Flink Metrics 体系暴露，可接入 Prometheus + Grafana 做可视化。建议为每张核心业务表建立独立 Dashboard，重点监控 L0 文件数曲线和 Commit 耗时趋势，这两个指标能最早预警性能劣化。
06 / READ PERFORMANCE

读取性能优化策略

写入调优决定数据新鲜度，读取调优决定查询体验。以下策略能显著提升批量扫描和 point lookup 性能。

批量扫描优化

分区裁剪效果扫描量↓ 80%+
列裁剪（Column Pruning）IO↓ 60%+
统计信息下推（Row Group Skip）读行数↓ 40%+
Full Compaction 后扫描文件数↓ 70%

Point Lookup 优化

Primary Key IndexO(log n) 查找
Bloom Filter（主键命中）False Positive <1%
Lookup Join 本地缓存命中延迟↓ 毫秒级
Sorted Run 数越少合并成本 ↓ 线性
读取优化配置 — Bloom Filter 与 Secondary Index
-- 开启 Bloom Filter（减少不必要的文件读取）
CREATE TABLE orders (
  order_id BIGINT,
  user_id  BIGINT,
  amount   DECIMAL(12,2),
  PRIMARY KEY (order_id) NOT ENFORCED
) WITH (
  'file.format'              = 'parquet',
  'metadata.bloom-filter.columns' = 'order_id,user_id',  -- 对这些列建 BF
  'metadata.bloom-filter.enabled' = 'true'
);

-- 二级索引（Paimon 0.8+，加速非主键点查）
CREATE TABLE orders_with_index (
  order_id BIGINT,
  user_id  BIGINT,
  status   STRING,
  PRIMARY KEY (order_id) NOT ENFORCED
) WITH (
  'secondary-index.columns' = 'user_id'   -- 对 user_id 建二级索引
);

-- 查询时自动利用二级索引
-- SELECT * FROM orders_with_index WHERE user_id = 12345;
-- ↑ 通过索引找到 order_id，再按主键点查，避免全表扫描
07 / OPS CHECKLIST

生产运维检查清单

将以下检查项纳入日常巡检和发布流程，可有效预防大多数生产问题。

⚡ 日常巡检（每日）

✓
检查各核心表 L0 文件数，是否接近 stop-trigger 阈值
✓
确认 Compaction Job 状态正常，无异常退出
✓
验证各 CDC 链路的 Checkpoint 成功率 > 99.9%
✓
检查 Snapshot 总数是否在预期范围内
✓
确认 Consumer 消费延迟在告警阈值以内

🗂️ 周度运维（每周）

✓
对历史分区执行一次按分区 Compact，整理小文件
✓
清理废弃 Consumer ID，解除对旧 Snapshot 的 GC 阻塞
✓
检查孤儿文件，执行 remove_orphan_files 清理
✓
回顾存储增长曲线，预测未来 4 周容量需求
✓
验证 Tag 保留数量在 tag.num-retained-max 以内

🚀 上线前检查

✓
新表 Bucket 数量规划（数据量 / 目标文件大小）
✓
确认 changelog-producer 与下游消费需求匹配
✓
snapshot 保留策略满足下游最慢消费者的追赶时间
✓
验证 Schema 兼容性，无不支持的类型转换
✓
灰度验证：用 Tag 标记上线前版本，便于快速回滚

🛠️ 故障处置预案

!
数据质量问题 → CALL sys.rollback_to_tag() 回滚
!
写入暂停（stop-trigger 触发）→ 临时扩容 Compaction Job
!
Checkpoint 超时 → 检查 commit.duration，调查 Manifest 链长度
!
存储爆满 → 优先清理孤儿文件，再检查 Consumer 阻塞
!
CDC 作业重启 → 验证 consumer-id 消费位移是否正确继承
PRODUCTION WISDOM
Paimon 生产运维最重要的一条原则：宁可写入暂停，不可读取错误。stop-trigger 触发的写入暂停是可恢复的；但读到错误数据（由错误合并策略或乱序写入导致）造成的业务影响往往是不可逆的。在调优时，永远将数据正确性放在吞吐性能之前。
