01 / JOIN INTERNALS

四种 Join 策略内部机制

Hive 的四种 Join 策略本质上是不同的数据分发方式。理解每种策略的物理实现， 才能在 EXPLAIN 计划中准确识别并针对性调优。

STRATEGY 1 · 最优 · 无 Shuffle
Map Join（广播 Hash Join）
小表在 Job 启动前被完整读入 Driver 内存，序列化为 HashTable 后通过 DistributedCache 分发给每个 Map Task。 Map Task 在本地内存中完成 Probe 匹配，完全没有 Shuffle 阶段。 HybridGraceHashJoin（Hive 2.0+）在内存不足时自动将部分分区 Spill 到本地磁盘，避免 OOM。
小表 → DistributedCache Map 端 HashTable 无 Reducer HybridGrace Spill BROADCAST_EDGE
↓ 表数据过大无法广播时
STRATEGY 2 · 通用 · 有 Shuffle
Reduce-Side Join（Shuffle Hash Join）
两张表的数据都在 Map 阶段按 Join Key 做 Hash 分发，相同 Key 的数据汇聚到同一个 Reducer。 Reducer 收到数据后按标记区分两表，在内存中构建 HashTable（小侧）并探测（大侧）。 网络 Shuffle 是最大开销，热点 Key 会导致单 Reducer 数据爆炸。
两表全量 Shuffle hash(key) % numReducers SIMPLE_EDGE 热点 Key 风险
↓ 两表已按同键分桶时
STRATEGY 3 · 大表友好 · 无全量 Shuffle
SMB Join（Sort-Merge-Bucket Join）
两表按相同 Join Key 分桶且已排序时，对应 Bucket 编号的文件可直接做归并 Join， 类似数据库的 Merge Join。每个 Map Task 只读取对应编号的 Bucket 文件， 无需全量 Shuffle，内存占用极低，适合超大表 Join。
Bucket-to-Bucket 匹配 归并扫描 无全量 Shuffle 前提：同键分桶+排序
↓ 存在热点 Key 时
STRATEGY 4 · 倾斜兜底
Skew Join（热点 Key 特殊处理）
检测到超过 hive.skewjoin.key 阈值的热点 Key 后，将热点 Key 的数据单独 路由到一个额外的 Map Join 处理流程（小表广播），非热点 Key 走正常 Reduce Join。 最终两路结果 UNION 合并。本质是两个 Job 的串联，有额外开销。
热点 Key → Map Join 非热点 → Reduce Join 结果 UNION 两 Job 串联
Join 策略 适用场景 Shuffle 内存压力 倾斜免疫 前提条件
Map Join 大表 × 小表（<25~200MB） 无 中（小表缓存） ✓ 天然免疫 小表可装入内存
Reduce-Side Join 大表 × 大表，通用场景 全量 Shuffle 低（流式处理） ✕ 热点 Key 致命 无特殊前提
SMB Join 超大表 × 超大表，重复 Join 无全量 极低（归并） ✓ 分散到各 Bucket 同键分桶+排序+桶数倍数
Skew Join Reduce Join 出现热点 Key 部分 中 ✓ 热点专项处理 需配置倾斜阈值

Key 分布不均（Join 倾斜）
JOIN 时某些 Key（如 NULL、默认值 0、超级用户 ID）对应的数据行数远超平均水平，被 hash 到同一 Reducer 后该 Reducer 成为长尾任务。最典型：NULL JOIN 时所有 NULL 行都去同一个 Reducer。
📊
Group By 倾斜
GROUP BY 中某个分组值的记录数远多于其他值（如电商中"其他"类目聚合了 80% 的订单），该分组的所有数据集中在单个 Reducer 处理，触发 OOM 或超时。
⚡
COUNT DISTINCT 倾斜
COUNT(DISTINCT col) 默认只有 1 个 Reducer 处理全量数据，天然是最严重的倾斜场景。无论数据分布是否均匀，单 Reducer 的并发限制本身就是致命瓶颈。
skew_diagnosis.hql · 倾斜诊断三步法
━━━ STEP 1：定位倾斜的 Key ━━━
-- 查看 JOIN Key 的数据分布（找出 TOP 热点）
SELECT
    user_id,
    COUNT(*) AS cnt,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER(), 2) AS pct
FROM dwd.user_behavior
WHERE dt = '2024-01-01'
GROUP BY user_id
ORDER BY cnt DESC
LIMIT 20;
-- 若 TOP1 占比 > 5%，大概率存在 Join 倾斜

━━━ STEP 2：确认倾斜 Key 类型 ━━━
-- 检查 NULL Key 的比例
SELECT
    COUNT(*) AS total,
    COUNT(CASE WHEN user_id IS NULL THEN 1 END) AS null_cnt,
    ROUND(COUNT(CASE WHEN user_id IS NULL THEN 1 END) * 100.0 / COUNT(*), 2) AS null_pct
FROM dwd.user_behavior WHERE dt = '2024-01-01';

━━━ STEP 3：在 Tez UI 定位长尾 Task ━━━
-- Tez UI → DAG → Vertex → Tasks 视图
-- 按 Duration 降序排列
-- 若最长 Task 耗时 > 平均 Task 耗时 × 3，判定为倾斜
-- 点击长尾 Task → Counters → 查看 INPUT_RECORDS_PROCESSED
-- 该数字即为该 Reducer 处理的实际行数
03 / NULL KEY SKEW

NULL Key 倾斜治理

NULL 是最常见的倾斜元凶。在 Hive 中，NULL = NULL 为 false， 但 hash(NULL) 始终返回同一个固定值，导致所有 NULL 行被分发到同一 Reducer。

null_key_fix.hql · NULL Key 三种治理方案
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 ❌ 问题 SQL：NULL user_id 全部堆到同一 Reducer
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SELECT a.*, b.user_name
FROM dwd.order_detail a
LEFT JOIN dim.user b ON a.user_id = b.user_id;
-- 若 order_detail 中 10% 的 user_id 为 NULL
-- 所有 NULL 行 → hash(NULL) = 固定值 → 同一 Reducer → 长尾！

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 ✅ 方案1：NULL 随机化（推荐，最简单）
 原理：将 NULL 替换为随机字符串，打散到不同 Reducer
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SELECT a.*, b.user_name
FROM dwd.order_detail a
LEFT JOIN dim.user b
  ON COALESCE(a.user_id, CONCAT('null_', RAND())) = b.user_id;
-- NULL 变成 'null_0.7823...' 等随机字符串
-- 随机字符串不会匹配 dim.user 中任何真实 user_id
-- LEFT JOIN 结果正确（NULL 行匹配不到，保留原行，b.* 为 NULL）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 ✅ 方案2：先过滤后 UNION（逻辑最清晰）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
-- NULL 部分：直接输出，不参与 Join
SELECT a.*, NULL AS user_name
FROM dwd.order_detail a
WHERE a.user_id IS NULL

UNION ALL

-- 非 NULL 部分：正常 Join
SELECT a.*, b.user_name
FROM dwd.order_detail a
JOIN dim.user b ON a.user_id = b.user_id
WHERE a.user_id IS NOT NULL;

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 ✅ 方案3：Hive 自动 Skew Join（hive.optimize.skewjoin）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SET hive.optimize.skewjoin=true;
SET hive.skewjoin.key=100000;  -- 超过此行数视为热点 Key
-- Hive 自动将热点 Key 路由到 Map Join 分支处理
-- 缺点：需要额外一个 Job，整体耗时可能增加 20%
💡
选型建议：NULL 比例 < 1% → 方案3（自动，无需改 SQL）；NULL 比例 1%~20% → 方案1（COALESCE + RAND，改动最小）；NULL 比例 > 20% 或 NULL 有业务语义 → 方案2（UNION ALL，逻辑最清晰，性能最优）。
04 / GROUPBY & COUNT DISTINCT

Group By 倾斜与 COUNT DISTINCT 优化

聚合场景的倾斜与 Join 倾斜机制不同，需要两阶段聚合和改写策略来解决。 COUNT DISTINCT 是生产环境中最高频的性能杀手，掌握其所有改写姿势至关重要。

groupby_skew.hql · 两阶段聚合解决 Group By 倾斜
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 方案1：开启 Map 端预聚合（针对 COUNT/SUM/AVG）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SET hive.map.aggr=true;         -- 开启 Map 端预聚合（默认已开启）
SET hive.groupby.skewindata=true; -- 开启两阶段 Group By（解决热点分组）
-- 效果：第一个 MR Job 随机分发数据做部分聚合
--       第二个 MR Job 按真实 Key 合并最终聚合结果

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 方案2：随机前缀两阶段聚合（手动控制，适合极端倾斜）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
-- 第一阶段：加随机前缀，打散热点 Key 到多个 Reducer
SELECT
    CONCAT(FLOOR(RAND() * 10), '_', category) AS category_rand,
    SUM(amount) AS partial_sum,
    COUNT(*) AS partial_cnt
FROM dwd.order_detail
GROUP BY CONCAT(FLOOR(RAND() * 10), '_', category)

-- 第二阶段：去掉随机前缀，按原始 Key 合并
SELECT
    REGEXP_REPLACE(category_rand, '^[0-9]+_', '') AS category,
    SUM(partial_sum) AS total_sum,
    SUM(partial_cnt) AS total_cnt
FROM above_result
GROUP BY REGEXP_REPLACE(category_rand, '^[0-9]+_', '');
count_distinct.hql · COUNT DISTINCT 全部改写姿势
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 ❌ 反模式：单 Reducer，全量数据，无法并行
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SELECT COUNT(DISTINCT user_id) FROM dwd.user_behavior WHERE dt='2024-01-01';
-- 1 个 Reducer 处理当天全部 1 亿行！

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 ✅ 改写1：子查询 GROUP BY（最通用，精确值）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SELECT COUNT(*)
FROM (
    SELECT user_id
    FROM dwd.user_behavior
    WHERE dt = '2024-01-01'
    GROUP BY user_id   -- 并行去重，多个 Reducer
) t;

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 ✅ 改写2：随机前缀两阶段 COUNT DISTINCT
    适合：极高基数去重 + 数据均匀分布
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SELECT SUM(partial_cnt) AS total_uv
FROM (
    SELECT
        prefix_key,
        COUNT(DISTINCT user_id) AS partial_cnt  -- 每个前缀分组内独立去重
    FROM (
        SELECT
            FLOOR(RAND() * 64) AS prefix_key, -- 64 个分桶
            user_id
        FROM dwd.user_behavior WHERE dt='2024-01-01'
    ) t1
    GROUP BY prefix_key
) t2;
-- ⚠️ 注意：此改写只有在 user_id 均匀分布时才精确！
-- 若 user_id 有重复跨桶，会导致重复计数，结果偏高。
-- 精确方案用改写1，近似估算可用 HyperLogLog UDF。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 ✅ 改写3：Hive 3.x 自动优化（最省力）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SET hive.optimize.countdistinct=true; -- Hive 3.x+ 自动拆分 COUNT DISTINCT
-- 原 SQL 不变，Hive 自动在编译期改写为两阶段执行
SELECT COUNT(DISTINCT user_id) FROM dwd.user_behavior WHERE dt='2024-01-01';
⚠️
多字段 COUNT DISTINCT 陷阱：SELECT COUNT(DISTINCT a), COUNT(DISTINCT b) FROM t 无法用单次 GROUP BY 改写——两个去重列不同，必须分两个子查询分别计算后 CROSS JOIN 合并，或使用窗口函数重写。盲目改写会得到错误结果。
05 / SMB JOIN PRACTICE

SMB Join 完整实战

Sort-Merge-Bucket Join 是处理超大表 Join 的终极武器，但配置复杂、前提严格。 一旦正确建立，Join 性能可媲美 Map Join，且不受小表大小限制。

1
建表时指定分桶与排序
两张表必须按相同的 Join Key 列分桶，且桶数有倍数关系（如 256 和 128），同时指定 SORTED BY 该列。分桶数建议选 2 的幂次，便于倍数关系匹配。
2
写入时强制分桶（关键！）
Hive 不会强制验证写入数据是否真正分桶。必须设置 hive.enforce.bucketing=true 或在写入 SQL 中手动保证 Reducer 数 = 桶数。写入时的 Reducer 数必须与 CREATE TABLE 声明的桶数完全一致，否则 SMB Join 退化为普通 Reduce Join。
3
开启 SMB Join 相关参数
同时开启 hive.auto.convert.sortmerge.join、hive.optimize.bucketmapjoin、hive.optimize.bucketmapjoin.sortedmerge 三个参数，优化器才会考虑 SMB Join 执行路径。
4
用 EXPLAIN 验证是否真正触发
在 EXPLAIN 输出中查找 Sorted Merge Bucket Map Join 字样。若看到普通 Map Join 或 Reduce Join，说明前提不满足，需检查桶数、排序列、写入方式是否正确。
smb_join_full.hql · SMB Join 完整配置示例
-- ① 建表：两表按同一 Join Key 分桶 + 排序
CREATE TABLE dwd.order_fact (
    order_id   BIGINT,
    user_id    BIGINT,
    amount     DECIMAL(10,2)
)
CLUSTERED BY (user_id) SORTED BY (user_id ASC) INTO 256 BUCKETS
STORED AS ORC;

CREATE TABLE dim.user_profile (
    user_id    BIGINT,
    user_name  STRING,
    city       STRING
)
CLUSTERED BY (user_id) SORTED BY (user_id ASC) INTO 256 BUCKETS
STORED AS ORC;

-- ② 写入时强制 Reducer 数 = 桶数（关键！）
SET hive.enforce.bucketing=true;  -- Hive 自动设置 Reducer 数 = 桶数
INSERT OVERWRITE TABLE dwd.order_fact
SELECT order_id, user_id, amount
FROM ods.raw_orders WHERE dt='2024-01-01';
-- 验证：hdfs dfs -ls /warehouse/dwd.db/order_fact/
-- 应该正好有 256 个文件（000000_0 到 000255_0）

-- ③ 开启 SMB Join
SET hive.auto.convert.sortmerge.join=true;
SET hive.optimize.bucketmapjoin=true;
SET hive.optimize.bucketmapjoin.sortedmerge=true;
SET hive.enforce.sortmergebucketmapjoin=false; -- false=不满足时静默退化，true=报错

-- ④ 执行 Join（无需 Hint，优化器自动识别）
EXPLAIN
SELECT a.order_id, b.user_name, a.amount
FROM dwd.order_fact a
JOIN dim.user_profile b ON a.user_id = b.user_id;
-- EXPLAIN 输出中应出现：
-- "Sorted Merge Bucket Map Join Operator"
-- 而非 "Map Join Operator" 或 "Join Operator"
SMB Join 最适合的场景 推荐
  • 超大表（百亿级）与超大表 Join，Map Join 内存装不下
  • 同一 Join Key 在多个 ETL 任务中反复使用
  • 数仓维度表（大维度）关联事实表
  • 数据已有自然排序倾向，写入开销可接受
SMB Join 不适合的场景 慎用
  • Join Key 选择性低（如性别、状态码），桶内数据量不均
  • 数据更新频繁导致桶文件数不稳定
  • 一次性临时分析查询，建分桶表成本不值得
  • 两表桶数无法调整为倍数关系
06 / HOT KEY ULTIMATE

hot_key_split.hql · 热点 Key 分离处理完整实现
-- ① 首先识别热点 Key（阈值根据实际数据量调整）
CREATE TEMPORARY TABLE tmp_hot_keys AS
SELECT seller_id
FROM dwd.order_detail WHERE dt='2024-01-01'
GROUP BY seller_id
HAVING COUNT(*) > 500000; -- 超过 50W 条视为热点卖家

-- ② 热点 Key 走 Map Join（小表广播 dim.seller）
SELECT /*+ MAPJOIN(b) */
    a.order_id, a.seller_id, a.amount,
    b.seller_name, b.shop_type,
    'hot' AS join_type
FROM (
    SELECT a.*
    FROM dwd.order_detail a
    JOIN tmp_hot_keys h ON a.seller_id = h.seller_id
    WHERE a.dt = '2024-01-01'
) a
JOIN dim.seller b ON a.seller_id = b.seller_id

UNION ALL

-- ③ 非热点 Key 走正常 Reduce Join
SELECT
    a.order_id, a.seller_id, a.amount,
    b.seller_name, b.shop_type,
    'normal' AS join_type
FROM dwd.order_detail a
JOIN dim.seller b ON a.seller_id = b.seller_id
LEFT ANTI JOIN tmp_hot_keys h ON a.seller_id = h.seller_id
-- 或用 NOT IN/NOT EXISTS 排除热点 Key
WHERE a.dt = '2024-01-01'
  AND a.seller_id NOT IN (SELECT seller_id FROM tmp_hot_keys);

-- ④ 效果验证：查看两个分支的行数比例
SELECT join_type, COUNT(*) FROM above_result GROUP BY join_type;

常见倾斜场景与治理手段速查

倾斜场景 根因 推荐治理手段 是否改 SQL 效果
NULL Key JOIN hash(NULL) 固定值 COALESCE + RAND() 随机化 需改 SQL ★★★★★
热点 Key JOIN 业务真实热点（超级卖家/大商户） 热点分离 + Map Join UNION 需改 SQL ★★★★★
GROUP BY 倾斜 分组值分布不均（80/20 法则） hive.groupby.skewindata=true 无需改 ★★★★☆
COUNT DISTINCT 单 Reducer 处理全量 改写为子查询 GROUP BY 需改 SQL ★★★★★
JOIN Key 类型隐式转换 INT/STRING 比较触发全表广播 统一列类型，消除隐式转换 需改 DDL ★★★★☆
动态分区写入倾斜 某分区数据量远超其他 增加 distribute by 打散写入 需改 SQL ★★★☆☆
🔥
隐式类型转换触发全表广播，Map Join 失效
当 JOIN ON 两侧列类型不一致时（如 a.user_id BIGINT = b.user_id STRING），Hive 会将整张小表的所有行转为字符串后做字符串匹配，但更致命的是：类型转换使 CBO 无法估算 Join 选择率，可能触发错误的执行计划。务必保持 JOIN Key 两侧类型完全一致，修改 DDL 统一类型。
💀
多表 JOIN 顺序错误：大表在前，内存 OOM
Hive 在 Map Join 场景中，多表连续 Join 时会将 Join 右侧的小表全部广播到内存中构建 HashTable。若 CBO 统计信息缺失，可能错误地将大表当作"小表"广播，导致 Task OOM。排查方法：EXPLAIN 查看每个表的 Statistics: Num rows，确认与实际行数量级一致。
⚡
SMB Join 静默退化：桶数不是倍数关系
若表 A 有 256 个 Bucket，表 B 有 200 个 Bucket，两者没有倍数关系，SMB Join 条件不满足，Hive 会静默退化为普通 Reduce Join（若 hive.enforce.sortmergebucketmapjoin=false）。整个 SQL 正常执行，但性能远未达到预期。监控手段：EXPLAIN 验证 Join 类型，生产前必须确认 EXPLAIN 输出。
