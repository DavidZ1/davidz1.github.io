02 / SPARK INTEGRATION

Spark on Hive 深度集成

Spark 与 Hive 的集成是生产环境中最常见的组合，但也是最容易踩坑的地方。 核心问题在于：普通表和 ACID 表的读写方式截然不同，混淆使用会导致静默数据错误。

直接读写（非 ACID 表）推荐
  • Spark enableHiveSupport() 注册 HMS 为默认 Catalog
  • 直接 spark.table("db.table") 读取 ORC/Parquet 表
  • 写入用 df.write.mode("overwrite").saveAsTable()
  • 分区表写入需 df.write.partitionBy("dt")
  • 统计信息自动收集：spark.sql.statistics.size.autoUpdate.enabled
HWC（ACID 事务表）ACID 必须
  • 引入 hive-warehouse-connector 依赖
  • HiveWarehouseSession.session(spark).table() 读取
  • 底层通过 JDBC 连接 HiveServer2 执行读取
  • 写入：hwc.save("db.table") 或 hwc.merge()
  • 性能低于直接读（经过 HS2 中转），但保证 ACID 一致性
spark_hive_integration.py · Spark 集成 Hive 完整示例
from pyspark.sql import SparkSession

━━━ 1. SparkSession 初始化（连接 Hive Metastore） ━━━
spark = (SparkSession.builder
    .appName("HiveIntegration")
    .enableHiveSupport()           # 必须！启用 Hive Catalog
    .config("spark.sql.hive.metastore.version", "3.1.3")
    .config("spark.sql.hive.metastore.jars", "path")
    .config("hive.metastore.uris", "thrift://hms-host:9083")
    # 写入时自动收集统计信息（供 Hive CBO 使用）
    .config("spark.sql.statistics.size.autoUpdate.enabled", "true")
    # ORC 向量化读（与 Hive ORC 格式兼容）
    .config("spark.sql.orc.impl", "native")
    .config("spark.sql.orc.enableVectorizedReader", "true")
    .getOrCreate())

━━━ 2. 读取普通 Hive 表（ORC/Parquet，推荐） ━━━
# 方式1：通过 Catalog 读取（最简单）
df = spark.table("dwd.user_behavior")

# 方式2：分区裁剪（Spark 会自动下推 WHERE 到 Hive 分区）
df = spark.sql("""
    SELECT user_id, item_id, behavior
    FROM dwd.user_behavior
    WHERE dt = '2024-01-01'          -- 分区裁剪
      AND behavior IN ('buy', 'cart') -- 谓词下推到 ORC 列统计
""")

━━━ 3. 写入 Hive 分区表（INSERT OVERWRITE 语义） ━━━
(result_df
    .write
    .mode("overwrite")
    .option("compression", "snappy")
    .partitionBy("dt")              # 动态分区写入
    .format("orc")
    .saveAsTable("dwd.user_summary"))

# ⚠️ 重要：写入后刷新 Spark Catalog 缓存
spark.catalog.refreshTable("dwd.user_summary")
# 若 Hive 也需要查询最新数据，同步执行：
spark.sql("MSCK REPAIR TABLE dwd.user_summary")

━━━ 4. 读取 ACID 事务表（必须使用 HWC） ━━━
from pyspark_llap import HiveWarehouseBuilder

hwc = HiveWarehouseBuilder.session(spark).build()

# HWC 读取（底层走 JDBC→HS2→ACID 读取链路）
acid_df = hwc.table("dwd.orders")  # ACID 表

# HWC 写入 ACID 表
(result_df.write
    .format(HiveWarehouseSession.HIVE_WAREHOUSE_CONNECTOR)
    .option("table", "dwd.orders")
    .save())

# ❌ 错误！直接读取 ACID 表会读到 delta/delete_delta 原始文件
# bad_df = spark.table("dwd.orders")  # 数据包含已删除行！静默错误！
🚨
最高危陷阱：Spark 直接读取 Hive ACID（Transactional）表，会将 delta 目录和 delete_delta 目录中的原始文件全部扫描并合并，无法理解 ValidWriteIdList 语义，结果包含被删除的行、重复的行。这是静默数据错误，查询不报错但结果不正确。唯一正确方式：HWC 或 JDBC 读取 HS2。
03 / FLINK STREAMING

Flink Hive Catalog 流批一体

Flink 通过 HiveCatalog 将流处理结果实时写入 Hive 分区表， 实现数据分钟级刷新的近实时数据湖，是替代传统 T+1 ETL 的核心架构方案。

flink_hive_catalog.java · Flink 流写 Hive 分区表完整示例
// ━━━ 1. 注册 HiveCatalog ━━━
EnvironmentSettings settings = EnvironmentSettings
    .newInstance().inStreamingMode().build();
TableEnvironment tEnv = TableEnvironment.create(settings);

HiveCatalog hiveCatalog = new HiveCatalog(
    "hive_catalog",           // Catalog 名称（Flink SQL 中引用）
    "dwd",                    // 默认数据库
    "/etc/hive/conf"          // hive-site.xml 所在目录
);
tEnv.registerCatalog("hive_catalog", hiveCatalog);
tEnv.useCatalog("hive_catalog");

// ━━━ 2. 在 Flink SQL 中直接使用 Hive 表 ━━━
tEnv.executeSql("""
    SELECT * FROM hive_catalog.dwd.user_behavior
    WHERE dt = '2024-01-01'
""");  // 批读 Hive 表，直接读 HDFS ORC 文件

// ━━━ 3. 流写 Hive 分区表（核心：Partition Commit） ━━━
tEnv.executeSql("""
    CREATE TABLE kafka_source (
        user_id   BIGINT,
        item_id   BIGINT,
        behavior  STRING,
        ts        TIMESTAMP(3),
        WATERMARK FOR ts AS ts - INTERVAL '5' SECOND
    ) WITH (
        'connector' = 'kafka',
        'topic'     = 'user_behavior',
        'properties.bootstrap.servers' = 'kafka:9092',
        'format'    = 'json'
    )
""");

tEnv.executeSql("""
    INSERT INTO hive_catalog.dwd.user_behavior_realtime
    /*
     * 关键配置说明（在 Hive 表的 TBLPROPERTIES 中设置）：
     * 'sink.partition-commit.trigger'    = 'partition-time'
     *    -- 按分区时间触发提交（非处理时间）
     * 'sink.partition-commit.delay'      = '1 min'
     *    -- 分区数据延迟 1 分钟后触发 Commit（等待迟到数据）
     * 'sink.partition-commit.policy.kind'= 'metastore,success-file'
     *    -- 提交策略：1) 通知 HMS 新分区 2) 写入 _SUCCESS 文件
     * 'partition.time-extractor.kind'    = 'default'
     *    -- 从分区路径提取时间（如 dt=2024-01-01/hour=14）
     */
    SELECT user_id, item_id, behavior,
           DATE_FORMAT(ts, 'yyyy-MM-dd') AS dt,
           DATE_FORMAT(ts, 'HH')         AS hour
    FROM kafka_source
""");  // 每分钟提交一个小时分区，Hive 任务可感知新分区
1
Kafka → Flink 实时消费
Flink 消费 Kafka 中的实时数据，按事件时间划分窗口，水位线控制迟到数据处理策略（允许 5 秒延迟）。
2
Flink → Hive 分区表（分钟级写入）
Flink Hive Streaming Sink 按小时分区写入 HDFS ORC 文件，每分钟滚动生成新文件。Partition Commit 机制确保分区写完后通知 HMS，避免 Hive 读取到不完整分区。
3
Hive → T+0 分析查询
Hive/Presto/Trino 可在分区 Commit 后立即查询近实时数据，实现分钟级数据刷新的 T+0 数仓（延迟约 5~15 分钟，取决于 Commit 配置）。
4
小文件合并（定时任务）
Flink 流写产生大量小文件（每分钟一批），需要定时（每小时）运行 ALTER TABLE ... CONCATENATE 合并，或使用 Flink 1.15+ 的 Compact 算子在流水线内合并。
💡
Flink 流写小文件治理：Flink Hive Streaming Sink 每个 Checkpoint 周期（默认 1 分钟）在每个分区生成一个文件，一天产生约 1440 个小文件。Flink 1.15+ 的 auto-compaction 功能可在写入流程中内联合并小文件。短期内仍需在 Hive 侧定时执行 ALTER TABLE ... CONCATENATE 兜底。

05 / ICEBERG MIGRATION

Hive → Iceberg 迁移路径

Apache Iceberg 正在成为数据湖的新标准格式，提供比 Hive ACID 更强大的事务能力。 理解 Iceberg 与 Hive 的关系和渐进式迁移路径，是现代数仓演进的必备知识。

PHASE 1
评估阶段：识别迁移收益与成本
分析现有 Hive 表的使用场景：哪些表有大量 UPDATE/DELETE（迁移 Iceberg 收益大）；哪些是纯 INSERT 批量表（迁移必要性低）；哪些下游依赖 HiveQL 语法（迁移复杂度高）。
场景分析收益评估依赖梳理
PHASE 2
试点阶段：新建 Iceberg 表并行运行
选择 1~2 张高频 UPDATE 的表试点，在 Hive Catalog 中创建 Iceberg 格式表，双写一段时间对比数据一致性和查询性能，验证 Spark/Flink 集成是否正常。
小范围试点双写验证性能对比
PHASE 3
迁移阶段：Hive 表原地转换为 Iceberg
使用 Iceberg 提供的 CALL system.migrate('db.table') 原地转换 Hive 表为 Iceberg 格式（不需要数据复制，仅转换元数据）。转换后兼容 Hive 读取。
原地转换零数据拷贝Hive 兼容读
PHASE 4
完全迁移：下游切换到 Iceberg 原生 API
下游 Spark/Flink 任务从 HiveQL 迁移到 Iceberg 原生 API（SparkCatalog），享受 Hidden Partitioning、Time Travel、增量读取等高级特性。Hive 继续读取（通过 HMS Iceberg 适配层）作为兜底。

核心最佳实践 · 生产黄金法则

01
存储格式：ORC + Snappy，统一标准
生产数仓默认选 ORC + Snappy 压缩。ORC 的 Bloom Filter、Min/Max 索引与 Stripe 级统计信息是 Hive 谓词下推的核心依据；Snappy 兼顾压缩比与 CPU 解压速度。只有需要跨引擎共享（Spark/Presto 为主）时才选 Parquet。
02
分区设计：低基数列 + 合理粒度
分区列选择基数低（日期、地区）、查询频繁过滤的列。单表分区数控制在 10 万以内，超过 50 万触发 Metastore 性能劣化。分区粒度过细（按小时而非按天）会在小数据量场景产生大量空分区。
03
ANALYZE 策略：增量收集，ETL 末端触发
在每个 ETL 任务的最后一步加入增量 ANALYZE，只分析当天写入的分区，不做全表扫描。CBO 的 Join Reorder 完全依赖准确统计信息，缺失统计信息是大量慢查询的根本原因。
04
ACID 选型：优先 insert_only，谨慎用完整 ACID
insert_only 模式（transactional_properties=insert_only）比完整 ACID 轻量 80%，无需分桶、Compaction 开销更低，且 Presto/Trino 可以正常读取。只有真正需要行级 UPDATE/DELETE 的场景才使用完整 ACID。
05
多引擎架构：Hive 写 + Presto 查
Hive on Tez 专注批量 ETL 写入（高吞吐、支持 ACID、CBO 优化成熟）；Presto/Trino 专注 BI 分析和即席查询（低延迟、高并发）。两者共享 HMS 和 ORC 文件，职责分离是现代数仓的最优分工。
06
变更管理：先 EXPLAIN，后执行
任何影响数据的操作前必须先 EXPLAIN：验证分区裁剪是否生效、Join 策略是否最优、Stage 数量是否合理。Schema 变更前评估下游影响，ADD COLUMNS 必须带 CASCADE，列改名必须走渐进式迁移而非直接 CHANGE。
07
小文件治理：预防 > 治疗
在 ETL 写入阶段控制文件大小（通过合理的 Reducer 数和 merge.size.per.task），优于事后合并。Flink 流写场景需专门设计小文件合并管道。HDFS NameNode 小文件上限建议设置告警（>500 万文件/分区），提前干预。
08
倾斜治理：诊断优先，通用方案兜底
数据倾斜治理按成本从低到高：① 开启 hive.groupby.skewindata（无改动）→ ② COALESCE+RAND NULL 随机化（小改 SQL）→ ③ 热点 Key 分离 UNION（大改 SQL）。优先用成本最低的方案，确认无效后再升级策略。

生态集成最高危陷阱：Spark 直读 ACID 表静默数据错误
再次强调：这是集成场景最危险的陷阱。Spark 直接 spark.table("acid_table") 不报错但读取包含已删除行的原始 delta 文件。数据管道静默输出错误数据，直到下游业务发现数字不对。建立 ACID 表访问白名单，所有 ACID 表的 Spark 读取必须走 HWC 或 JDBC，在 CI/CD 流程中自动检测并拦截直接读取 ACID 表的代码。
🔥
多引擎写入同一 Hive 表：文件格式不一致导致读取报错
Hive 写入 ORC 格式，Spark 写入 Parquet 格式，两者混写到同一分区目录。Hive 按表级 SerDe 配置读取，遇到格式不匹配的文件直接报错 IOException: Not an ORC file。生产中必须建立严格的表写入权责制度：每张表只由一个引擎负责写入，其他引擎只读。通过表级权限控制（Ranger）强制执行。
🐌
Presto 读取 Hive 表后元数据缓存过期：查不到新分区
Presto 有自己的 HMS 元数据缓存（默认 1 分钟 TTL）。Hive ETL 任务写入新分区后，Presto 在缓存过期前仍查不到新分区，业务侧误以为数据未就绪。解决方案：① 调短 Presto 缓存 TTL（hive.metastore-cache-ttl=30s）；② 在 Hive ETL 完成后主动调用 Presto REST API 刷新指定表的元数据缓存；③ Hive 写入时同时通知下游（通过消息队列），而非让 Presto 轮询。
