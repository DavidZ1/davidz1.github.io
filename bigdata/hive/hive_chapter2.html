01 / COMPILER PIPELINE

HQL 编译全流程

一条 HQL 从字符串到可执行任务，历经 6 个阶段。每个阶段有不同的数据结构， 也是不同类型报错和性能问题的根源地。

STAGE 1
词法 & 语法解析（Lexer / Parser）
HQL 字符串 → Token 流 → AST（抽象语法树）。由 ANTLR3 文法驱动，完全基于文本，不访问 Metastore。语法错误在此阶段暴露："cannot recognize input near 'X'"。
HiveLexer.g HiveParser.g CommonTree (AST)
STAGE 2
语义分析（SemanticAnalyzer）
AST → QB（QueryBlock）→ Operator Tree（逻辑算子树）。此处首次访问 Metastore 验证表名/列名/类型，同时确定分区裁剪谓词范围，生成初始逻辑计划。类型不匹配报错在此阶段抛出。
QueryBlock TableScanOperator FilterOperator JoinOperator
STAGE 3
逻辑优化（Logical Optimizer）
对 Operator Tree 应用一系列规则（Rule-Based Optimization）和基于代价的优化（CBO，由 Apache Calcite 提供）。包含谓词下推、列裁剪、聚合下推、Join Reorder、子查询展开等核心变换。
PredicatePushDown ColumnPruner JoinReorder (CBO) ConstantFolding
STAGE 4
物理计划生成（Physical Plan Generator）
Operator Tree → Task Tree（MapWork / ReduceWork / TezWork）。决定 Map/Reduce 边界，分配 Shuffle Key，确定每个算子运行在 Map 端还是 Reduce 端，生成执行引擎可理解的物理计划。
MapWork ReduceWork TezWork (DAG) SparkWork
STAGE 5
物理优化（Physical Optimizer）
在物理计划层面应用引擎特定优化：Map Join 转换（小表广播）、Skew Join（数据倾斜特殊处理）、Bucket Map Join、SMB Join（Sort-Merge-Bucket）。此阶段优化对性能影响极大。
MapJoinProcessor BucketMapJoin SkewJoinOptimizer SMBJoin
STAGE 6
任务提交（Task Execution）
Task Tree 序列化后提交至 YARN。Tez 模式下构建 DAG 并通过 TezClient 提交；MapReduce 模式逐 Stage 串行提交 Job。FetchTask 直接在 Driver 端本地执行（如 LIMIT 小结果集）。
TezClient JobClient (MR) FetchTask DDLTask
🔬
调试入口：在 HiveServer2 日志（hiveserver2.log）中搜索 Starting command 可看到每条 HQL 的完整生命周期时间戳，定位是哪个阶段耗时最长。Tez UI 的 DAG 视图则是物理执行阶段最直观的分析工具。
02 / CBO & STATISTICS

Calcite CBO 与统计信息体系

CBO（基于代价的优化器）是 Hive 3.x 最重要的优化机制，但它高度依赖准确的统计信息。 没有统计信息的 CBO 只是空转——理解这套体系，是让优化器真正发挥作用的前提。

4类

Calcite
CBO 底层框架
NDV
最关键统计指标
RBO（规则驱动优化）始终生效
  • 基于固定规则变换，不依赖统计信息
  • 谓词下推 / 常量折叠 / 列裁剪
  • 总是确定性执行，结果可预期
  • 无法感知数据分布，无法做 Join 顺序优化
  • Hive 早期（1.x/2.x）的主要优化手段
CBO（代价驱动优化）需统计信息
  • 基于表/列统计信息估算各计划代价
  • 自动选择最优 Join 顺序（小表驱动大表）
  • 自动判断用 Map Join 还是 Sort-Merge Join
  • 利用 NDV 优化 GROUP BY 和 DISTINCT
  • 统计信息过时或缺失时退化为 RBO
statistics.hql · 统计信息收集完整指南
-- ① 收集表级统计（行数、文件数、总大小）
ANALYZE TABLE dwd.user_behavior COMPUTE STATISTICS;

-- ② 收集列级统计（NDV、Min、Max、Null数、直方图）
ANALYZE TABLE dwd.user_behavior
  COMPUTE STATISTICS FOR COLUMNS
  user_id, item_id, behavior, ts;

-- ③ 对分区表：只分析特定分区（增量方式，推荐）
ANALYZE TABLE dwd.user_behavior
  PARTITION(dt='2024-01-01')
  COMPUTE STATISTICS FOR COLUMNS;

-- ④ 自动统计信息收集（INSERT/CTAS 后自动触发，Hive 3.x）
SET hive.stats.autogather=true;           -- 表级统计自动收集（默认已开启）
SET hive.stats.column.autogather=true;    -- 列级统计自动收集（默认关闭，开启有性能开销）

-- ⑤ 验证统计信息是否已收集
DESCRIBE EXTENDED dwd.user_behavior;
-- 看 parameters 中的 numRows、rawDataSize、COLUMN_STATS_ACCURATE

-- ⑥ 开启 CBO（Hive 3.x 默认开启，验证确认）
SET hive.cbo.enable=true;
SET hive.compute.query.using.stats=true;
SET hive.stats.fetch.column.stats=true;

-- ⑦ 确认 CBO 是否实际生效（看 EXPLAIN 输出中的统计数字）
EXPLAIN CBO
SELECT a.user_id, COUNT(*) FROM dwd.user_behavior a
JOIN dim.user b ON a.user_id = b.user_id
WHERE a.dt = '2024-01-01'
GROUP BY a.user_id;
-- 若输出中 cardinality=xxx 有合理数值，CBO 已生效
⚠️
统计信息陈旧陷阱：ANALYZE 是时间点快照。分区每天写入新数据，但历史分区统计不会自动更新。若 CBO 基于 3 个月前的统计信息做 Join 顺序决策，可能选出完全错误的执行计划。建议在 ETL 管道的最后一步加入增量 ANALYZE，或定期对活跃分区重新收集统计。

03 / JOIN STRATEGIES

Join 策略深度对比

Hive 实现了 4 种本质不同的 Join 物理策略，选择错误的策略是造成任务慢 10 倍的最常见原因。 CBO 自动选择策略，但你必须理解背后的原理才能干预和调优。

Map Join（广播 Join）
最快
SMB Join（桶排序 Join）
快
Reduce-Side Join（普通）
中
Skew Join（倾斜处理）
兜底

 策略1：Map Join（小表广播，无 Shuffle，最快）
 触发条件：小表大小 < hive.mapjoin.smalltable.filesize
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SET hive.mapjoin.smalltable.filesize=25000000; -- 小表阈值 25MB（可适当调大）
SET hive.mapjoin.cache.numrows=25000;          -- 小表缓存行数

-- 手动提示（当自动转换未触发时）
SELECT /*+ MAPJOIN(dim_user) */
    a.user_id, b.user_name
FROM dwd.user_behavior a
JOIN dim.user b ON a.user_id = b.user_id;

 策略2：SMB Join（两表同键分桶 + 排序，无 Reduce Shuffle）
 前提：两表按 JOIN KEY 分桶，且桶数有倍数关系
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SET hive.enforce.sortmergebucketmapjoin=false;

-- 调整 Reducer 数量（影响并行度和内存压力）
SET hive.exec.reducers.bytes.per.reducer=268435456;

 热点 Key 先广播处理，非热点 Key 正常 Shuffle
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SET hive.optimize.skewjoin=true;
SET hive.skewjoin.key=100000;   -- 超过此行数判定为热点 Key
💡
Map Join 不触发？排查顺序：① 确认 hive.auto.convert.join=true；② 检查小表实际大小（HDFS 压缩后的物理大小）是否超过阈值；③ 小表若是子查询，Hive 可能无法估算大小，改用 /*+ MAPJOIN(t) */ Hint；④ 确认 CBO 已有该表的 numRows 统计，否则 CBO 无法判断表大小。

━━━━ 关键信号解读 ━━━━

🟢
BROADCAST_EDGE
Map Join 已生效。小表被广播到所有 Map Task，无 Shuffle 开销。看到这个是最优 Join 信号。
🟡
SIMPLE_EDGE
普通 Hash Shuffle。数据按 key 分发到 Reducer，有网络开销。大表 Join 的正常情况，若出现多次需警惕。
🔵
mode: hash
Map 端预聚合（Combiner）。GROUP BY 场景下极重要，大幅减少 Shuffle 传输量。若未出现，检查 UDF 是否阻止预聚合。
🔴
Num rows: 1
CBO 统计信息缺失的典型标志！CBO 无法估算表大小，回退使用 1 行作为默认值，Join 顺序决策完全失效。
🟣
HybridGraceHashJoin
内存敏感的 Map Join 实现。内存足够时纯内存 Hash Join，内存不足时自动 spill 分区到磁盘，防止 OOM。
⚪
FetchTask
无需 MR/Tez Job 的本地执行任务。简单 SELECT、LIMIT 小结果集、SHOW 命令等直接在 Driver 端执行，速度极快。
05 / OPTIMIZER KNOBS

关键优化器参数配置

以下参数是在生产环境中对 Hive 查询优化影响最大的配置项， 理解每个参数的作用机制，才能在不同场景下灵活调整。

hive.cbo.enable
默认值：true（Hive 3.x）
全局 CBO 开关。开启后使用 Calcite 框架做代价估算和 Join Reorder，依赖 ANALYZE 收集的统计信息。关闭后退化为纯规则优化。
Join Reorder代价模型必须开启
hive.auto.convert.join
默认值：true
自动将 Reduce-Side Join 转为 Map Join（小表广播）。触发条件：小表文件大小 < hive.mapjoin.smalltable.filesize（默认 25MB）。对性能影响极大，必须保持开启。
Map Join消除 Shuffle必须开启
hive.vectorized.execution.enabled
默认值：true（Hive 0.13+）
向量化执行模式，批量处理 1024 行而非逐行处理。对数值计算、过滤、聚合等操作有 2~5x 加速效果。需搭配 ORC 格式使用效果最佳。
ORC 最优批处理加速SIMD
hive.exec.parallel
默认值：false
允许 Stage 间并行执行（无依赖关系的 Stage 同时运行）。对多路 UNION、多个独立子查询场景效果显著，建议生产开启。并发数由 hive.exec.parallel.thread.number 控制（默认 8）。
Stage 并行UNION 优化建议开启
hive.merge.tezfiles / hive.merge.mapfiles
默认值：true / true
任务结束后自动合并小文件。hive.merge.smallfiles.avgsize（默认 16MB）是合并触发阈值，hive.merge.size.per.task（默认 256MB）是目标文件大小。对防止小文件积累至关重要。
小文件合并NameNode 友好必须开启
hive.tez.container.size
默认值：-1（继承 mapreduce.map.memory.mb）
Tez Task Container 内存大小。Map Join 的小表 HashTable 存放在此内存中，OOM 时需增大。建议设为 4~8GB，同时设 hive.tez.java.opts=-Xmx[0.8×container]。
内存调优OOM 防护Map Join 依赖

06 / OPTIMIZER PITFALLS

优化器常见陷阱

即使配置正确，优化器也可能在某些场景下做出错误决策。 以下是生产环境中高频出现的优化器失效场景。

🔥
CBO Join Reorder 反向优化：大表变成驱动表
当统计信息不准（如 ANALYZE 后数据大量增长），CBO 可能将大表排在 Join 左侧（驱动侧），导致内存暴增。排查方法：EXPLAIN CBO 检查各表 cardinality 是否符合实际。临时修复：SET hive.cbo.enable=false 并手动调整 SQL 中表的顺序（小表写在前）。
⚡
谓词下推被 OUTER JOIN 阻断
对于 LEFT JOIN，右表的 WHERE 条件无法下推到 Join 之前（否则改变语义）。SELECT * FROM a LEFT JOIN b ON ... WHERE b.col IS NOT NULL 实际上等价于 INNER JOIN，但优化器需要先执行 Left Join 再过滤，浪费大量计算。解决：改写为 INNER JOIN 或将过滤条件移到 ON 子句内（语义等价时）。
🐌
向量化执行被复杂 UDF 静默禁用
自定义 UDF（GenericUDF）通常不支持向量化，导致整个 Task 退回逐行执行模式。Hive 不会主动报警，性能下降难以察觉。诊断方法：在 Tez UI 的 Task 日志中搜索 NOT vectorized，找到具体原因（通常是 UDF class 名）。解决方案：升级 UDF 实现 VectorizedGenericUDF，或将 UDF 替换为内置函数。
💀
子查询展开失败导致额外 Stage
Hive 会尝试将 IN (SELECT ...) 形式的子查询转换为 JOIN，但对于关联子查询（Correlated Subquery）或过于复杂的嵌套结构，展开可能失败，产生额外的 Stage 和不必要的全表扫描。建议：尽量将子查询改写为显式 JOIN，并用 EXPLAIN 验证 Stage 数量是否符合预期。
🧩
Map Join 触发 OOM：小表实际不小
Map Join 阈值基于压缩后的 HDFS 文件大小，而实际内存中的 HashTable 是解压后数据。ORC/Parquet 压缩比可达 5~10x，一个 25MB 的 ORC 文件解压后可能占用 150~250MB 内存。Task OOM 时先检查小表实际行数，再调整 hive.tez.container.size 或降低 hive.mapjoin.smalltable.filesize 阈值。
🔐
hive.exec.parallel 导致资源竞争反而变慢
Stage 并行执行在 YARN 资源充足时效果显著，但在资源紧张的集群中，多个 Stage 争抢 Container 导致频繁等待，总耗时反而更长。建议在 Session 级别按需开启，生产调度任务中根据集群负载动态决定是否启用。
