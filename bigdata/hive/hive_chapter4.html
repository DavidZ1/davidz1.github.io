01 / ACID ARCHITECTURE

ACID 事务底层架构

Hive ACID（Atomicity, Consistency, Isolation, Durability）并非传统 RDBMS 式的行级锁事务， 而是基于 MVCC（多版本并发控制）和 delta 文件追加的乐观并发模型， 理解这套机制是排查 ACID 相关问题的根基。

MVCC
并发控制模型
delta
增量写入文件格式
SI
快照隔离级别
ORC
ACID 唯一支持格式
TRANSACTION MANAGER · 事务管理层
DbTxnManager（默认，基于 Metastore）
所有 ACID 事务的协调中心，存储在 Metastore 的 TXNS、TXN_COMPONENTS、 WRITE_SET 等表中。负责分配全局递增的 WriteId（写入版本号） 和 TxnId（事务ID），并在提交时做冲突检测。
TXNS 表（事务状态） WRITE_SET（冲突检测） 锁管理（SHARED/EXCL） 心跳超时回滚
↓ 写入时生成
DELTA FILES · 增量文件层
delta_minWriteId_maxWriteId / delete_delta
每次 INSERT/UPDATE/DELETE 都在分区目录下生成新的 delta 文件夹， 而非修改已有文件。UPDATE 拆解为 DELETE（delete_delta）+ INSERT（delta） 两个操作。 每行数据携带 ROW__ID（含 WriteId + BucketId + RowId）作为全局唯一标识。
delta_0000001_0000001/ delete_delta_0000002_0000002/ ROW__ID 结构体 ORC 格式存储
↓ Compaction 后合并为
BASE FILES · 基线文件层
base_maxWriteId（Compaction 产物）
Major Compaction 将 base + 所有 delta 合并为新的 base 文件， 应用所有变更后输出当前最终状态，同时物理删除被 delete_delta 标记的行。 读取时合并 base + 所有新 delta，通过 ValidWriteIdList 过滤可见版本。
base_0000010/ ValidWriteIdList（读可见性） 物理删除标记行 Minor / Major Compaction
💡
为什么 ACID 只支持 ORC？ORC 格式天然支持在文件级别存储 ROW__ID 结构体（事务元数据列），而 Parquet/TextFile 没有对应的行级标识机制。这也是为什么 ACID 表必须 STORED AS ORC，设置 transactional=true 后写入其他格式会报错。
02 / DELTA FILE LAYOUT

delta 文件与 HDFS 目录详解

ACID 表的 HDFS 目录结构与普通表完全不同，理解 base/delta/delete_delta 的命名规则和读取合并逻辑，是排查数据不一致和 Compaction 问题的必要前提。

hdfs_acid_layout.txt · ACID 表 HDFS 目录结构全解
/warehouse/dwd.db/orders/dt=2024-01-01/     ← 分区目录
│
├── base_0000000/                            ← 初始全量写入（第一次 INSERT OVERWRITE）
│   └── 000000_0                             ← Bucket 文件（ORC，含 ROW__ID）
│
├── delta_0000001_0000001/                    ← WriteId=1 的 INSERT 操作
│   └── 000000_0                             ← 新增行（ROW__ID.writeId=1）
│
├── delta_0000002_0000002/                    ← WriteId=2 的 UPDATE（新值部分）
│   └── 000000_0
│
├── delete_delta_0000002_0000002/             ← WriteId=2 的 UPDATE（旧值删除标记）
│   └── 000000_0                             ← 只含 ROW__ID，标记哪些行被删除
│
├── delete_delta_0000003_0000003/             ← WriteId=3 的 DELETE 操作
│   └── 000000_0
│
└── base_0000010/                            ← Minor/Major Compaction 后产生
    └── 000000_0                             ← 合并了 base_0 + delta_1~10，已物理删除被标记行

━━━ 文件命名规则 ━━━
delta_{minWriteId}_{maxWriteId}[_{stmtId}]
  - minWriteId: 此 delta 包含的最小写入版本号
  - maxWriteId: 此 delta 包含的最大写入版本号
  - stmtId: 同一事务内多条语句的区分序号（可选）

delete_delta 同上，但只存储被删除行的 ROW__ID

base_{maxWriteId}:
  - Compaction 产物，表示已合并到该写入版本的所有变更

━━━ 读取时的合并逻辑 ━━━
1. 找到最新的 base_N（基线文件）
2. 读取所有 writeId > N 的 delta 文件（新增行）
3. 读取所有 writeId > N 的 delete_delta（删除标记）
4. 根据 ValidWriteIdList 过滤：只保留已提交事务的 writeId
5. 对相同 ROW__ID 的行，保留最新 writeId 的版本
6. 过滤掉所有在 delete_delta 中出现的 ROW__ID

Minor Compaction 轻量
  • 将多个 delta 文件合并为一个大 delta
  • 不应用 delete_delta，不物理删除行
  • 减少读取时需要扫描的文件数
  • 对正在运行的读取任务影响小
  • 触发：delta 文件数 > hive.compactor.delta.num.threshold（默认10）
Major Compaction 深度清理
  • 将 base + 所有 delta 合并为新的 base 文件
  • 物理应用所有删除标记，移除已删除行
  • 旧文件不立即删除，等 Cleaner 确认无活跃读者后清理
  • 产生大量临时写入，对 HDFS 压力大
  • 触发：delta 大小比例 > hive.compactor.delta.pct.threshold（默认10%）
compaction_ops.hql · Compaction 手动触发与监控
-- 查看表的 Compaction 状态
SHOW COMPACTIONS;
-- 输出字段：Database / Table / Partition / Type / State / Worker / Start / Duration
-- State: initiated / working / ready for cleaning / succeeded / failed / refused

-- 手动触发 Minor Compaction（生产谨慎使用，会占用 YARN 资源）
ALTER TABLE dwd.orders PARTITION(dt='2024-01-01')
  COMPACT 'MINOR';

-- 手动触发 Major Compaction（耗时较长，建议在低峰期执行）
ALTER TABLE dwd.orders PARTITION(dt='2024-01-01')
  COMPACT 'MAJOR';

-- 关键 Compaction 参数
-- hive.compactor.initiator.on=true     启动 Compaction 发起线程（必须在 HMS 上开启）
-- hive.compactor.worker.threads=1      Compaction Worker 数量（建议 2~4）
-- hive.compactor.delta.num.threshold=10  delta 文件数触发 Minor 阈值
-- hive.compactor.delta.pct.threshold=0.1 delta 大小比例触发 Major 阈值

-- 查看表的事务锁状态（排查 ACID 写入阻塞）
SHOW LOCKS dwd.orders PARTITION(dt='2024-01-01') EXTENDED;

-- 查看未完成的事务（超时事务会阻塞 Compaction）
SHOW TRANSACTIONS;
03 / DML OPERATIONS

INSERT / UPDATE / DELETE 深度实战

Hive ACID 的 DML 操作与传统数据库有根本性差异。 理解每类操作的物理实现和性能特征，才能在 ETL 场景中做出正确的使用决策。

INSERT
追加插入
在分区目录下创建新的 delta_N_N/ 文件夹，写入新行（含 ROW__ID）。物理上是纯追加，不修改现有文件。事务提交后新行对后续查询可见。
⚡ 高频 INSERT 产生大量 delta 文件，需要 Compaction 及时清理
UPDATE
更新（拆解为 DELETE+INSERT）
UPDATE 被拆解为两个物理操作：① 在 delete_delta_N_N/ 中写入被更新行的 ROW__ID（标记删除）；② 在 delta_N_N/ 中写入更新后的新行。整个过程无随机写，纯追加。
⚠️ 大批量 UPDATE 产生 delete_delta 膨胀，读取性能下降，需及时 Major Compact
DELETE
软删除（标记删除）
在 delete_delta_N_N/ 文件中写入被删除行的 ROW__ID 结构体，不修改原始数据文件。读取时合并过滤掉标记行，物理删除只在 Major Compaction 时发生。
🗑 大批量 DELETE 后磁盘空间不会立即释放，Major Compaction 后才真正回收
acid_dml.hql · ACID DML 完整示例与注意事项
-- ① 建立 ACID 事务表（必要前提）
CREATE TABLE dwd.orders (
    order_id   BIGINT,
    user_id    BIGINT,
    status     STRING,
    amount     DECIMAL(10,2),
    updated_at TIMESTAMP
)
PARTITIONED BY (dt STRING)
CLUSTERED BY (order_id) INTO 256 BUCKETS
STORED AS ORC
TBLPROPERTIES(
    'transactional'='true',      -- 开启 ACID，建表后不可关闭！
    'transactional_properties'='insert_only'  -- 仅插入模式：更轻量，无需分桶
    -- 完整 ACID 去掉上面 insert_only 行
);

-- ② INSERT（全量初始化）
INSERT INTO dwd.orders
SELECT order_id, user_id, status, amount, updated_at, dt
FROM ods.raw_orders WHERE dt='2024-01-01';

-- ③ UPDATE（批量更新状态）
UPDATE dwd.orders
SET status = 'completed', updated_at = CURRENT_TIMESTAMP()
WHERE dt = '2024-01-01'
  AND order_id IN (SELECT order_id FROM ods.status_update);
-- ⚠️ UPDATE 的 WHERE 必须包含分区列，否则全表扫描所有分区

-- ④ DELETE（物理删除过期数据）
DELETE FROM dwd.orders
WHERE dt = '2024-01-01'
  AND status = 'cancelled'
  AND DATEDIFF(CURRENT_DATE(), TO_DATE(dt)) > 365;

-- ⑤ MERGE（Upsert 场景，Hive 2.2+）
MERGE INTO dwd.orders AS target
USING (
    SELECT order_id, user_id, status, amount, updated_at, dt
    FROM ods.order_updates WHERE dt='2024-01-01'
) AS source
ON target.order_id = source.order_id AND target.dt = source.dt
WHEN MATCHED AND source.updated_at > target.updated_at THEN
    UPDATE SET
        status = source.status,
        amount = source.amount,
        updated_at = source.updated_at
WHEN NOT MATCHED THEN
    INSERT VALUES(source.order_id, source.user_id, source.status,
                   source.amount, source.updated_at, source.dt);
-- MERGE 是 ETL 增量更新的最优写法，一次扫描完成 INSERT+UPDATE
⚠️
insert_only vs 完整 ACID：若业务只需要 INSERT（无 UPDATE/DELETE），强烈推荐使用 transactional_properties=insert_only。insert_only 模式无需分桶、Compaction 开销更低、读取性能更好，且支持 Parquet 格式（Hive 4.x+）。只有真正需要行级 UPDATE/DELETE 时才使用完整 ACID。
04 / SCHEMA EVOLUTION

Schema 演化操作全览

数仓在生产运行中需求变化不可避免。每种 Schema 变更操作的风险程度和 对下游影响截然不同——从安全的加列到危险的改列顺序，必须精确区分。

ADD COLUMN
追加新列（末尾）
最安全的 Schema 变更。新列追加到 Schema 末尾，旧文件中不存在该列时读取返回 NULL（ORC 按列名匹配）。不重写任何数据文件，元数据变更即时生效。
✅ 向后兼容，对已有数据和下游查询无影响
CHANGE COLUMN
列改名 / 类型转换
列改名：ORC 按列名读取，旧文件中的旧列名数据将读取为 NULL（旧列数据丢失！）。类型转换：仅支持兼容性转换（INT→BIGINT），不兼容类型（STRING→INT）会导致读取报错。
⚠️ 列改名实际导致旧数据不可读，生产极危险
REPLACE COLUMNS
重写全部列定义
替换整个列定义列表。ORC 表按列名匹配，只要新 Schema 中列名存在于旧文件，数据仍可读。但若列名/类型对不上，旧数据列全部返回 NULL。列顺序对 ORC 无影响，但 TextFile 是按位置读取，REPLACE COLUMNS 会导致数据错乱！
🚨 TextFile 表禁止使用，ORC 表需谨慎验证

Schema 变更前后对比：安全 vs 危险场景

⚠️ 危险变更（旧数据丢失）
CREATE TABLE orders (
order_id BIGINT,
uid BIGINT, -- 列名 uid
status STRING,
created STRING -- STRING 类型
)
STORED AS ORC;
 
-- 危险：将 uid 改名为 user_id
ALTER TABLE orders
CHANGE uid user_id BIGINT;
-- 旧文件中 uid 列数据全部
-- 变成 NULL！！
✅ 安全变更（向后兼容）
CREATE TABLE orders (
order_id BIGINT,
user_id BIGINT, -- 直接用正确列名建表
status STRING,
created TIMESTAMP -- 直接用正确类型
)
STORED AS ORC;
 
-- 安全：追加新列（末尾）
ALTER TABLE orders
ADD COLUMNS (
updated_at TIMESTAMP,
region STRING
);

CHANGE（类型加宽）INT→BIGINT ✓ 安全 ⚠ 谨慎 ✓ 自动转换 类型扩大，无损 ★★★★☆

05 / DOWNSTREAM IMPACT

Schema 变更对下游链路的影响

Schema 变更的影响链往往超出预期：Hive 表、下游 Spark 任务、 BI 工具、数据质量监控可能同时受到冲击。建立系统化的变更流程是生产必备。

1
影响评估：识别所有下游依赖
通过数据血缘系统（Atlas/DataHub）找出直接引用该表的所有任务、视图、BI报表。重点排查使用 SELECT * 的下游任务——ADD COLUMN 后新列会被意外引入，可能导致下游 Schema 推断错误。
2
测试环境验证：全链路回归
在测试集群上执行 Schema 变更，然后全量运行下游 ETL 任务验证数据一致性。特别注意：Spark 读取 Hive ORC 表时有自己的 Schema 解析逻辑，CHANGE COLUMN 可能只有 Hive 能正确读取，Spark 仍按旧 Schema 读取造成数据错位。
3
灰度变更：新旧兼容并行期
对于影响范围大的变更，先创建新列（ADD COLUMNS），新旧列并行写入一段时间；下游逐步迁移到新列后，再废弃旧列。避免一刀切式强制变更。
4
执行变更：低峰期 + 快速回滚预案
Schema 变更选在业务低峰期执行（DDL 不阻塞读但影响元数据）。ADD COLUMNS 可随时回滚（DROP COLUMN）；CHANGE COLUMN 和 REPLACE COLUMNS 一旦有写入新数据则难以回滚，需提前备份 Metastore 相关表记录。
5
变更后验证：数据质量检查
变更后运行数据质量规则：行数与前日对比、新列 NULL 率是否在预期范围、关键指标同环比是否异常。建立 Schema 变更后自动触发数据质量检测的流程。
schema_change_safe.hql · 安全 Schema 变更操作示例
━━━ 场景1：安全加列（末尾追加，生产标准操作）━━━
ALTER TABLE dwd.orders
  ADD COLUMNS (
    channel   STRING    COMMENT '下单渠道 app/h5/mini',
    coupon_id BIGINT    COMMENT '使用的优惠券ID'
  );
-- 立即生效，旧分区中这两列读取返回 NULL
-- 新写入数据需在 INSERT 语句中显式填充这两列

━━━ 场景2：安全列改名（正确方式：新列+迁移）━━━
-- ❌ 错误方式（旧数据变 NULL）:
-- ALTER TABLE dwd.orders CHANGE uid user_id BIGINT;

-- ✅ 正确方式（渐进式迁移）:
ALTER TABLE dwd.orders
  ADD COLUMNS (user_id BIGINT COMMENT '用户ID（从uid迁移）');

-- ETL 任务中同时写入 uid 和 user_id（兼容期）
INSERT INTO dwd.orders
SELECT ..., uid, uid AS user_id, ... FROM source;

-- 下游全部切换到 user_id 列后，历史分区用 INSERT OVERWRITE 回填
INSERT OVERWRITE TABLE dwd.orders PARTITION(dt='2024-01-01')
SELECT order_id, uid AS user_id, status, amount, ..., dt
FROM dwd.orders WHERE dt='2024-01-01';

━━━ 场景3：CASCADE 分区同步（必须显式指定，否则只改表级 Schema）━━━
ALTER TABLE dwd.orders
  ADD COLUMNS (region STRING) CASCADE;
-- CASCADE: 同步更新所有已有分区的 Schema
-- 若不加 CASCADE，新列只在表级 Schema 有，分区级 DESCRIBE 仍显示旧 Schema
-- 分区级 Schema 覆盖表级，不加 CASCADE 会导致分区读取不到新列！

━━━ 场景4：验证 Schema 变更生效 ━━━
DESCRIBE dwd.orders;                           -- 表级 Schema
DESCRIBE dwd.orders PARTITION(dt='2024-01-01'); -- 分区级 Schema（可能不同！）
DESCRIBE EXTENDED dwd.orders;                  -- 含 SerDe、Storage 完整信息
🚨
ADD COLUMNS 不加 CASCADE 的隐患：Hive 分区的 Schema 独立于表级 Schema 存储在 Metastore。ALTER TABLE t ADD COLUMNS (col STRING) 只修改表级 Schema，已有分区的 Schema 不变。查询已有分区时，Hive 以分区级 Schema为准，新列对旧分区不可见，读取返回缺列或报错。生产变更必须加 CASCADE。
06 / ACID & SCHEMA PITFALLS

ACID 与 Schema 演化常见陷阱

以下是生产环境中高频出现的 ACID 事务和 Schema 变更问题， 每一条都可能导致数据异常、任务失败或数据静默错误（最危险的那种）。

🔥
Compaction 积压：delta 文件爆炸导致查询急速劣化
ACID 表每次写入产生新的 delta 目录。若 Compaction Worker 线程不足或 HMS 压力大导致 Compaction 落后，分区目录下可能积累数百个 delta 文件夹。每次查询都需要打开并合并所有 delta 文件，I/O 开销成倍增加，查询性能下降 10~50 倍。监控指标：SHOW COMPACTIONS 查看队列积压，delta 目录数 > 50 需立即告警并扩充 Worker。
💀
事务超时回滚：长时间 INSERT 任务中途失败数据不一致
Hive 事务默认超时时间由 hive.txn.timeout 控制（默认 300 秒）。超时的事务会被 TxnManager 标记回滚，但已写入 HDFS 的 delta 文件不会立即清理（由 Cleaner 异步处理）。在 Cleaner 运行前，这些孤立 delta 文件不会被读取（ValidWriteIdList 过滤），但占用磁盘空间。大型 ETL 任务需要通过 hive.heartbeat.interval 保持心跳，或将大事务拆分为多个小事务提交。
⚡
Spark 读取 Hive ACID 表：必须使用 Hive Warehouse Connector
Spark 原生读取 ACID 表时无法正确处理 delta/delete_delta 的合并逻辑，会将所有 delta 文件（包括已删除行）全部读出，导致数据重复或读到已删除的数据。必须使用 Hive Warehouse Connector（HWC） 或通过 JDBC 访问 HiveServer2 来正确读取 ACID 表。生产环境中 Spark 直接 spark.table("hive_acid_table") 是静默错误的高危操作。
🐌
MERGE 语句笛卡尔积：ON 条件不包含分区列导致全表扫描
MERGE INTO 的 ON 条件若不包含分区列，Hive 会对 target 表做全分区扫描来寻找匹配行。10 个分区 × 1 亿行 = 10 亿行数据全量处理。MERGE 的 ON 条件必须包含所有分区列，同时确保 source 数据也已按分区列过滤，避免生成笛卡尔积式的执行计划。
🧩
Schema 变更后 Spark 缓存旧 Schema：读取数据错位
Spark 会在会话级别缓存 Hive 表的 Schema 信息。若在 Spark Session 运行期间对 Hive 表执行了 ALTER TABLE（如 ADD COLUMNS），Spark 缓存的旧 Schema 不会自动刷新，后续读取可能按错误的列顺序解析数据（TextFile 表尤为严重）。解决方案：执行 spark.catalog.refreshTable("db.table") 强制刷新 Schema 缓存，或重启 Spark Session。
🔐
转换普通表为 ACID 表：无法直接 ALTER，需重建
已有的非事务表无法直接通过 ALTER TABLE SET TBLPROPERTIES 转为 ACID 表（Hive 会报错或允许但产生不一致状态）。正确方式：① 创建新 ACID 表（正确建表语句）；② INSERT INTO new_acid_table SELECT * FROM old_table 迁移数据；③ 验证后删除旧表。整个过程需要足够的 HDFS 临时空间（约原表 2 倍）。
