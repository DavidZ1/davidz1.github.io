02
🔑 核心根因 · Flush 策略差异（官方文档）
🔴 StarRocks 官方文档明确说明 · Flush 策略
at-least-once  →  buffer 满 / interval 到 / checkpoint 时  ← 三种条件任一触发即 flush
exactly-once    →  ⚠ 仅在 checkpoint 触发时 flush！  ← buffer-flush 参数全部失效！

这意味着配置了 sink.buffer-flush.interval-ms = 1000， 在 exactly-once 模式下完全无效—— 数据会一直积压在 buffer 中，直到下一次 checkpoint 才写入 StarRocks。

exactly-once · Flush 时间线
00:00 数据进入 buffer
00:01 interval 到 → 忽略！不 flush
00:10 buffer 满  → 忽略！不 flush
05:00 checkpoint 触发
     → 才开始 flush → 数据延迟 5 分钟！
at-least-once · Flush 时间线
00:00 数据进入 buffer
00:01 interval 到 → 立即 flush ✓
00:01 数据写入 StarRocks
00:01 数据对外可见 ✓
 → 延迟约等于 interval（1秒）
⚙ Checkpoint 间隔 = 数据延迟下限（exactly-once）
-- 如果 checkpoint 间隔配置为 5 分钟 execution.checkpointing.interval = 300000 -- ms -- 则 exactly-once 模式下，数据最多延迟 5 分钟 数据延迟 ≈ checkpoint interval（与 buffer-flush 参数无关！） -- 这就是"慢几分钟"的直接原因
03
根因二 · exactly-once 2PC 开销 × 3
🔴 两阶段提交 (2PC) 机制
Checkpoint 触发
→
Pre-commit
数据不可见
→
等待所有Sink
3个都完成
→
Commit
数据可见
单流
Checkpoint N
  └→ 1次 2PC 提交
     └→ 数据立即可见 ✓
3流拆分
Checkpoint N
  ├→ Sink1 2PC ... 等待
  ├→ Sink2 2PC ... 等待
  └→ Sink3 2PC ... 等待
    = max(T1, T2, T3) ← 最慢决定延迟
✅ 解决方案
-- 改为 at-least-once，flush 不再依赖 checkpoint 'sink.semantic' = 'at-least-once' -- buffer-flush 参数重新生效，数据秒级写入 'sink.buffer-flush.interval-ms' = '1000'
04
根因三 · partial_update Compaction 堆积
🔴 核心问题：数据完整性依赖 Compaction

3个Sink分别写入同一行的不同字段，每次写入产生独立 Rowset，必须等 Compaction 合并后才得到完整一行。

T1 Sink1 写入 → order_no=001, model_code='X', model_name='Y' → Rowset_A 生成，字段不完整
T2 Sink2 写入 → order_no=001, car_style_id=1, car_style='SUV' → Rowset_B 生成，字段不完整
T3 Sink3 写入 → order_no=001, power_type='EV' → Rowset_C 生成，字段不完整
T4+ Compaction 触发 → A+B+C 合并 → 完整一行 ← 这段等待时间就是"慢几分钟"
⚠ Rowset 堆积速度
-- flush interval = 1秒 单Sink：1秒 → 1个 Rowset 3个Sink：1秒 → 3个 Rowset 1分钟 → 180个 Rowset 堆积 Compaction 线程根本追不上 → 延迟叠加
Merge-on-Read 查询开销
-- Compaction 完成前，每次查询都需要实时 merge SELECT * FROM table WHERE order_no = '001' -- 内部执行： merge(Rowset_A, Rowset_B, Rowset_C, ...) → CPU 开销大
05
根因四 · Buffer Flush 参数验证
⚠ 参数 Key 名称陷阱
-- 你配置的 'sink.buffer-flush.interval-ms' = '1000' -- 部分版本实际识别的 key 'sink.buffer-flush.interval' = '1000' ⚠ Key 名不对时，参数静默忽略 → 使用默认值 300s！ ✓ 检查方式：Flink WebUI → TaskManager → Logs 搜索 "buffer-flush"
你的参数 值 延迟影响 说明
sink.buffer-flush.interval-ms 1000ms ★★★★★ 需确认 key 是否生效
sink.properties.partial_update true ★★★★★ 3流分写，Compaction 压力大
sink.properties.format json ★★ JSON 解析比 CSV 慢，3倍开销
sink.max-retries 10 ★ 失败重试增加延迟
sink.semantic 未配置 ✓ 默认 at-least-once，正确
sink.buffer-flush.max-rows 未配置 ★★★ 使用默认值，可能提前 flush

07
解决方案 · 优先级排序
🥇 最优 · 合并单流

将3个Sink合并为1个，SELECT全字段一次写入，彻底消除 Compaction 等待。

-- 一次写全部字段 INSERT INTO sink SELECT order_no, col_a, col_b, -- 原Sink1 col_c, col_d, -- 原Sink2 col_e, __op -- 原Sink3 FROM source
延迟降至秒级
🥈 快速生效 · 调整参数

确认 flush 参数生效，配合 StarRocks 调整 Compaction 线程。

'sink.buffer-flush.interval' = '1000' 'sink.buffer-flush.max-rows' = '100000' 'sink.semantic' = 'at-least-once'
延迟部分改善
🥉 StarRocks 侧调优

增加 Compaction 线程，降低触发阈值，加快合并频率。

-- BE 配置 cumulative_compaction_num _threads_per_disk = 4 min_cumulative_compaction _num_chunks = 3
治标，非治本
