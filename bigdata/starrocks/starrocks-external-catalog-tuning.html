// 03 元数据缓存优化 — 消灭冷查询延迟
Hive Catalog 元数据策略 HIVE

StarRocks 默认对 Hive 使用懒加载 + 异步更新策略。命中分区后自动缓存，后台刷新保持元数据新鲜度。

FE 动态配置 — 元数据缓存刷新
-- 开启定时元数据刷新（HMS 访问量大时减少依赖）
ADMIN SET FRONTEND CONFIG (
  "enable_background_refresh_connector_metadata"
    = "true"
);

-- 刷新间隔（毫秒）默认 600000 = 10分钟
ADMIN SET FRONTEND CONFIG (
  "background_refresh_metadata_interval_millis"
    = "300000"  -- 5分钟更激进
);

-- 手动强制刷新分区元数据
REFRESH EXTERNAL TABLE
  hive_catalog.sales.orders
  PARTITION ('dt=2024-01-15');
Iceberg Catalog 元数据策略 ICEBERG

StarRocks v3.3+ 重构了 Iceberg 元数据框架，支持分布式并行 Manifest 读取和Manifest 缓存，大幅降低大表首次查询延迟。

系统变量 — 控制元数据读取策略
-- 自动选择（推荐），系统根据节点数和
-- Manifest 文件数自动决策
SET plan_mode = 'auto';

-- 强制分布式元数据读取（超大 Iceberg 表）
SET plan_mode = 'distributed';

-- 开启 Iceberg 定时缓存刷新
ADMIN SET FRONTEND CONFIG (
  "enable_iceberg_metadata_cache" = "true"
);

-- 停止访问后的元数据缓存保留时长（ms）
ADMIN SET FRONTEND CONFIG (
  "iceberg_metadata_cache_expire_time"
    = "86400000"  -- 24小时
);

// 04 CBO 统计信息收集 — 让优化器做正确决策
为什么外部 Catalog 统计信息至关重要 CRITICAL

CBO 基于统计信息估算各算子代价，统计信息缺失或过期会导致：大表被 Broadcast Join、Join 顺序错误、并行度不足。对外部 Catalog 而言，StarRocks 无法像内部表一样自动感知数据变化，必须主动收集。

手动统计信息收集 ANALYZE
在外部 Catalog 上下文中执行
USE hive_catalog.sales;

-- 全表全量统计（小表适用）
ANALYZE TABLE orders;

-- 指定列（推荐：只分析查询频繁列）
ANALYZE TABLE orders (dt, cust_id, amount);

-- 采样统计（大表推荐，权衡精度与开销）
ANALYZE TABLE orders WITH SYNC MODE
  PROPERTIES("sample_ratio"="0.1");

-- 直方图（高基数列，提升 Join 过滤估算精度）
ANALYZE TABLE orders
  UPDATE HISTOGRAM ON amount, cust_id
  WITH 128 BUCKETS;

-- 查看统计状态
SHOW ANALYZE STATUS;

Parquet 低基数全局字典优化 (v3.5) NEW v3.5

StarRocks v3.5 支持在查询 Parquet 格式的 Hive/Iceberg 表时，自动为低基数列创建全局字典，将字符串比较转换为整数比较，显著加速 GROUP BY 和过滤操作。

// 05 Data Cache — 消灭远端 I/O 瓶颈
Data Cache 工作原理 CORE FEATURE

Data Cache 将远端存储（S3/HDFS/OSS）的文件以固定大小 Block 分片缓存到 BE/CN 节点的本地磁盘（NVMe/SSD）。v3.3.0 起默认开启，v3.4 起外部 Catalog 与云原生表共享统一 Cache 实例。

  • 热数据命中率高时，查询性能接近内部表，延迟降低 5-10x
  • 冷读路径：v3.3+ 支持并行 tablet 扫描 + 小 I/O 自动合并，减少冷读延迟
  • JDBC Catalog 不支持 Data Cache（直接 JDBC 连接无文件块概念）
BE 节点 Data Cache 配置 BE CONFIG
be.conf 配置（重启生效）
# 开启 DataCache（v3.3+ 默认 true）
datacache_enable = true

# 磁盘缓存路径（建议 NVMe SSD）
datacache_disk_path = /nvme0/datacache

# 磁盘缓存大小上限
datacache_disk_size = 2T

# 内存缓存（热点 Block 二级缓存）
datacache_mem_size = 10G

# Block 大小（默认 1MB，Parquet 列扫描
# 建议调大至 4MB 减少元数据开销）
datacache_block_size = 4194304
Session 级缓存控制 SESSION
查询时动态控制缓存行为
-- 开启扫描时读 DataCache（Session级）
SET enable_scan_datacache = true;

-- 开启扫描时填充 DataCache
SET enable_populate_datacache = true;

-- 绕过缓存（调试/全量扫描场景）
SET enable_scan_datacache = false;

-- 查看各 BE 节点 Cache 使用情况
SHOW BACKENDS\G
-- 关注 DataCacheMetrics 字段：
-- DiskUsed / DiskCapacity / MemUsed

-- 查询级 Cache 统计（Profile 中）：
-- DataCacheReadBytes   ← 命中量
-- DataCacheMissBytes   ← 未命中量
-- DataCacheHitRate = Read/(Read+Miss)
Data Cache 调优诊断树 RECIPE
  • 命中率 < 50%：磁盘容量不足 → 扩大 datacache_disk_size，或识别并淘汰冷数据分区
  • ScanTime 高但命中率 > 90%：Block 尺寸过小导致 IOPS 过高 → 调大 datacache_block_size 至 4-8MB
  • 冷启动后首次查询慢：预期行为，考虑用定时查询预热热分区数据
  • 持续高命中率 + 低延迟：缓存策略已最优，关注 Join 和聚合算子
// 06 Scan 算子优化 — 减少数据读取量
分区裁剪 (Partition Pruning) PUSHDOWN

外部 Catalog 分区裁剪依赖 FE 元数据和谓词形式。写法不当会导致全分区扫描。

✗ 错误写法 — 函数包裹导致无法下推
SELECT * FROM hive.sales.orders
WHERE DATE_FORMAT(dt, '%Y-%m') = '2024-01';
-- ✗ 函数包裹分区列 → 全分区扫描
-- ✗ LIKE '%...' → 无法使用 ZonemapIndex
✓ 正确写法 — 裸列比较保证下推
SELECT * FROM hive.sales.orders
WHERE dt >= '2024-01-01'
  AND dt <  '2024-02-01';
-- ✓ 裸列范围比较 → 精准分区裁剪
-- ✓ Parquet Row Group ZonemapIndex 生效
列裁剪与 Parquet 优化 COLUMN PRUNE

StarRocks 向量化引擎对 Parquet/ORC 做列式读取，只读取 SQL 引用的列。额外优化点：

  • SELECT 指定列，避免 SELECT *（宽表开销巨大）
  • Parquet Bloom Filter（v3.5+）：对高基数等值过滤列在 Parquet Writer 侧建立 Bloom Filter，StarRocks 可在文件级跳过不命中的 Row Group
  • ORC / Parquet 压缩格式：优先选 Zstd（压缩率 + 解压速度均衡）或 LZ4（低延迟场景）
  • 小文件合并：Iceberg/Hive 小文件过多会导致元数据爆炸，建议定期 COMPACTION
v3.5 Parquet Bloom Filter 查询加速
-- 确认 Bloom Filter 下推生效（Profile）：
-- BloomfilterFilterRows > 0 表示已过滤
EXPLAIN ANALYZE
SELECT * FROM iceberg.dw.events
WHERE user_id = 'U123456';

// 07 Join 优化 — 最高频的外部 Catalog 性能杀手
Join 类型与选择策略 HIGH IMPACT
Join 类型适用场景外部 Catalog 注意点
Broadcast Join小表 < 100MB（CBO 自动判断）统计信息准确时自动选择；统计缺失可能误选大表 Broadcast → 内存爆炸
Shuffle Join两表均较大，均匀分布网络传输开销大，需足够带宽；外部 Catalog 场景已有 I/O 压力，应先减少数据量
Bucket Shuffle Join内部表 + 外部表，内部表有 Hash 分布外部 Catalog 表无 bucket 概念，仅适用于内外表混合查询
Colocate Join纯内部表不适用于外部 Catalog
Join Hint 强制指定策略 HINT
当 CBO 因统计缺失选错 Join 类型时
-- 强制 Broadcast Join（右表确定是小表）
SELECT o.*, c.name
FROM hive.sales.orders o
JOIN [BROADCAST] hive.sales.customers c
  ON o.cust_id = c.id;

-- 强制 Shuffle Join（避免大表被 Broadcast）
SELECT a.*, b.*
FROM iceberg.dw.fact_orders a
JOIN [SHUFFLE] iceberg.dw.fact_returns b
  ON a.order_id = b.order_id;

-- SET 变量临时限制 Broadcast 阈值
SET broadcast_row_limit = 10000000;
-- 右表估算行数超此值时不选 Broadcast
Join Reorder 与 Runtime Filter OPTIMIZER

StarRocks CBO 自动进行 Join Reorder，但外部 Catalog 统计缺失时可能选错顺序。同时 Runtime Filter 可在 Probe 端提前过滤数据，减少扫描量。

Runtime Filter 优化控制
-- 开启 Runtime Filter（默认 true）
SET enable_runtime_filter = true;

-- Runtime Filter 等待超时（ms）
SET runtime_filter_wait_timeout_ms = 1000;

-- 开启 Global Runtime Filter（跨 Fragment）
SET enable_global_runtime_filter = true;

-- SETVAR Hint 针对单条查询
SELECT /*+ SET_VAR(
  enable_runtime_filter=true,
  broadcast_row_limit=5000000
) */ ...
FROM hive.sales.orders o
JOIN hive.sales.regions r ON o.region_id = r.id;

// 09 异步物化视图 — 数据湖查询加速王器
外部 Catalog 物化视图加速策略 RECOMMENDED

对于高频访问的外部 Catalog 报表查询，异步物化视图是最强力的加速手段：将计算结果持久化到 StarRocks 内部存储，查询时透明改写，完全绕开远端 I/O。

支持的外部 Catalog 类型：Hive、Iceberg、Hudi、Delta Lake、JDBC、Paimon

物化视图创建与刷新策略 MV
基于 Iceberg Catalog 创建物化视图
CREATE MATERIALIZED VIEW dw_daily_sales_mv
PARTITION BY (dt)
DISTRIBUTED BY HASH(region_id) BUCKETS 32
REFRESH ASYNC
EVERY(INTERVAL 1 HOUR)
PROPERTIES(
  "replication_num" = "1",
  "partition_refresh_number" = "3"  -- 每次刷新最近3个分区
)
AS
SELECT
  dt,
  region_id,
  product_category,
  SUM(amount)       AS total_sales,
  COUNT(DISTINCT order_id) AS order_cnt,
  approx_count_distinct(cust_id) AS uv
FROM iceberg_catalog.dw.fact_orders
WHERE status = 'COMPLETED'
GROUP BY dt, region_id, product_category;

-- 对 Hive Catalog 开启分区级感知刷新
ADMIN SET FRONTEND CONFIG (
  "enable_hive_partition_refresh" = "true"
);

-- 查看物化视图状态
SHOW MATERIALIZED VIEWS;
SELECT * FROM
  information_schema.task_runs
WHERE task_name = 'dw_daily_sales_mv';
查询透明改写 (Query Rewrite) REWRITE

物化视图创建后，StarRocks CBO 自动检测并改写符合条件的查询，无需修改业务 SQL。

验证改写是否生效
EXPLAIN
SELECT dt, region_id, SUM(amount)
FROM iceberg_catalog.dw.fact_orders
WHERE status = 'COMPLETED'
  AND dt >= '2024-01-01'
GROUP BY dt, region_id;

-- 计划中出现 OlapScanNode 且 table 为
-- dw_daily_sales_mv 则改写成功

-- 强制开启/关闭改写（调试用）
SET enable_materialized_view_rewrite = true;
Hive 分区感知刷新 HIVE

为 Hive Catalog 物化视图配置分区级感知，StarRocks 周期性检查 HMS 感知新增分区，只刷新变更分区，避免全量重算。

  • 设置 enable_hive_partition_refresh=true 开启感知
  • 物化视图分区键与 Hive 表分区键对齐（如 dt）
  • 配合 partition_refresh_number 控制每批刷新分区数，避免 FE 压力
  • HMS 性能较差时，调大 background_refresh_metadata_interval_millis
// 10 Query Feedback — 自适应计划修正 (v3.4+)
Query Feedback 工作原理 v3.4+

Query Feedback 是 CBO 的自我修正框架：记录查询实际执行统计（真实行数、真实 NDV），当 CBO 估算与实际偏差超阈值时，生成 Tuning Guide 并在后续相似查询中自动修正执行计划。

典型修正场景：大表被误判为小表广播、Join 顺序因统计偏差选错、分区裁剪估算不准。

查看当前 FE 的 Tuning Guides
SHOW QUERY FEEDBACK;

-- 输出示例：
-- 1: LeftChildEstimationErrorTuningGuide
-- Reason: left child of JoinNode overestimated
-- Advice: Adjust distribution join type

-- EXPLAIN 时看到 "Plan had been tuned by Plan Advisor"
-- 即表示 Feedback 已介入修正
EXPLAIN
SELECT COUNT(*) FROM
  hive.sales.large_orders t1
  JOIN hive.sales.small_ref t2 ON t1.id = t2.id;

按优先级排序的调优行动清单 ACTION LIST
  • [P0] 收集 CBO 统计信息 — ANALYZE TABLE 外部表，v3.4+ 开启自动收集，这是一切优化的前提
  • [P0] 确认 Data Cache 已启用 — 检查 BE datacache_enable=true，Session enable_scan_datacache=true
  • [P1] 开启 Query Profile 分析瓶颈 — 找到最热的 Operator（Scan/Join/Agg）再对症下药
  • [P1] 检查谓词下推是否生效 — Profile 中 PushdownPredicates=0 且过滤行数高则必须改写 SQL
  • [P1] 元数据缓存刷新配置 — 避免每次查询都冷读 HMS/Glue，配置后台刷新间隔
  • [P2] 高频报表创建异步物化视图 — 绕开远端 I/O，查询性能提升 10x+
  • [P2] Join 类型验证 — EXPLAIN 确认 CBO 选择正确，必要时使用 Hint 强制
  • [P2] 启用 Query Feedback（v3.4+） — 让系统自动纠正统计偏差导致的次优计划
  • [P3] 小文件合并与分区设计 — Iceberg COMPACTION，Hive 分区粒度与查询模式对齐
  • [P3] 资源组隔离 — 大查询与高并发短查询分离，避免资源争抢
