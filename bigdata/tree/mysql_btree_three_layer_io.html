InnoDB B+ Tree 索引原理 生产实战

MySQL B+ 树：三层 I/O 覆盖千万数据

InnoDB 16 KB 页、约 1600 扇出，3 层树高可覆盖约 4000 万条记录——这个数字是怎么算出来的？

① 从"为什么"出发：磁盘 I/O 才是瓶颈

数据库查询的终极成本不是 CPU，而是磁盘 I/O 次数。每次读取磁盘页（InnoDB 默认 16 KB）都需要约 5–10 ms，而内存访问只需 100 ns，相差 5 万倍。因此，索引结构的核心目标是：用最少的 I/O 次数，找到目标数据。

B+ 树的设计思路就是把"每次 I/O 能消除多少候选项"最大化——这个能力叫做扇出（Fan-out）。

② 三层 B+ 树全景图

下图展示一棵三层 B+ 树的物理结构。层 1 是根节点（常驻内存），层 2 是中间索引节点，层 3 是叶子节点（存放实际数据行或主键回表指针）。

核心结论：B+ 树的非叶子节点只存 Key + 指针，叶子节点才存完整数据行（聚簇索引）或主键（二级索引）。这让中间层可以塞入尽可能多的指针，最大化扇出。叶子节点之间通过双向链表相连，天然支持范围查询而无需回溯树干。
实战口诀
上层导航、下层存货，叶子串成链、范围不回头。

③ 扇出计算：1600 这个数是怎么来的

这是整篇的核心数学。我们来逐步拆解。

内节点（非叶子节点）的页结构

一个 16 KB 的内节点页由三部分组成：固定页头、若干个 [Key, ChildPointer] 键值对，以及一个末尾指针。

扇出精确计算步骤

// 步骤1：一个 16 KB 页的可用空间 16384 B (16 KB) − 38 B (File Header) − 56 B (Page Header) − 26 B (Page Directory + Trailer) = 16264 B 可用于存储键值对 // 步骤2：单个索引键值对大小（以 INT 主键为例） Key : 4 B (INT) Ptr : 6 B (Page Number, 4B) + 2B (pointer metadata) = 约 10~14 B / entry // 步骤3：扇出（每页指针数） fan_out = 16264 ÷ 10 ≈ 1626 （乐观） fan_out = 16264 ÷ 14 ≈ 1162 （保守） 常用估算值：约 1200 ~ 1600，官方文档取 ~1200

④ 三层覆盖量：指数爆炸的威力

有了扇出系数，三层覆盖量就是简单的乘方。关键在于理解：每一层都是对上一层的指数级放大，就像二叉树的 2ⁿ，只不过这里底数是 1600。

树层 节点数量 计算公式 I/O 次数 说明
层 1（根） 1 个页 1 0（常驻内存） Buffer Pool 热点，几乎不读盘
层 2（中间） ~1,600 个页 1 × 1600 1 次 I/O 读取对应中间节点页
层 3（叶子） ~256 万个页 1600 × 1600 1 次 I/O 读取对应叶子页，获得数据
总计覆盖 256万页 × ~16条 仅 2 次磁盘 I/O 根节点已缓存，实际仅需 2 次！
核心结论：
  1. 覆盖量 = 扇出^(树高-1) × 叶子页行数。以扇出 1600、树高 3 计算：1600² × 16 ≈ 4000 万条。
  2. 根节点几乎永远在 Buffer Pool 中，所以实际磁盘 I/O 只有 2 次（中间层 1 次 + 叶子层 1 次）。
  3. 叶子页每页约存 16 条数据行（以 1 KB/行为例：16384 ÷ 1024 ≈ 16；行越小，每页越多）。
实战口诀
扇出 1600 是底数，树高 3 是指数，叶子行数是系数；
根在内存不算盘，每查一次最多 2 I/O 就能见。

⑥ 生产实战：配置与诊断

关键配置参数

-- 查看当前页大小 SHOW VARIABLES LIKE 'innodb_page_size'; -- 查看 Buffer Pool 大小（根节点缓存） SHOW VARIABLES LIKE 'innodb_buffer_pool_size'; -- 推荐：Buffer Pool 设为物理内存 70~80% innodb_buffer_pool_size = 12G -- 16G 内存机器

估算表的树高

-- 查看表的页数（间接推算树高） SELECT TABLE_NAME, DATA_LENGTH / 16384 AS page_count, TABLE_ROWS FROM information_schema.TABLES WHERE TABLE_SCHEMA = 'your_db'; -- 树高估算：log_{扇出}(page_count) -- page_count=1600 → 高度≈2 -- page_count=256万 → 高度≈3（千万级）

常见错误配置 vs 正确写法

-- ❌ 错误：用 UUID 做主键（36B 字符串） CREATE TABLE orders ( id VARCHAR(36) PRIMARY KEY DEFAULT (UUID()), -- 过长，扇出骤降 ... ); -- ✅ 正确：INT / BIGINT 自增主键（4/8B） CREATE TABLE orders ( id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY, biz_uuid VARCHAR(36) NOT NULL, -- 业务 UUID 单独存，不当主键 INDEX idx_biz_uuid (biz_uuid), ... ); -- ❌ 错误：联合索引字段顺序错误（选择性低的字段放前面） INDEX idx_wrong (status, user_id); -- status 只有 3 个值，扇出极差 -- ✅ 正确：高选择性字段放前面 INDEX idx_right (user_id, status); -- user_id 选择性高，先过滤
完整推导公式
扇出 f ≈ (16384 − 页头) ÷ (Key_size + Ptr_size)
叶子页数 L = f^(h−1)　　　（h 为树高）
总行数 N = L × rows_per_leaf
代入 f=1600, h=3, rows≈16：N = 1600² × 16 ≈ 4096万
