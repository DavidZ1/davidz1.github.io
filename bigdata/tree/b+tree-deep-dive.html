B+ 树深度解析

从节点设计到生产调优，全面拆解数据库索引背后最核心的数据结构

01
概念定义
核心定义
B+ 树（B+ Tree）是一种自平衡的多路搜索树，所有实际数据记录只存储在叶子节点（Leaf Node），内部节点仅保存用于导航的键（Key），且所有叶子节点通过双向链表串联，形成一个有序序列。

在数据库体系中，B+ 树是存储引擎的核心索引结构。MySQL InnoDB、PostgreSQL、SQLite 等几乎所有主流关系型数据库都以 B+ 树作为主索引（Primary Index）与辅助索引（Secondary Index）的底层实现。它直接决定了数据库在磁盘 I/O 层面的读写效率。

直观类比
把 B+ 树想象成一本图书馆的多级目录系统：封面是"大类目录"（根节点），里面的章节目录是"中间层目录"（内部节点），而最终每一本书（数据行）整齐排列在书架最底层（叶子节点）。翻书目录只是为了快速定位，不是为了"阅读"——书的内容只在书架上。叶子节点之间的链表，就像书架上的书按编号顺序相邻摆放，让你可以从某本书开始顺序扫描而无需回到目录。

3.2 阶（Order）与高度（Height）

阶数 m 是 B+ 树最关键的参数，决定了每个节点能容纳的最大键数（m-1 个）和子指针数（m 个）。阶数越大，树越"矮胖"，磁盘 I/O 次数越少。

高度公式
对于 N 条记录、阶数为 m 的 B+ 树，树高约为 h ≈ log_m(N)。InnoDB 默认页大小 16 KB，阶数可达 1000+，意味着存储 10 亿条数据只需约 3 层 I/O。

3.3 叶节点链表（Leaf Linked List）

叶子节点之间通过双向链表串联，构成一个有序序列。这是 B+ 树区别于 B 树最核心的设计，赋予了 B+ 树天然支持范围查询（Range Query）和顺序扫描（Full Scan）的能力，无需回到根节点重新遍历。

-- SQL 范围查询示例：直接在叶链表上顺序扫描
SELECT * FROM orders
WHERE order_id BETWEEN 1000 AND 2000;
-- B+ 树执行路径：
-- 1. 从根向下找到 order_id=1000 所在叶节点（log m(N) 次 I/O）
-- 2. 沿叶节点链表顺序右移，直到 order_id > 2000（顺序 I/O）
-- B 树不能这么做：需要回溯到父节点再重新向下
04
工作原理 / 执行流程图

B+ 树的三大核心操作是查找（Search）、插入（Insert）与删除（Delete），插入和删除在保证有序性的同时，通过节点分裂（Split）与节点合并（Merge）维持树的平衡。

节点分裂（Node Split）示例代码

def split_leaf_node(leaf, new_key, new_val, parent):
    # leaf 已满（n == m-1），需要分裂
    mid = len(leaf.keys) // 2

    # 创建右兄弟节点
    right = LeafNode()
    right.keys  = leaf.keys[mid:]     # 右半部分 key
    right.vals  = leaf.vals[mid:]     # 对应数据指针
    right.next  = leaf.next           # 接管右链表指针
    right.prev  = leaf                # 回指左节点

    # 截断原节点
    leaf.keys   = leaf.keys[:mid]
    leaf.vals   = leaf.vals[:mid]
    leaf.next   = right               # 前进指针指向右兄弟

    # 上推分裂点 Key（B+ 树：叶节点第一个 key 上推，副本留下）
    push_up_key = right.keys[0]
    parent.insert_key(push_up_key, right)  # 递归，父满则继续分裂

06
与其他概念的关联关系

在数据库体系中，B+ 树并非独立存在，它与多个核心概念紧密协作：

🗄️
聚簇索引（Clustered Index） InnoDB 的主键索引直接将完整行数据存储在 B+ 树叶节点中，数据物理顺序与索引逻辑顺序一致，避免回表（Back-to-table Lookup）。
🔗
辅助索引（Secondary Index） 非主键字段的 B+ 树叶节点存储的是主键值而非行数据，查询时需二次回表到主键 B+ 树（称为"回表"）。
📄
页（Page）与缓冲池（Buffer Pool） B+ 树每个节点对应磁盘上的一个数据页（InnoDB 默认 16 KB），Buffer Pool 以 LRU 策略缓存热点页，减少磁盘 I/O。
🔒
间隙锁（Gap Lock） 基于 B+ 树叶节点链表实现，锁住相邻叶节点间的"间隙"，防止幻读（Phantom Read），是 MVCC 机制的重要支撑。 
-- 组合使用示例：覆盖索引（Covering Index）消除回表
-- 场景：频繁查询 user_id, name, age 三个字段

-- 建立组合索引（name, age 冗余进辅助索引叶节点）
CREATE INDEX idx_user_cover ON users(user_id, name, age);

-- 此查询完全命中辅助 B+ 树叶节点，无需回表
SELECT user_id, name, age
FROM   users
WHERE  user_id BETWEEN 1001 AND 2000;

-- EXPLAIN 输出中 Extra = "Using index"，代表走了覆盖索引

进阶特性与底层原理

7.1 页内二分查找（Binary Search in Page）

每个内部节点的 Key 数组是有序的，在节点内部使用二分查找定位下一层子指针。因此一次节点访问（1 次 I/O）内部的搜索复杂度为 O(log m)，总体查找为 O(log m × log_m N) = O(log N)。

7.3 为什么内部节点不存数据——扇出的意义

以 InnoDB 16 KB 页为例：若每条记录大小约 1 KB，则叶节点约存 16 条记录；而内部节点每个键只需约 10 字节（bigint 主键 8 B + 指针 6 B），单页可容纳约 1600 个子指针。这意味着：

扇出计算
树高 2 层（不含叶节点）：1600 × 1600 = 256 万个叶节点，每叶节点约 16 条记录 → 约 4000 万条记录，只需 3 次磁盘 I/O（根 + 内部 + 叶）。这是 B+ 树在数据库场景秒杀红黑树的根本原因：红黑树树高约 30，需要 30 次 I/O。
08
生产实践 / 调优指南
常见问题 根因分析 解决方案
索引失效（全表扫描） 对索引列使用函数或隐式类型转换 避免 WHERE YEAR(create_time)=2024，改用范围条件
索引选择性低 列基数（Cardinality）太低，如布尔字段 不建单列索引，考虑组合索引放高选择性列在前
回表开销大 辅助索引查询后需二次回聚簇索引 使用覆盖索引，将 SELECT 列加入索引定义
页分裂频繁 使用随机主键（UUID）导致写入离散 改用自增主键或有序 UUID（UUIDv7），减少页分裂
索引碎片化 大量删除操作导致叶节点稀疏 定期执行 OPTIMIZE TABLE 或 ALTER TABLE ... FORCE
最左前缀失效 组合索引 (a, b, c) 中跳过了 a 或 b 遵循最左前缀原则，调整查询或索引列顺序

🔧 最佳实践

  1. 主键选自增整数：避免 UUID 随机写入引发的页分裂，每次插入均在链表末尾追加，I/O 最优。
  2. 组合索引遵循最左前缀：索引 (a, b, c) 可满足 WHERE a=?、WHERE a=? AND b=?，但 WHERE b=? 无法走索引。
  3. 优先考虑覆盖索引：高频查询的 SELECT 列纳入索引，消除回表，尤其对 OLAP 场景显著提升性能。
  4. 控制索引数量：每张表索引不超过 5 个，过多索引会拖慢写入（每次写操作需更新所有 B+ 树索引）。
  5. 定期分析索引使用情况：通过 sys.schema_unused_indexes（MySQL 8.0+）或 pg_stat_user_indexes（PostgreSQL）删除无用索引。
-- MySQL 8.0+ 查看索引使用情况
SELECT object_schema, object_name, index_name
FROM   performance_schema.table_io_waits_summary_by_index_usage
WHERE  count_star = 0
  AND  index_name IS NOT NULL
ORDER BY object_schema, object_name;   -- 找出从未被访问的索引

-- 分析查询是否命中索引
EXPLAIN FORMAT=JSON
SELECT * FROM orders WHERE user_id=1001 AND status='paid';
-- 关注 key_name（实际走的索引）和 rows（估算扫描行数）

🧠 核心记忆要点（8 条）

1️⃣
数据只在叶节点内部节点纯粹是"路由器"，不存实际数据，使得单页可容纳极多子指针（高扇出）。
2️⃣
叶节点链表 = 范围查询神器有序双向链表让区间扫描无需回溯，O(log N + k) 解决任意范围查询。
3️⃣
三层 I/O 覆盖千万数据InnoDB 16 KB 页、约 1600 扇出，3 层树高可覆盖约 4000 万条记录。
4️⃣
插入分裂向上传播节点满则分裂，中间 Key 上推父节点，父满则递归，直至根节点分裂（树增高）。
5️⃣
删除合并向上传播节点下溢先尝试向兄弟节点借 Key（旋转），借不了则合并，合并也会递归向上。
6️⃣
自增主键是最优写入策略顺序插入永远在链表末尾追加，避免随机写入导致的频繁页分裂与碎片化。
7️⃣
覆盖索引消灭回表将查询所需列全部纳入辅助索引，查询只需访问辅助 B+ 树，无需二次查聚簇索引。
8️⃣
所有写操作均有代价每次 INSERT / UPDATE / DELETE 都要同步维护所有 B+ 树索引，索引越多写入越慢。
