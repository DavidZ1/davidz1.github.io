Section 01

设计背景：为什么磁盘逼出了 B 树

在理解 B 树之前，先思考一个问题：二叉搜索树（BST）哪里出了问题？

BST 在内存中表现优秀，时间复杂度 O(log n)。但当数据量超过 RAM 容量，数据必须存在磁盘上时，一切都变了。

核心认知

磁盘 I/O 不是按字节读取，而是按页（Page）读取，通常 4KB 或 16KB。访问磁盘的延迟是访问内存的 10 万倍。BST 每次比较访问一个节点，一棵百万节点的 BST 最坏需要 20 次磁盘 I/O——这是灾难性的。

类比：想象你在图书馆查书。BST 的方式是：每次只能拿出一本书看一个字，放回去，再找下一本。而 B 树的方式是：每次拿出一整箱书（一个磁盘页），在箱子里找——I/O 次数从几十次降到 3~4 次。

B 树由 Rudolf Bayer 和 Ed McCreight 在 1972 年提出，核心思想只有一句话：

让每个节点尽可能"胖"，使树尽可能"矮"，从而最小化磁盘 I/O 次数
图 1-1 · BST vs B 树：树高与 I/O 次数的根本差异
实战口诀

B 树是为磁盘而生的数据结构。树越矮，I/O 越少，性能越好。每增加一层树高，I/O 成本翻数百倍。

Section 02

整体架构：B 树的全景图

B 树（Balance Tree）是一种自平衡的多路搜索树。在深入细节前，先建立整体认知：B 树的每个节点就是一个磁盘页，每个节点可以存储多个键和多个子指针。

一棵阶为 t（最小度数）的 B 树满足以下性质：

性质 描述
键数约束 每个非根节点最少 t-1 个键，最多 2t-1 个键
子节点约束 每个内部节点最少 t 个子节点，最多 2t 个子节点
有序性 节点内键有序，子树键范围由父节点键划分
平衡性 所有叶子节点在同一深度（自平衡）
树高上界 高度 h ≤ logt( (n+1)/2 )，n 为总键数
图 2-1 · B 树整体架构全景（阶 t=3，3层树可索引数百万条记录）

上图展示了一棵 最小度数 t=3 的 B 树。观察几个关键特征：紫色根节点、青色内部节点、绿色叶子节点分别对应控制流、普通路径、数据存储三个语义层次。所有叶子节点都在同一深度——这是 B 树自平衡的核心保证。

核心结论

① B 树的高度是有严格上界的：h ≤ log_t(n)，t 越大，树越矮。② 每次磁盘 I/O 读取一个节点，因此查找一个键最多需要 h+1 次 I/O。③ InnoDB 默认页大小 16KB，t 约为数百，三层 B+ 树可索引数千万行——这就是为什么说"InnoDB 索引高度通常不超过 3"。

Section 03

核心机制一：节点结构与阶

每个 B 树节点对应磁盘上的一个页（Page）。理解节点的内部结构，是理解所有后续操作的前提。

一个包含 k 个键的内部节点，有 k+1 个子指针。键和指针交替排列：

[ P₀ | K₁ | P₁ | K₂ | P₂ | ... | Kₖ | Pₖ ]

其中 P_i 指向的子树，所有键均满足：K_i < 子树中所有键 < K_{i+1}。这就是 BST 的有序性在多路情况下的推广。

图 3-1 · B 树节点内存布局：键与子指针交替，每 k 个键对应 k+1 个指针

「阶」与「最小度数」的命名混乱

B 树有两种常见的参数定义方式，工程师经常被混淆：

参数 定义方式 最大键数 最小键数（非根） 常见场景
阶 m（Order） 最大子节点数 m-1 ⌈m/2⌉ - 1 教材（Knuth）
最小度数 t 最小子节点数 2t-1 t-1 CLRS 算法导论

两者的换算关系：m = 2t（当 t 为整数时）。MySQL InnoDB 的"页大小"本质上决定了每个节点能容纳多少键——16KB 页面可以放数百个整数键，这使得 B+ 树的阶高达几百。

实战口诀

看到 Order/阶 就是最大孩子数；看到 degree/t 就是最小孩子数。换算：order = 2 × degree。记住这一个等式，永远不会搞混。

Section 04

核心机制二：查找路径

B 树的查找类比"在图书馆的楼层索引牌中找书"：每一层都有范围指示牌，根据区间走对应通道，一直到书架（叶子节点）取出书。

算法步骤：从根开始，在当前节点内二分查找目标键 k，若找到则返回；否则根据键范围选择对应子指针，加载下一节点（一次磁盘 I/O），递归。

图 4-1 · B 树查找 key=47 的完整路径（绿色高亮路径，灰色为排除路径）
核心结论

① 查找的 I/O 次数恰好等于树的高度 h，与节点内部键的数量无关（节点内二分查找在内存中完成，极快）。② 灰色的"排除路径"是 B 树效率的来源：每次比较一个节点的多个键，一口气排除掉多个子树。③ 找不到的查找（Range Miss）和找到的代价完全相同，都是 h 次 I/O。

实战口诀

B 树查找 = 楼层导引牌 + 最后一层找书架。每层一次 I/O，树高决定查找代价，而树高由数据量和节点容量共同决定。

Section 05

核心机制三：插入与节点分裂

插入是 B 树最复杂的操作，因为它可能破坏节点的键数约束（超过 2t-1 个键），需要通过"节点分裂"来恢复平衡。

类比：你在一个书柜（节点）里放书，柜子满了，就把书柜从中间劈开，各自放半边书，并把中间那本书的书名牌推给上层管理员——这本书就"升级"到父节点了。

插入步骤：先查找插入位置，如果目标叶子节点已满（键数 = 2t-1），则执行分裂，分裂会将中间键提升到父节点，然后递归判断父节点是否也需要分裂。

图 5-1 · B 树节点分裂过程：中间键 30 上浮到父节点，节点一分为二
核心结论

① 分裂的"中间键"是第 t 个键（1-indexed），它被"提升"而非复制到父节点——这与 B+ 树不同。② 分裂自下向上传播，最坏情况下根节点分裂，这是 B 树唯一增加高度的方式，所以它保持完美平衡。③ 为了避免回溯，可以在查找路径上预先分裂满节点（自顶向下的变体），代价是多一些不必要的分裂。

Section 06

核心机制四：删除与合并/借键

删除比插入更复杂，因为要处理三种情况：键在叶子节点、键在内部节点、以及删除后节点键数不足（下溢）的修复。

图 6-1 · B 树删除的三种情形：直接删除 / 向兄弟借键 / 节点合并
注意

删除内部节点的键时，需要用前驱键（左子树最大值）或后继键（右子树最小值）替换，然后转化为删除叶子节点的问题——这是一个递归问题。实际数据库引擎（如 InnoDB）对删除有惰性策略，标记为"已删除"后批量合并，而非立即重组。

实战口诀

删除三步走：够就删，不够就借，借不到就合并。合并一定会让父节点少一个键，所以可能向上连锁。

Section 07

B 树 vs B+ 树：新老对比

现实中，数据库几乎不用原始 B 树，而是用 B+ 树。两者的本质区别只有一点：B+ 树的数据只存在叶子节点，内部节点只存索引键。

图 7-1 · B 树 vs B+ 树：数据存储位置与叶子链表是核心差异
特性 B 树 B+ 树 胜者
数据位置 所有节点都存数据 仅叶子节点存数据 B+ 树 内部节点更紧凑
点查询 O(log n)，可能提前结束 O(log n)，必须到叶子 持平 实际差异忽略不计
范围查询 O(k · log n)，需回溯 O(log n + k)，链表扫描 B+ 树 数量级优势
全表扫描 需遍历整棵树 遍历叶子链表 O(n) B+ 树 性能极优
内部节点容量 较小（含数据指针） 较大（仅含键） B+ 树 树高更低
使用场景 文件系统（HFS+） 数据库索引（MySQL/PG） —
核心结论

B+ 树赢在范围查询。数据库 90% 的查询是范围查询（WHERE age BETWEEN 20 AND 30，ORDER BY，GROUP BY），而 B+ 树的叶子链表让范围查询降到 O(log n + k)。这就是为什么 MySQL InnoDB、PostgreSQL、SQLite 都选择 B+ 树而非 B 树。

Section 08

生产实战：MySQL InnoDB 索引配置与排障

理论落地到实际：MySQL InnoDB 使用 B+ 树实现所有索引（包括主键和二级索引）。理解 B 树原理，才能看懂 InnoDB 的行为和调优参数。

关键配置参数

参数 默认值 B 树意义 调优建议
innodb_page_size 16384 (16KB) 每个 B+ 树节点的大小 NVMe SSD 可考虑 32KB/64KB
innodb_buffer_pool_size 128MB 缓存热点 B+ 树节点（页） 通常设为可用内存的 70-80%
innodb_fill_factor 100 页填充率（留空间减少分裂） 写入密集场景设 80，减少分裂
key_block_size 0 (默认) 压缩后每块大小（B+ 节点） 压缩表用 8，减少 I/O

完整生产级代码示例

SQL · MySQL InnoDB B+ 树索引实战
-- ============================================================
-- B+ 树索引实战：电商订单表
-- 演示: 索引设计、覆盖索引、范围查询、避免索引失效
-- ============================================================

-- 1. 建表：主键 = 聚簇索引（B+ 树，叶子存完整行）
CREATE TABLE orders (
  id          BIGINT       NOT NULL AUTO_INCREMENT,
  user_id     BIGINT       NOT NULL,
  status      TINYINT      NOT NULL DEFAULT 0,  -- 0=待付款 1=已付款 2=已发货
  amount      DECIMAL(12,2) NOT NULL,
  created_at  DATETIME     NOT NULL,
  updated_at  DATETIME     NOT NULL,
  
  PRIMARY KEY (id),                          -- 聚簇索引：叶子存完整行数据
  
  -- 二级索引（叶子存 primary key，查询需"回表"）
  INDEX idx_user_status_time (user_id, status, created_at)
  --  ↑ 联合索引：B+ 树先按 user_id 排，再按 status，再按 created_at
  --  符合"最左前缀"原则，满足以下查询无需回表：
  --  WHERE user_id=?
  --  WHERE user_id=? AND status=?
  --  WHERE user_id=? AND status=? AND created_at BETWEEN ? AND ?
) ENGINE=InnoDB
  innodb_fill_factor=80    -- 每页只填 80%，给插入留余量，减少页分裂频率
  ROW_FORMAT=DYNAMIC       -- 支持大字段外存（off-page），不影响索引节点大小
  CHARSET=utf8mb4;

-- ============================================================
-- 2. 范围查询利用 B+ 叶子链表扫描
-- ============================================================
-- ✓ 正确：命中 (user_id, status, created_at) 联合索引，利用叶子链表
SELECT id, amount
FROM   orders
WHERE  user_id  = 10086
  AND  status   = 1
  AND  created_at BETWEEN '2024-01-01' AND '2024-12-31'
ORDER BY created_at;  -- created_at 已在索引中有序，无需额外排序

-- ✗ 错误：函数破坏 B+ 树有序性，导致全索引扫描
-- SELECT * FROM orders WHERE YEAR(created_at) = 2024;
-- ↑ 对 created_at 套了 YEAR()，索引从 B+ 树点查退化为全扫

-- ============================================================
-- 3. 覆盖索引：避免"回表"（B+ 二级索引→主键→聚簇索引）
-- ============================================================
-- 回表场景：二级索引叶子只有 id，还要再走一次聚簇索引取 amount
EXPLAIN SELECT id, user_id, status, amount  -- amount 不在联合索引中 → 回表
FROM orders WHERE user_id = 10086;
-- Extra: NULL （未覆盖，需回表）

-- ✓ 覆盖索引：所有查询列均在索引叶子中，无需回表
EXPLAIN SELECT id, user_id, status, created_at  -- 均在索引中
FROM orders WHERE user_id = 10086;
-- Extra: Using index （覆盖索引，只走一次 B+ 树）

-- ============================================================
-- 4. 排障：观察 B+ 树分裂频率（页分裂过多 → 写入性能下降）
-- ============================================================
SELECT
  INDEX_NAME,
  ROUND(STAT_VALUE * @@innodb_page_size / 1024 / 1024, 2) AS size_mb,
  STAT_VALUE AS num_pages
FROM   mysql.innodb_index_stats
WHERE  database_name = 'your_db'
  AND  table_name    = 'orders'
  AND  stat_name     = 'n_leaf_pages';
-- 若叶子页数量异常多（相对数据量），说明分裂后存在大量空洞
-- 解决：OPTIMIZE TABLE orders; （重建 B+ 树，消除碎片）

-- ============================================================
-- 5. 强制使用/不使用某个 B+ 树索引（调试用）
-- ============================================================
SELECT * FROM orders
  USE INDEX (idx_user_status_time)   -- 强制走此索引
WHERE user_id = 10086;

SELECT * FROM orders
  IGNORE INDEX (idx_user_status_time)  -- 忽略此索引
WHERE user_id = 10086;

常见错误配置 vs 正确写法

SQL · 反模式对比
-- ❌ 错误 1：NOT IN / != 导致 B+ 树无法使用范围扫描
SELECT * FROM orders WHERE status != 0;
-- B+ 树不知道"不等于"对应哪段连续区间，退化为全扫

-- ✓ 正确：改为 IN 或多个 = 条件，让优化器选择 B+ 树叶子扫描
SELECT * FROM orders WHERE status IN (1, 2);

-- ❌ 错误 2：隐式类型转换破坏 B+ 树有序性
SELECT * FROM orders WHERE user_id = '10086';
-- user_id 是 BIGINT，字符串'10086'触发隐式转换 → 索引失效

-- ✓ 正确：类型严格匹配
SELECT * FROM orders WHERE user_id = 10086;

-- ❌ 错误 3：违背最左前缀，跳过中间列
SELECT * FROM orders
WHERE user_id = 10086
  AND created_at = '2024-06-01';
-- 跳过了 status，B+ 树只能用到 user_id 部分，created_at 无法走索引

-- ✓ 正确：要么加上 status，要么建新索引 (user_id, created_at)
SELECT * FROM orders
WHERE user_id = 10086
  AND status   = 1
  AND created_at = '2024-06-01';

-- ❌ 错误 4：对索引列做运算
SELECT * FROM orders WHERE id + 1 = 100;  -- 全表扫描！

-- ✓ 正确：把运算移到右边
SELECT * FROM orders WHERE id = 99;

最终核心结论

B 树（B+ 树）的所有工程决策都源自同一个哲学：最小化磁盘 I/O 次数。理解了这个原点，你就理解了为什么要选择性高的列放索引（减少扫描节点数），为什么最左前缀失效（B+ 树按列顺序排序，跳过中间列就无法二分），为什么 fill_factor 影响写入性能（留余量减少分裂），为什么覆盖索引快（少一次 B+ 树遍历）。
