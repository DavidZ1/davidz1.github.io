01 / Columnar Storage Internals

列式存储：为什么 OLAP 必须用列存

行存与列存的本质差异不是"哪行数据挨在一起"，而是 IO 模式与压缩率。理解这个差异，才能理解为什么 Parquet 在分析场景比 CSV/JSON 快 10~100 倍。

行式存储（CSV / JSON / Row Parquet）
OLTP 友好
Row 1
user_id: 1001 city: 北京 age: 28 amount: 299.0
Row 2
user_id: 1002 city: 上海 age: 35 amount: 580.5
Row 3
user_id: 1003 city: 北京 age: 22 amount: 120.0
查询 SUM(amount) 需要读取每行的全部字段，即使只需 amount 列。对百列宽表而言，读取 IO 是实际需求的 100 倍。
优势：整行读取快，适合按主键查询、频繁更新的 OLTP 场景。
列式存储（Parquet / ORC）
OLAP 最优
city 列
北京 上海 北京 广州 北京
age 列
28 35 22 41 28
amount 列
299 580 120 999 450
查询 SUM(amount) 只需读取 amount 列，IO 减少 75%（4列只读1列）。同类型数据相邻，压缩率提升 5~20 倍。
额外收益：列级别统计（min/max）支持谓词下推，跳过不满足条件的 Row Group。

Parquet 文件物理结构：Row Group → Column Chunk → Page

📄 part-00000-xxxx.parquet 文件大小推荐：128MB ~ 512MB
Row Group 0（0~128MB）
user_id 列块DELTA_BINARY
city 列块DICT+RLE
age 列块DELTA
amount 列块PLAIN+SNAPPY
Row Group 1（128~256MB）
user_id 列块DELTA_BINARY
city 列块DICT+RLE
age 列块DELTA
amount 列块PLAIN+SNAPPY
Row Group 2（256~384MB）
user_id 列块DELTA_BINARY
city 列块DICT+RLE
age 列块DELTA
amount 列块PLAIN+SNAPPY
Row Group 行数：约 100万行 每列块含 Page（8KB~1MB） 文件尾：Footer（Schema + 列统计） 谓词下推粒度：Row Group 级别
📐
Row Group Size 与 Spark Task 的关系
Spark 读取 Parquet 时，默认以 spark.sql.files.maxPartitionBytes（默认 128MB）为粒度切分 Task。Row Group 不可跨 Task 拆分——因此 Row Group 大小最好与 maxPartitionBytes 对齐，避免单个 Task 处理多个小 Row Group（增加 Footer 读取开销）或一个 Row Group 被截断（浪费 IO）。
写出时用 parquet.block.size（默认 128MB）控制 Row Group 大小。
02 / Encoding & Compression

列编码机制：压缩率背后的算法

Parquet 在压缩算法（Snappy/Zstd/Gzip）之前，先进行编码——编码利用数据特征消除冗余，压缩再进一步减小体积。两者叠加才是列存的真实压缩率。

字典编码（Dictionary Encoding）
低基数列首选
原始值
北京上海北京北京广州
字典页
0→北京1→上海2→广州
数据页
01002
字符串 "北京"（6字节）→ 整数 0（1字节），压缩率 6x。 当 distinct 值超过字典阈值（默认 1MB），自动 fallback 到 PLAIN 编码。 适用场景：城市、状态码、类别标签等低基数字段。
游程编码（RLE / Bit-Packing）
重复值 / 布尔列
原始值
truetruetruefalsefalse
RLE 编码
3×true2×false
Delta 编码
base:100+1+1+2-1
RLE 将连续重复值压缩为 (次数, 值)，对全为 null 的稀疏列效果极佳。 Delta 编码存储相邻值的差（适合时间戳、单调递增 ID），结合 Bit-Packing 进一步压缩小差值。

# ── Parquet 写出最佳配置 ──────────────────────────────
df.write \
  .option("compression", "zstd") \          # zstd: 比 snappy 压缩率高40%，解压速度相当
  .option("parquet.block.size", str(256 * 1024 * 1024)) \  # Row Group 256MB
  .option("parquet.page.size", str(1 * 1024 * 1024)) \     # Page 1MB（默认 1MB）
  .option("parquet.enable.dictionary", "true") \             # 启用字典编码
  .option("parquet.dictionary.page.size", str(2 * 1024 * 1024)) \  # 字典页最大 2MB
  .option("parquet.writer.version", "v2") \                # v2 支持更多编码类型
  .mode("overwrite") \
  .parquet("hdfs://data/output")

# ── 读取优化：跳过不必要的 Row Group ─────────────────
spark.conf.set("spark.sql.parquet.filterPushdown", "true")       # 谓词下推（默认开）
spark.conf.set("spark.sql.parquet.recordLevelFilter.enabled", "true")  # 行级过滤
spark.conf.set("spark.sql.parquet.bloomFilter.enabled", "true")       # 布隆过滤器（高基数点查）

# ── 压缩算法选型建议 ─────────────────────────────────
# SNAPPY  → 解压最快，压缩率中等，适合热数据（频繁读取）
# ZSTD    → 压缩率高30~50%，解压速度与 snappy 相近，推荐生产默认
# GZIP    → 压缩率最高，但 CPU 消耗大，适合冷存档
# LZ4     → 极速压缩解压，适合内存到磁盘的临时 Shuffle 数据
# BROTLI  → 高压缩率，Parquet v2 支持，适合网络传输场景

03 / Parquet vs ORC

Parquet vs ORC：深度对比与选型

两者都是优秀的列式格式，但在索引能力、嵌套数据支持、生态兼容性上有显著差异。选错格式在 PB 级数据场景下代价极高。

特性Apache ParquetApache ORC推荐场景
列式存储✓ 支持✓ 支持两者均可
嵌套复杂类型✓ 原生 Dremel 编码⚠ 支持但较弱嵌套 JSON → Parquet
ACID 事务✕ 依赖上层（Delta等）✓ Hive ACID 原生支持Hive 写密集 → ORC
轻量索引⚠ 列统计 + Bloom Filter✓ Row Index + Bloom Filter + 条纹索引点查优化 → ORC
Spark 默认格式✓ 默认需显式指定Spark 生态 → Parquet
Presto/Trino 支持✓ 优秀✓ 优秀两者均可
Delta / Iceberg 格式✓ 主要格式⚠ Iceberg 支持，Delta 不支持湖仓 → Parquet
压缩率（典型业务数据）中等（1:3~1:8）略优（1:4~1:10）存储敏感 → ORC
机器学习框架兼容✓ TensorFlow/PyTorch 原生支持✕ 需要转换ML Pipeline → Parquet
💡
2024 年的选型建议
Parquet 是现代数据湖（Delta Lake / Iceberg / Hudi 均支持）的事实标准，Spark 生态首选。嵌套数据、ML 场景无争议选 Parquet。
ORC 在 Hive 生态（仍大量存在的企业传统数仓）中更成熟，ORC 的行索引（Row Index）在点查和范围扫描上有一定优势。
新项目建议统一使用 Parquet + ZSTD + Delta Lake，兼顾压缩率、生态和事务能力。
04 / Delta Lake Transaction Log

Delta Lake：事务日志如何实现 ACID

对象存储（S3/HDFS）本身不支持事务。Delta Lake 通过在 _delta_log/ 目录维护一个 JSON 格式的事务日志（Transaction Log），将 ACID 语义叠加在任何存储之上。

Version 000000000000000000000.json · 初始化
CREATE TABLE — 写入协议与元数据
包含 protocol（minReaderVersion, minWriterVersion）、metaData（schema, partitionColumns, configuration）。协议版本决定了读写兼容性，升级列映射等特性时版本号随之提升。
protocolmetaDataschema 记录
Version 000000000000000000001.json · 首次写入
INSERT — 记录新增文件（add action）
每个写入的 Parquet 文件对应一条 add 记录，包含路径、大小、行数、列统计（min/max/nullCount）、分区值。文件实际写入后，最后才原子性写入此 JSON，确保读者看到完整数据或什么都看不到（原子性）。
add action列统计原子写入
Version 000000000000000000002.json · 更新
UPDATE — remove 旧文件 + add 新文件
Delta 采用 Copy-on-Write（默认）：更新时读取受影响文件、在内存修改、写出新 Parquet 文件，再用 remove 标记旧文件（逻辑删除，物理文件仍存在）和 add 新文件。旧文件在 VACUUM 前可用于时间旅行查询。
remove actionCopy-on-Write时间旅行
Version 000000000000000000010.checkpoint.parquet · 快照
每 10 次提交自动生成 Checkpoint（Parquet 格式）
将前 N 个 JSON 日志合并为单个 Parquet 快照，记录当前有效文件的完整集合。读取时只需加载最新 Checkpoint + 其后的增量 JSON，避免扫描全量历史日志。生产大表建议调小 checkpointInterval（默认 10）以加速元数据查询。
Checkpoint Parquet元数据加速每10次提交
并发写入冲突解决 · Optimistic Concurrency Control
乐观并发控制：冲突检测与重试
多个 Writer 同时写入时，Delta 使用乐观锁：每个 Writer 读取当前版本，处理数据，尝试写入 nextVersion.json。若发现已被占用（版本号冲突），则检测操作是否真正冲突（例如修改了不同分区），可以冲突则失败回滚，无冲突则重试。S3 场景需配置 DynamoDB 作为乐观锁协调器。
OCC版本冲突检测S3: DynamoDB Lock
delta_lake_ops.py PySpark + Delta 
from delta.tables import DeltaTable

# ── 创建 Delta Table ──────────────────────────────────
df.write \
  .format("delta") \
  .partitionBy("dt") \
  .option("delta.checkpointInterval", "5") \   # 每5次提交做一次 Checkpoint
  .save("s3://datalake/orders")

dt = DeltaTable.forPath(spark, "s3://datalake/orders")

# ── Upsert（MERGE）────────────────────────────────────
updates = spark.read.parquet("s3://staging/updates")

dt.alias("target").merge(
    updates.alias("source"),
    "target.order_id = source.order_id"
).whenMatchedUpdateAll() \
 .whenNotMatchedInsertAll() \
 .execute()

# ── 时间旅行查询 ─────────────────────────────────────
# 按版本号
df_v3 = spark.read.format("delta") \
             .option("versionAsOf", "3") \
             .load("s3://datalake/orders")

# 按时间戳
df_yesterday = spark.read.format("delta") \
                    .option("timestampAsOf", "2024-06-01") \
                    .load("s3://datalake/orders")

# ── Z-Order 优化（多维度数据跳过）───────────────────
# 将相关数据物理上聚集，提升多列过滤的 Row Group 跳过率
dt.optimize().executeZOrderBy("user_id", "event_date")

# ── 清理旧版本文件 ────────────────────────────────────
dt.vacuum(168)  # 保留最近 168 小时（7天）的历史文件，删除更老的
05 / Delta vs Iceberg vs Hudi

湖仓三强：架构差异与选型决策

三大开源湖仓格式各有侧重，选型时需结合生态绑定程度、更新模式、元数据规模和团队技术栈综合判断。

07 / Common Pitfalls

存储格式与数据湖常见陷阱

这些问题在初期不显眼，但随着数据规模增长会成为严重瓶颈。提前了解，规避于萌芽期。

🗂️
小文件地狱：Delta 表写入过于频繁
流式写入或频繁小批量写入会产生大量小 Parquet 文件，每次查询都需要列举和打开海量文件，元数据开销成为瓶颈。需定期执行 OPTIMIZE 合并小文件，或配置 Auto Compaction。
⏳
忘记 VACUUM：存储持续膨胀
Delta 的 CoW 更新不删除旧文件，时间旅行数据累积会让存储成本数倍膨胀。必须定期执行 VACUUM，且注意不要设置过短的保留期（会破坏流式消费者的偏移量）。
🔑
分区列选择错误：数据倾斜分区
选择高基数列（如 user_id）作为分区键会产生数百万个分区目录，文件系统元数据爆炸；选择极低基数列（如 is_active: true/false）导致分区内文件巨大。分区列应选择查询过滤频率高且基数适中（数百~数千）的列，如日期/地区/类别。
🧬
Schema Evolution 不兼容：类型变更
将列从 INT 改为 STRING，或删除列后又重新添加不同类型的同名列，会导致旧数据读取报错。Delta 只支持向上兼容的类型转换（INT→LONG），Iceberg 支持更多类型提升。任何 schema 变更前必须先测试时间旅行查询。
🔒
S3 上的并发写入冲突
S3 不支持原子 rename，Delta 在 S3 上需要 DynamoDB 作为分布式锁，否则并发写入可能损坏事务日志。必须配置 spark.delta.logStore.class 为 S3 专用实现，并创建对应 DynamoDB 表。
📉
Z-Order 未命中：列顺序选择错误
Z-Order 对最先指定的列效果最好，高选择性列应排在前面。若将基数极低的列（如 status）放在第一位，Z-Order 几乎无效。查询分析时先用 EXPLAIN 确认 Row Group 跳过率，再决定 Z-Order 列的顺序与组合。
✅
数据湖运维黄金法则
每日运维：对活跃写入的 Delta 表每日执行 OPTIMIZE（合并小文件）+ 每周 VACUUM（清理旧文件，保留 7 天）
监控指标：文件数量、平均文件大小（目标 128MB~512MB）、事务日志条数（超过 1000 条考虑 Checkpoint）
写入模式：流式写 → 定期 Compaction；批量写 → 直接写大文件；Upsert 场景 → 考虑 Hudi MoR
Schema 变更：使用 ALTER TABLE ADD COLUMNS（而非 overwriteSchema），保留历史数据可读性
