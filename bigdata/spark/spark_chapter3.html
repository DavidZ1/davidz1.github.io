01 / Execution Modes

两种执行模式：Micro-Batch vs Continuous

Structured Streaming 提供两套执行引擎，选择时需在延迟、吞吐、语义保证之间权衡。绝大多数生产场景使用 Micro-Batch。

⚙ 默认引擎
Micro-Batch Processing
延迟：100ms ~ 数秒（可配置）
  • 将流数据切分为微批次，每批次是一个完整的 Spark Job
  • 天然支持 Exactly-Once（通过 Offset + WAL 机制）
  • 吞吐量高，可充分利用批处理优化（Catalyst、Codegen）
  • 支持全部算子：聚合、Join、窗口函数、去重
  • Trigger 间隔可设为 0（尽快处理）或固定间隔
  • Spark 3.x 新增 Available-Now Trigger（一次性消费全量积压）
⚡ 实验性
Continuous Processing
延迟：~1ms（接近真实流）
  • Spark 2.3 引入，至今仍为实验特性（Experimental）
  • Record 级别处理，无批次概念，Driver 周期性同步 offset
  • 仅支持 At-Least-Once（checkpoint epoch 间可能重复）
  • 算子受限：只支持 map、filter、flatMap 等无状态操作
  • 不支持聚合、窗口、去重、Sort 等有状态算子
  • 生产中极少使用，延迟敏感场景建议用 Flink
💡
无界表（Unbounded Table）模型
Structured Streaming 将流数据抽象为一张持续追加行的无界表。用户写 DataFrame/SQL 操作这张表，引擎负责将其翻译为增量计算。这意味着：任何批处理的 DataFrame 逻辑，理论上只需换 Source 和启动方式，即可转为流处理——这是 Flink 等传统流框架无法做到的统一性。
02 / Micro-Batch Internals

Micro-Batch 引擎内部执行流程

每一次 Trigger 触发后，Micro-Batch 引擎经历固定的六步执行序列。理解这个流程是排查流作业卡顿、数据丢失和重复处理的基础。

Step 01 · Trigger
触发器激活，确定本批次 Offset 范围
StreamExecution 轮询 Source，调用 getOffset() 获取当前最新 Offset。与上次 Checkpoint 记录的 startOffset 对比，确定本批次的 endOffset。若无新数据，根据 Trigger 类型决定等待或退出。
StreamExecutiongetOffset()batchId 递增
Step 02 · WAL Write
Offset 写入 WAL（Write-Ahead Log）
Offset 范围 先于数据处理 写入 Checkpoint 目录下的 offsets/ WAL 文件。即使后续处理失败，重启后也能从此 Offset 重新消费，这是 Exactly-Once 的第一道保障。写入使用原子操作（HDFS rename）。
WALoffsets/ 目录原子写入
Step 03 · Batch Execution
触发标准 Spark Job 处理本批次数据
调用 getBatch(startOffset, endOffset) 生成该批次的 DataFrame，经过完整 Catalyst 优化 → 物理计划 → Codegen，作为普通 Spark Job 执行。有状态操作（聚合/Join）会读写 State Store。
getBatch()Catalyst 优化State Store 读写
Step 04 · Sink Commit
幂等写入 Sink，提交 batchId
结果写入 Sink（Kafka/文件/数据库）。可靠 Sink 实现幂等提交：相同 batchId 的数据写入两次结果相同。Kafka Sink 使用事务 Producer；文件 Sink 通过原子 rename 实现。
幂等 SinkbatchIdKafka 事务
Step 05 · Checkpoint Commit
将 Offset 写入 commits/ 标记批次完成
数据写出成功后，将 endOffset 写入 commits/ 目录，标记本批次彻底完成。下次重启时，若 offsets 中有记录但 commits 中没有，说明上次处理失败，需重新执行该批次。
commits/ 目录故障恢复标记
Step 06 · State Checkpoint
异步将 State Store 快照写入持久化存储
有状态查询还需将 State Store 的内存状态异步 checkpoint 到 HDFS/S3。RocksDB State Store（Spark 3.2+）支持增量 checkpoint，只写出变化的 SST 文件，大幅减少 checkpoint 时间和存储开销。
State CheckpointRocksDB 增量异步写出
03 / Watermark & Late Data Handling

Watermark 机制与乱序数据处理

流数据天然存在乱序——网络延迟、设备离线都可能导致事件时间远落后于处理时间。Watermark 定义了引擎愿意等待延迟数据的最大容忍边界。

Watermark 边界示意（延迟容忍 = 10 分钟）
12:0012:0612:1212:1812:2412:30
准时到达（纳入计算）
延迟但在容忍范围内（纳入计算）
超出 Watermark（丢弃）
Watermark 边界（max_event_time − 10min）
watermark_window.py PySpark 
from pyspark.sql import SparkSession
from pyspark.sql.functions import window, col, count, from_json
from pyspark.sql.types import StructType, StringType, TimestampType

spark = SparkSession.builder \
    .config("spark.sql.streaming.statefulOperator.checkCorrectness.enabled", "true") \
    .getOrCreate()

schema = StructType() \
    .add("user_id", StringType()) \
    .add("event_type", StringType()) \
    .add("event_time", TimestampType())  # 事件时间（不是处理时间）

# ── Kafka Source ─────────────────────────────────────
raw = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "broker:9092") \
    .option("subscribe", "user_events") \
    .option("startingOffsets", "latest") \
    .option("maxOffsetsPerTrigger", "100000") \  # 限制每批数据量
    .load()

events = raw.select(from_json(col("value").cast("string"), schema).alias("data")) \
            .select("data.*")

# ── Watermark + 滑动窗口聚合 ─────────────────────────
windowed = events \
    .withWatermark("event_time", "10 minutes") \  # 容忍最多10分钟延迟
    .groupBy(
        window(col("event_time"), "5 minutes", "1 minute"),  # 5分钟窗口,1分钟滑动
        col("event_type")
    ) \
    .agg(count("*").alias("event_count"))

# ── 输出模式选择（关键！）────────────────────────────
# append  - 只输出已关闭窗口的最终结果（需要 watermark）
# update  - 每次 trigger 输出所有变化的行（无需 watermark）
# complete- 每次输出全量结果（只适合小结果集）

query = windowed.writeStream \
    .outputMode("append") \         # 窗口关闭后才输出，保证准确性
    .format("kafka") \
    .option("kafka.bootstrap.servers", "broker:9092") \
    .option("topic", "event_counts") \
    .option("checkpointLocation", "hdfs://checkpoints/event_count_job") \
    .trigger(processingTime="30 seconds") \
    .start()

query.awaitTermination()
⚠️
Watermark 的三个关键约束
① append 模式必须设置 Watermark：没有 Watermark，引擎不知道窗口何时可以关闭，状态无限增长。
② Watermark 基于最大事件时间：watermark = max(event_time) − delay，由所有分区的最大值决定。某个分区停止消费会导致 Watermark 停滞！
③ 多流 Join 的 Watermark：多流 Join 时，全局 Watermark 取所有流中最小的那个，必须为每个流都设置 Watermark。
04 / State Store Internals

State Store：有状态计算的核心

所有有状态算子（聚合、流-流 Join、去重、mapGroupsWithState）都依赖 State Store 在批次间保存中间状态。Spark 3.2 引入 RocksDB 后端彻底改变了大状态场景的可行性。

🏠
HDFS-Based State Store（默认）
状态存储在 Executor 内存中（Java HashMap），每次 checkpoint 将全量状态序列化写入 HDFS。状态大时内存压力极大，checkpoint 时间随状态线性增长，可能引发长暂停。
适合状态 < 1GB
🪨
RocksDB State Store（3.2+）
使用 RocksDB LSM-Tree 存储状态于堆外（Native Memory），支持增量 checkpoint（仅写出变化的 SST 文件）。状态可超过 Executor 内存限制，checkpoint 时间基本恒定，是生产大状态场景的推荐选择。
适合状态 > 1GB · 增量 Checkpoint
🔑
State Schema Evolution（3.4+）
在不丢失历史状态的前提下，允许向 State Schema 新增列（仅支持追加，不支持删除/修改类型）。需要在 mapGroupsWithState 中显式声明新旧 schema 的兼容性。
Spark 3.4+ · 仅追加列
rocksdb_statestore.py PySpark 
# ── 启用 RocksDB State Store ──────────────────────────
spark = SparkSession.builder \
    .config(
        "spark.sql.streaming.stateStore.providerClass",
        "org.apache.spark.sql.execution.streaming.state.RocksDBStateStoreProvider"
    ) \
    # RocksDB 关键参数
    .config("spark.sql.streaming.stateStore.rocksdb.changelogCheckpointing.enabled", "true") \  # 增量 checkpoint
    .config("spark.sql.streaming.stateStore.rocksdb.compactOnCommit", "false") \    # 不在提交时做 Compaction
    .config("spark.sql.streaming.stateStore.rocksdb.blockSizeKB", "4") \
    .config("spark.sql.streaming.stateStore.rocksdb.blockCacheSizeMB", "8") \
    .getOrCreate()

# ── 自定义状态管理：mapGroupsWithState ───────────────
from pyspark.sql.streaming.state import GroupState, GroupStateTimeout
from dataclasses import dataclass
from typing import Iterator

@dataclass
class UserSessionState:
    session_count: int = 0
    total_amount: float = 0.0
    last_active_ts: int = 0

def update_session(
    user_id: str,
    events: Iterator,
    state: GroupState[UserSessionState]
) -> Iterator:
    # 超时处理（EventTime Timeout = 30分钟无活动视为会话结束）
    if state.hasTimedOut():
        final = state.get()
        state.remove()
        yield (user_id, final.session_count, final.total_amount, "CLOSED")
        return

    cur = state.getOption() or UserSessionState()
    for ev in events:
        cur.session_count += 1
        cur.total_amount += ev.amount
        cur.last_active_ts = ev.event_time

    state.update(cur)
    state.setTimeoutDuration("30 minutes")  # 重置超时计时器
    yield (user_id, cur.session_count, cur.total_amount, "ACTIVE")
05 / Trigger Strategies

Trigger 策略选择指南

Trigger 决定了流作业何时启动下一个 Micro-Batch，不同策略对延迟、吞吐、资源消耗有截然不同的影响。

Trigger 类型 API 行为 延迟 吞吐 适用场景
Default（Unspecified） .trigger() 不传参 上批完成立即执行下批 极低 高 需要最低延迟的场景
Fixed Interval processingTime="30s" 每 N 秒执行一次，上批超时则立即启动 中 高 均衡延迟与资源消耗
Once once=True 消费当前所有数据，处理一次后停止 高（批处理） 高 定时批处理场景（已弃用）
Available-Now（3.3+） availableNow=True 消费所有积压数据（多批次），完成后停止 高（批处理） 极高 代替 Once，支持流控
Continuous（实验性） continuous="1s" Record 级别处理，定期同步 checkpoint ~1ms 中 极低延迟无状态管道
trigger_examples.py PySpark 
from pyspark.sql.streaming import Trigger

# ✅ 生产推荐：固定间隔，平衡延迟与吞吐
query = df.writeStream \
    .trigger(processingTime="30 seconds") \
    .start()

# ✅ 最低延迟（适合延迟敏感 + 数据量不大）
query = df.writeStream \
    .trigger(processingTime="0 seconds") \  # 等价于默认
    .start()

# ✅ Available-Now：消费积压数据后自动停止（Spark 3.3+）
# 适合每小时运行一次、处理过去1小时积压的调度场景
query = df.writeStream \
    .trigger(availableNow=True) \
    .start()
query.awaitTermination()  # 等待处理完成

# ── 监控流查询状态 ───────────────────────────────────
query = df.writeStream.start()

# 实时进度（包含处理速率、batch耗时、输入行数等）
progress = query.lastProgress
print(f"输入速率: {progress['inputRowsPerSecond']:.1f} 行/秒")
print(f"处理速率: {progress['processedRowsPerSecond']:.1f} 行/秒")
print(f"Batch 耗时: {progress['batchDuration']} ms")

# 流状态（ACTIVE / TERMINATED）
print(query.status)
06 / Delivery Semantics & Exactly-Once

端到端 Exactly-Once 语义实现

Exactly-Once 是流处理最难保证的语义。Structured Streaming 通过 Source 可重放 + WAL + 幂等 Sink 三者协同实现，缺一不可。

✓ Exactly-Once
恰好一次
每条消息被处理且仅被处理一次，结果幂等写入 Sink。需要 Source 可重放 + 幂等 Sink + WAL 三者同时满足。
必需条件：可重放 Source + 幂等/事务 Sink
~ At-Least-Once
至少一次
每条消息至少被处理一次，失败重试可能导致重复处理。Sink 不支持幂等时（如 JDBC append）会产生重复数据。
条件：可重放 Source，任意 Sink
○ At-Most-Once
至多一次
消息可能丢失，但不重复。Source 不可重放（如直接 Socket）或不保存 Offset 时退化为此语义。生产中应避免。
条件：不可重放 Source
✓ Kafka → Kafka 端到端
实际生产中最常见的 E2E 配置
Kafka Source（可重放）+ WAL Checkpoint + Kafka Sink（事务 Producer）。Kafka Sink 使用两阶段提交：先写入事务，Batch 成功后 commit，失败则 abort，下次重放时写入新事务。
配置：kafka.isolation.level = read_committed
exactly_once_kafka.py PySpark 
# ── Kafka → Spark Streaming → Kafka 端到端 Exactly-Once ──

# Source: Kafka（天然可重放，通过 Checkpoint 记录 Offset）
source = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "broker:9092") \
    .option("subscribe", "input_topic") \
    .option("startingOffsets", "earliest") \
    .load()

processed = source.selectExpr("CAST(value AS STRING) as value")

# Sink: Kafka（事务 Producer，开启后自动 Exactly-Once）
query = processed.writeStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "broker:9092") \
    .option("topic", "output_topic") \
    .option("checkpointLocation", "hdfs://checkpoints/e2e_job") \  # 必须！
    .option("kafka.enable.idempotence", "true") \   # Producer 幂等
    .option("kafka.transactional.id", "spark-stream-job-1") \  # 事务 ID（唯一）
    .option("kafka.transaction.timeout.ms", "900000") \  # 15分钟超时
    .trigger(processingTime="10 seconds") \
    .start()

# ── 消费侧也需配置隔离级别 ───────────────────────────
# Consumer 必须设置 isolation.level=read_committed
# 否则会读到事务中间状态（uncommitted 消息）
consumer_config = {
    "kafka.isolation.level": "read_committed"
}
🚨
Checkpoint 目录：不可随意删除
Checkpoint 目录存储了 Offset WAL、State Store 快照、Schema 信息。删除后重启 = 从头消费，可能产生数据重复或丢失。
变更 query 逻辑（如新增列、修改 schema）有时需要新建 checkpoint，此时必须手动处理历史 Offset 的重放逻辑。
生产铁律：checkpoint 目录绑定作业版本，升级时用新路径，旧路径归档保留至少 7 天。
07 / Production Tuning

生产关键配置与调优参数

流作业长期运行的稳定性调优，与批处理有本质区别——需要重点关注状态增长、Trigger 延迟抖动和背压控制。

maxOffsetsPerTrigger
默认值：无限制 · 推荐：按数据量设置
限制每个 Micro-Batch 消费的最大 Offset 数量（即消息数）。避免积压时单批次数据量爆炸导致 OOM 或 Trigger 时间过长。Kafka Source 下每个 Partition 独立计算。
背压控制Kafka 专用
minBatchesToRetain
默认值：100 · 生产推荐：保持默认
Checkpoint 中保留的最小批次数。用于故障恢复时的 Offset 回溯。设置过小会导致历史 Offset 被清理，无法恢复到更早的检查点。
故障恢复Checkpoint 保留
statefulOperator.stateStoreMetrics
默认：false · 生产推荐：true
开启后 Spark UI 的 Streaming 页面显示详细 State Store 指标：状态行数、大小、读写延迟。是排查状态膨胀和 RocksDB 性能问题的必要工具。
可观测性State 监控
shuffle.partitions（流式场景）
默认值：200 · 推荐：与 Kafka 分区数对齐
流式场景下不建议开启 AQE 的 coalescePartitions（会导致分区数在批次间变化，破坏状态亲和性）。应固定设置为 Kafka Topic 分区数的整数倍，保证 State Store 本地性。
State 亲和性慎用 AQE

流作业关键监控指标

inputRowsPerSecond vs processedRowsPerSecond（追上速率 = 健康） 目标：处理 ≥ 输入
batchDuration（批次处理时间，应 < Trigger 间隔） 目标：< triggerInterval
State Store 行数增长率（无 Watermark 时应有上界） 目标：稳定或缓慢增长
Kafka Consumer Lag（积压消息数，应趋近于0） 目标：Lag → 0
08 / Common Pitfalls

生产常见陷阱与排查清单

流作业的陷阱往往比批处理更隐蔽——问题可能在运行数天后才显现，且难以复现。

📈
State 无限膨胀
未设置 Watermark 或 TTL 的聚合/去重操作，State Store 随时间线性增长，最终 OOM。必须为所有有状态算子设置 withWatermark 或 flatMapGroupsWithState 中的超时清理逻辑。
🧊
Watermark 停滞
某个 Kafka 分区长期无数据，其 max_event_time 不更新，导致全局 Watermark 停滞，窗口永不关闭，数据堆积。需监控各分区消费活跃度，考虑设置 kafka.group.id 专属，避免与其他消费者干扰。
🔀
输出模式选择错误
对聚合结果使用 append 模式但未设 Watermark，运行报错；使用 complete 模式写 Kafka 导致每批全量重写。需严格匹配算子类型与输出模式的兼容矩阵。
🔄
AQE 与 State 亲和性冲突
流式作业开启 AQE 的 coalescePartitions 后，不同 Batch 的 Shuffle 分区数可能不同，导致 State Store 的 Key 被路由到不同 Executor，状态读取失败或性能骤降。流式场景应固定 shuffle.partitions 并禁用分区合并。
💸
Checkpoint 写入成为瓶颈
大状态作业使用默认 HDFS State Store 时，全量 Checkpoint 时间可能超过 Trigger 间隔，导致 Batch 时间持续累积。升级到 RocksDB State Store + 增量 Checkpoint 是根本解决方案。
🕳️
流-流 Join 的笛卡尔积陷阱
两个流做 Join 时，若未设置 Watermark 和 Join 时间范围条件，引擎需要缓存所有历史数据等待匹配，状态无限增长。必须同时设置双流 Watermark 和 interval join 条件。
🛠
流作业排查黄金检查清单
Batch 变慢 → 查 lastProgress.batchDuration 趋势；检查 State Store 大小；检查 Kafka Lag 是否在增长
数据重复 → 确认 Checkpoint 目录未被删除；Sink 是否幂等；Kafka 是否开启事务
窗口不关闭 → 确认 Watermark 在正常推进；检查是否有 Kafka 分区消费停滞
OOM → 检查 State Store 行数；切换 RocksDB；检查 maxOffsetsPerTrigger 是否过大
