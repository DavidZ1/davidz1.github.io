01 / Diagnosis Methodology

五步诊断方法论：先定位再优化

性能调优最大的反模式是"凭感觉加参数"。正确姿势是先通过工具链精准定位瓶颈，再有针对性地优化——否则可能优化了错误的地方，浪费大量时间。

1
Step 01 · 宏观判断
先看总体耗时分布：是 CPU、IO 还是等待？
打开 Spark UI → Jobs 页面，观察各 Job 耗时占比。关键问题：哪个 Stage 耗时最长？进入该 Stage → 查看 Task 时间分布（Scheduler Delay / Task Deserialization / GC Time / Shuffle 读写 / 实际计算）。若 GC Time > 总时间 10%，则优先解决 GC；若 Shuffle Read/Write 占主导，优先解决 Shuffle；若单个 Task 远超中位数，则是数据倾斜。
Spark UI · JobsStage 耗时Task 时间拆解
2
Step 02 · 计划审查
df.explain("formatted") 审查物理执行计划
检查：① Join 策略是否符合预期（BHJ > SMJ）② 谓词下推是否生效（PushedFilters 出现在 FileScan）③ 是否存在意外的 Exchange（Shuffle）节点 ④ Codegen 是否生效（算子前有 *(N) 标记）⑤ AQE 是否生效（出现 AdaptiveSparkPlan）。物理计划是所有调优的起点。
explain("formatted")BroadcastHashJoinExchange 节点
3
Step 03 · 数据分布
诊断分区大小分布：是否存在倾斜？
在 Stage 详情页查看 Task 的 Input Size 和 Duration 分布。若最大值 > 中位数 × 5，且最大值 > 256MB，判定为数据倾斜。同时检查分区数量：分区过少（并行度不足）或过多（调度开销 + 小文件）都会导致性能问题。AQE 开启后可在 SQL 页面查看实际分区合并情况。
Task Input Size倾斜判定分区数诊断
4
Step 04 · 内存 & GC
查看 Executor GC 时间和 Storage 内存使用
Executor 页面查看 GC Time 列——若某 Executor GC 时间持续超过 5%，结合日志中 Full GC 频率判断内存压力。Storage 页面查看 Cache 命中率，Cache Eviction 频繁说明 Storage Memory 不足。结合 Executor 的 OOM 日志（java.lang.OutOfMemoryError）定位具体 Stage。
GC Time %Full GCCache Eviction
5
Step 05 · CPU 热点
Async Profiler + Flame Graph 定位 CPU 热点函数
对于计算密集型作业，仅靠 UI 无法定位具体热点。使用 Async Profiler（JVM 采样）或 Spark 3.2+ 内置的 spark.executor.extraJavaOptions=-agentpath:... 生成 Flame Graph。热点函数通常集中在：序列化/反序列化（→ 换 Kryo）、UDF 内部逻辑（→ 重写为内置函数）、Shuffle Spill（→ 增大 Execution Memory）。

02 / Spark UI Deep Dive

Spark UI 关键页面解读指南

Spark UI 是免费的最强调优工具，但大多数人只看"作业完成了没有"。掌握每个页面的关键指标才能做到精准调优。

📊 Stages 页面 最重要
Task Metrics Summary 展示 Min/25th/Median/75th/Max 五分位数。Max Duration 远超 Median → 数据倾斜。Max GC Time 高 → 内存压力。 Max Duration > Median × 3 = 数据倾斜信号
Shuffle Read/Write Size Shuffle Write 过大（数百GB）说明分区数太少或数据没有充分预聚合。Shuffle Read Records Max 远超 Median 同样是倾斜信号。
Input / Output Size Input Size 远大于实际查询列的数据量，说明列裁剪/谓词下推未生效。Output Size 异常大，可能是 Cartesian Product 或 explode 产生了数据膨胀。 Output >> Input = 数据膨胀（检查 explode/join）
🔍 SQL / DataFrame 页面 执行计划
物理计划可视化图 点击查询可展开树形物理计划。每个节点显示实际行数、预估行数、处理时间。实际行数远超估算 → CBO 统计信息过期，需重新 ANALYZE。
Exchange / Sort 节点 每个 Exchange 节点代表一次 Shuffle。关注其上方的 Sort：是否可用 Broadcast Join 消除？AQE 开启后，Exchange 节点旁会标注实际 Shuffle 数据量。 Exchange 数量 = Shuffle 次数，越少越好
WholeStageCodegen 节点 标有 *(N) 的算子链在同一 Codegen Stage 内执行，无虚调用开销。若关键算子未被 Codegen 包含，需排查是否有 Python UDF 打断了链路。
💻 Executors 页面 资源监控
GC Time 列 各 Executor 的 GC 总耗时。若某个 Executor GC Time / Task Time > 10%，且 Failed Tasks 数量较高，该 Executor 存在内存压力，需增大 executor.memory 或减少 executor.cores。 GC Time / Total Time > 10% = 内存危险区
Storage Memory Used 与 executor.memory 对比查看内存使用率。接近上限说明 Cache 数据过多或 Execution Memory 不足（被 Shuffle 大量占用导致 OOM）。
Task 失败率 Failed Tasks 集中在同一 Executor，通常是硬件问题（磁盘满/网络不稳）。若分散在所有 Executor，则是逻辑问题（数据格式、OOM）。
🌊 Streaming 页面 流作业专用
Batch Duration 趋势 每批处理时间应稳定且低于 Trigger 间隔。若持续上升 → 处理速度跟不上输入速度，需增大并行度或减少 maxOffsetsPerTrigger 触发背压。 Batch Duration > Trigger Interval = 积压中
Input Rate vs Processing Rate 健康状态应处理速率 ≥ 输入速率。若长期低于，需排查 State Store 慢（切换 RocksDB）、Checkpoint 慢（增量 Checkpoint）或计算逻辑复杂度过高。
State Operator Metrics 开启 stateStoreMetrics 后显示 State 行数/大小/读写延迟。State 行数持续增长说明 Watermark 未生效或超时未正确清理。

数据倾斜是 Spark 生产问题 No.1 杀手。作业跑了 3 小时，最后一个 Task 卡了 2 小时 50 分钟——这就是倾斜。掌握系统化的根治方案，而不是头痛医头。

✕ 反模式：治标不治本
常见的错误应对方式
  • 盲目增大 executor.memory，治标但不治本，浪费资源
  • 增大 shuffle.partitions 到 10000，小分区开销反而更大
  • 对所有列做 Salting，破坏数据语义，引入额外复杂度
  • 禁用 AQE，手动处理所有倾斜，维护成本极高
  • 忽略倾斜，"等着跑完"，下次还会出现
✓ 正确方案：按根因对症
系统化根治路径
  • 先用 AQE Skew Join（Spark 3.0+），80%场景自动解决
  • 热点 Key 确认后，用 Salting（随机后缀）打散大 Key
  • 小表 JOIN 大表倾斜 → 广播小表（BroadcastHashJoin）
  • GROUP BY 倾斜 → 两阶段聚合（局部聚合 + 全局聚合）
  • 数据源层解决：写入时按更均匀的列分区
skew_solutions.py PySpark 
import pyspark.sql.functions as F

# ── 方案1: AQE 自动处理倾斜（优先尝试）────────────
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "3")  # 降低触发阈值
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "128m")

# ── 方案2: 手动 Salting（AQE 无效时的终极方案）───
SALT_NUM = 16  # Salt 粒度，根据倾斜程度调整

# 大表：给 Join Key 加随机 Salt 后缀
big_table_salted = big_table.withColumn(
    "salted_key",
    F.concat(
        F.col("user_id").cast("string"),
        F.lit("_"),
        (F.rand() * SALT_NUM).cast("int").cast("string")
    )
)

# 小表：将每行复制 SALT_NUM 份，分别加 0~N-1 后缀
salt_values = spark.range(SALT_NUM).toDF("salt")
small_table_expanded = small_table.crossJoin(salt_values).withColumn(
    "salted_key",
    F.concat(F.col("user_id").cast("string"), F.lit("_"), F.col("salt").cast("string"))
)

result = big_table_salted.join(small_table_expanded, "salted_key")

# ── 方案3: 两阶段聚合（GROUP BY 倾斜）──────────────
# 第一阶段：局部聚合，用随机 salt 打散 key
partial_agg = orders \
    .withColumn("salt", (F.rand() * 8).cast("int")) \
    .groupBy("user_id", "salt") \
    .agg(F.sum("amount").alias("partial_sum"))

# 第二阶段：全局聚合，再对 partial_sum 求和
final_agg = partial_agg \
    .groupBy("user_id") \
    .agg(F.sum("partial_sum").alias("total_amount"))

gc_tuning.conf JVM Config 
-- G1GC 调优（推荐：32GB+ Heap 的 Executor）-----------

spark.executor.extraJavaOptions = \
  "-XX:+UseG1GC                      # 启用 G1 GC"
  "-XX:G1HeapRegionSize=16m           # Region 大小（1MB~32MB，建议16MB）"
  "-XX:InitiatingHeapOccupancyPercent=35  # 堆占用35%时触发并发GC（默认45%太高）"
  "-XX:MaxGCPauseMillis=200           # 目标最大停顿时间 200ms"
  "-XX:+PrintGCDetails                # 打印GC详情（调试期开启，生产可关）"
  "-XX:+PrintGCDateStamps"
  "-Xloggc:/tmp/gc.log               # GC 日志路径"

-- 诊断 Off-Heap 问题时额外添加 ----------------------
  "-XX:+HeapDumpOnOutOfMemoryError    # OOM 时自动 Heap Dump"
  "-XX:HeapDumpPath=/tmp/heapdump.hprof"
  "-XX:+ExitOnOutOfMemoryError       # OOM 时立即退出（避免僵尸 Executor）"

-- 小 Heap（<8GB）Executor 可用 ParallelGC -----------
  "-XX:+UseParallelGC"
  "-XX:ParallelGCThreads=4"

-- Off-Heap 内存（减少 GC 压力的根本方案）-----------
spark.memory.offHeap.enabled     = true
spark.memory.offHeap.size        = 8g   # 从堆外分配8GB用于执行
spark.executor.memoryOverhead    = 4g   # 容器总内存 = executor.memory + overhead

-- 检查 GC 是否是瓶颈（Shell 命令）-------------------
# grep "Full GC" /tmp/gc.log | wc -l   # Full GC 次数
# grep "pause" /tmp/gc.log | awk '{print $NF}' | sort -n | tail  # 最长停顿
⚠️
GC 的三种典型症状与对应方案
① 频繁 Young GC（Minor GC）：短期对象（Task 中间变量）分配过快，增大 -Xmn（新生代大小）或增加 Executor 内存
② Full GC 频繁（Old Gen 满）：对象晋升到老年代太多，通常是 Cache 或大型 UDF 结果集驻留内存。切换 Off-Heap 或降低 spark.memory.storageFraction
③ OOM: GC Overhead Limit Exceeded：GC 消耗超过 98% 时间却只回收 2% 内存，JVM 主动抛出。根本原因是内存严重不足，需增大内存或减少单 Task 数据量（增大分区数）

05 / Shuffle Optimization

Shuffle 全链路优化

Shuffle 是分布式计算中最昂贵的操作——网络传输、序列化、磁盘 IO 三重开销叠加。优化目标是"能不 Shuffle 就不 Shuffle，必须 Shuffle 就尽量小"。

消除 Shuffle：Broadcast Join
阈值：autoBroadcastJoinThreshold = 10MB（可调至 512MB）
当一侧表 < 阈值时，Spark 自动广播到所有 Executor，完全消除该 Join 的 Shuffle。宽表（SELECT *）时阈值估算不准，需手动 broadcast() 提示或增大阈值。AQE 开启后会在运行时自动升级。
最高收益消除 Exchange
减小 Shuffle 量：map 端预聚合
算子：reduceByKey / aggregateByKey（非 groupByKey）
Map 端预聚合在 Shuffle 前先在本地合并相同 Key，大幅减少网络传输数据量。reduceByKey 比 groupByKey().mapValues(sum) 快 3~10 倍。SQL 中的 GROUP BY + SUM/COUNT 会自动触发 HashAggregate（含 map 端部分聚合）。
Map 端聚合网络 IO 减少
分区数调优：AQE + 手动设置
参数：spark.sql.shuffle.partitions（默认 200）
黄金公式：分区数 = max(数据量GB × 4, Executor数 × Cores × 2)。AQE 会在运行时自动合并过小的分区（目标 128MB），但如果初始分区数过少，数据倾斜无法被切分。建议设置初始值偏大（500~2000），让 AQE 合并。
并行度AQE 合并
Shuffle Spill 优化
参数：spark.shuffle.spill.compress = true
Shuffle Spill 发生时（Execution Memory 不足），中间数据溢写磁盘。启用压缩减少磁盘 IO（使用 snappy 而非 lz4）。根本解决方案：增大 Execution Memory 或减少单分区数据量（增大分区数）。Push-Based Shuffle（Spark 3.2+）可合并 Spill 文件减少随机 IO。
磁盘 Spill压缩减少 IO
06 / Resource Configuration Formula

Executor 资源配置黄金公式

Executor 配置是 Spark 调优中最基础也最容易出错的部分。以 YARN 模式、32 核 256GB 内存节点为例，演示生产推荐配置的推导过程。

resource_formula.sh 配置推导 
## ══ 生产 Executor 配置推导（YARN 集群）══════════════
## 硬件：每节点 32 核 / 256GB RAM / 10Gbps 网卡
## ─────────────────────────────────────────────────

## Step 1：确定 executor.cores（并发 Task 数）
## 经验法则：4~5 核/Executor（平衡并发与 GC 压力）
spark.executor.cores = 5
## → 每节点最多 32/5 ≈ 6 个 Executor（留1个 NodeManager）
## → 每节点实际: floor(32 / 5) = 6 Executors

## Step 2：确定 executor.memory
## 每节点内存：256GB，系统 + NM 预留 8GB → 可用 248GB
## 每 Executor 可用：248 / 6 ≈ 41GB → 取整 40GB
spark.executor.memory         = 36g  # JVM 堆内存
spark.executor.memoryOverhead  = 4g   # 堆外内存（容器总 40GB）

## Step 3：内存内部划分
## 可用堆 = 36g × (1 - Reserved 0.3) ≈ 25.2g（Spark 内部保留 10%）
## Unified Pool = 25.2g × memory.fraction(0.75) ≈ 18.9g
## Storage Region ≈ 18.9g × storageFraction(0.4) ≈ 7.6g
## Execution Region ≈ 18.9g × 0.6 ≈ 11.3g（可向 Storage 借用）
spark.memory.fraction         = 0.75  # Shuffle 密集型适当调高
spark.memory.storageFraction  = 0.4   # 无大量 Cache 时调低

## Step 4：Driver 配置
spark.driver.memory           = 8g   # collect() 场景加大到 16g
spark.driver.maxResultSize    = 4g   # Action 返回结果最大值

## Step 5：并行度
## 总 Task 槽 = 6 Executor/节点 × N节点 × 5 cores
## shuffle.partitions 推荐 = Task槽数 × 2~4
## 例：20节点 × 6 × 5 = 600 Task槽 → shuffle.partitions = 1200
spark.sql.shuffle.partitions  = 1200
spark.sql.adaptive.enabled    = true  # AQE 自动合并小分区

## Step 6：序列化（必须）
spark.serializer = org.apache.spark.serializer.KryoSerializer
spark.kryoserializer.buffer.max = 1g  # 单对象最大序列化大小

调优效果量化：典型 ETL 作业

Broadcast Join 替换 Sort-Merge Join（小表 < 50MB）提速 8~20x
Kryo 序列化 vs Java 序列化（Shuffle 密集型作业）提速 40~70%
Salting 解决 GroupBy 倾斜（单 Key 占 70% 数据）提速 5~15x
Off-Heap 内存 + G1GC 调优（Full GC 频繁场景）GC 停顿减少 60~85%
谓词下推 + 列裁剪（Parquet 宽表，只读 5/50 列）IO 减少 80~95%
AQE 全量开启（典型混合 ETL 作业综合提升）整体提速 20~50%

调优优先级排序：高收益优先
第一优先（消除 Shuffle）：Broadcast Join、谓词下推、列裁剪——IO 和网络传输是最贵的资源
第二优先（数据倾斜）：AQE Skew Join + Salting——一个倾斜 Task 可以让整个 Stage 慢 10 倍
第三优先（序列化）：Kryo 序列化——Shuffle 密集型作业 30~50% 的 CPU 在序列化上
第四优先（GC）：G1GC 调优 + Off-Heap——GC 问题通常只在数据量和并发度很高时才是主要瓶颈
第五优先（参数微调）：shuffle.partitions、memory.fraction——在前几项已优化的基础上再做精调
