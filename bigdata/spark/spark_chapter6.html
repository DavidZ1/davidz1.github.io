01 / Deployment Modes

三种部署模式：架构差异与选型

部署模式决定了 Spark 如何申请和管理计算资源。选型需结合现有基础设施、运维能力、弹性需求和云原生程度综合判断。

🧶
Spark on YARN
企业传统数仓主流
与 Hadoop 生态深度集成，共享 HDFS、Hive Metastore、Kerberos 认证
ResourceManager 统一调度 YARN 容量队列，多作业资源隔离成熟
动态资源分配（Dynamic Allocation）需搭配 External Shuffle Service
Driver 可运行在集群内（cluster 模式）或客户端（client 模式）
运维复杂度中等，需维护 NodeManager 和 ResourceManager HA
弹性扩容受限于物理集群规模，云原生弹性不如 K8s
推荐：现有 Hadoop 集群 · 传统数仓 · 强安全合规要求
⎈
Spark on Kubernetes
云原生趋势首选
Executor 以 Pod 运行，天然弹性伸缩，与云厂商 Auto Scaling 无缝集成
容器化隔离更彻底，不同作业使用不同镜像（Python 版本、依赖隔离）
Spark 2.3 正式支持，Spark 3.1+ 稳定性显著提升
Dynamic Allocation 需 ExternalShuffleService 或 Shuffle 文件系统方案
Spark Operator（开源）简化 K8s 上的 Spark 作业管理
存储依赖对象存储（S3/OSS），无本地 HDFS 数据局部性优化
推荐：云原生环境 · 多语言混合 · 强弹性需求
🖥
Standalone 模式
开发测试 / 小规模
Spark 自带集群管理器，无需额外依赖，部署最简单
Master / Worker 架构，Worker 节点注册到 Master
资源隔离能力弱，多作业共享时容易相互干扰
无动态资源分配，资源静态分配给每个 Application
适合快速验证、开发调试、小规模生产（<10节点）
生产大规模场景不推荐，无企业级 HA 和资源管理
推荐：本地开发 · 功能验证 · <10节点小集群

02 / Spark on Kubernetes Deep Dive

Spark on Kubernetes：生产关键配置

K8s 部署引入了容器调度、存储挂载、网络策略等新维度，与 YARN 的运维模型有本质差异。掌握关键配置才能在 K8s 上稳定运行 Spark。

📦
镜像分层策略
基础层（JDK + Spark）→ 依赖层（Python packages）→ 业务层（作业代码）。三层分离使依赖缓存最大化，业务变更只需更新顶层镜像（通常 <10MB）。
构建时间减少 80%
🗄️
Shuffle 数据持久化
K8s Pod 重启 = Shuffle 数据丢失。解决方案：① 挂载 hostPath 本地盘 ② Remote Shuffle Service（RSS，如 Apache Celeborn）③ 写出到对象存储（性能较低）。
Apache Celeborn 推荐
⚖️
资源 Request vs Limit
设置 CPU request = cores，limit = cores × 1.2（允许 burst）。Memory request = limit（避免 OOM Kill）。memoryOverhead 必须计入容器 limit。
避免 OOM Kill
🔐
RBAC 与 ServiceAccount
Driver Pod 需要创建和删除 Executor Pod 的权限。为每个业务团队创建独立 ServiceAccount，绑定最小权限 Role（仅 pods CRUD + services get）。
最小权限原则
🎯
Node Affinity 与污点
用 nodeSelector 将 Spark Pod 调度到专属节点池（带大内存/高网络节点），避免与在线服务竞争资源。用 taints 拒绝非 Spark 工作负载。
资源隔离
🔄
Spark Operator
将 SparkApplication 定义为 CRD，支持 Spark 作业的声明式管理、自动重试、定时调度（ScheduledSparkApplication）。Google 开源，生产环境强烈推荐。
google/spark-on-k8s-operator
spark-application.yaml Kubernetes 
apiVersion: sparkoperator.k8s.io/v1beta2
kind: SparkApplication
metadata:
  name: daily-etl-job
  namespace: spark-production
spec:
  type: Python
  pythonVersion: "3"

  restartPolicy:

    onFailureRetries: 3
    onFailureRetryInterval: 10

    nodeSelector:
      node-type: spark-executor

      effect: "NoSchedule"

prometheus_alerts.yaml YAML 
# ── Spark 关键告警规则（Prometheus AlertManager）──────
groups:
- name: spark_production_alerts
  rules:

  # P0: Executor 大量丢失（作业可能失败）
  - alert: SparkExecutorLostMass
    expr: rate(spark_executor_failed_total[5m]) > 3
    for: 2m
    severity: critical
    annotations:
      summary: "{{ $labels.app_id }} 5分钟内丢失超过3个Executor"

  # P1: GC 时间占比过高
  - alert: SparkHighGCTime
    expr: spark_executor_gc_time_percent > 0.1
    for: 5m
    severity: warning
    annotations:
      summary: "Executor {{ $labels.executor_id }} GC时间超过10%"

  # P1: Shuffle Spill 异常（内存不足）
  - alert: SparkShuffleSpillHigh
    expr: spark_stage_shuffle_spill_memory_bytes > 10737418240  # 10GB
    for: 1m
    severity: warning

  # P2: 作业运行时间超过阈值（检测卡死）
  - alert: SparkJobRunningTooLong
    expr: spark_job_duration_seconds > 7200  # 2小时
    for: 0m
    severity: warning

  # P0: Driver 堆内存使用率过高（OOM 预警）
  - alert: SparkDriverOOMRisk
    expr: spark_driver_heap_used / spark_driver_heap_max > 0.9
    for: 3m
    severity: critical

04 / Incident Runbook

高频故障排查手册

每个故障类型都有固定的排查路径。建立 Runbook（操作手册）让任何工程师都能按步骤快速定位和恢复，而不依赖个人经验。

💀 Executor Lost / 大量失败 P0
症状
Spark UI 显示大量 Failed Tasks；日志出现 ExecutorLostFailure；作业反复重试后失败
排查步骤
  • 检查 Executor 日志：grep "WARN\|ERROR\|killed" executor-*.log
  • 确认是否 OOM：日志含 OutOfMemoryError 或 Container killed by YARN
  • OOM → 增大 memoryOverhead 或减小 executor.cores
  • 非 OOM → 检查节点磁盘（df -h）和网络（netstat -s）
  • 若集中在特定节点 → 将该节点排除出集群，提工单修复
yarn logs -applicationId <appId> | grep "ExecutorLost\|OOM\|killed" kubectl logs <executor-pod> --previous # K8s 场景
🧠 Driver OOM P0
症状
Driver 进程崩溃；日志出现 java.lang.OutOfMemoryError: Java heap space；整个 Application 终止
排查步骤
  • 查 Driver 日志确认 OOM 触发点（哪一行代码）
  • 检查是否有 df.collect() 或 toPandas() 操作
  • 检查 broadcast 变量大小是否超过 driver.memory
  • 检查 spark.driver.maxResultSize 是否过大
  • 短期：增大 driver.memory；根本：消除大 collect()
# 用 Heap Dump 分析大对象 jmap -histo <driver_pid> | head -30 # 或开启自动 Dump: -XX:+HeapDumpOnOutOfMemoryError
🧊 Stage 卡死 / Task 长时间不完成 P1
症状
某个 Stage 只剩最后 1~3 个 Task，卡了数小时；其他 Task 已完成
排查步骤
  • Spark UI → Stage 详情 → 找到卡住的 Task，查看其 Input Size
  • Input Size 远大于其他 Task → 数据倾斜，参考 Ch.05 倾斜解决方案
  • Input Size 正常但很慢 → 查该 Task 所在 Executor 的 GC 日志
  • Executor 日志正常 → 可能是网络 IO 慢（跨机房 Shuffle）
  • 启用推测执行（Speculative Execution）作为临时缓解措施
# 启用推测执行（慢 Task 在其他节点重跑） spark.speculation=true spark.speculation.multiplier=1.5 spark.speculation.quantile=0.9
🌊 流作业 Lag 持续增长 P1
症状
Kafka Consumer Lag 监控持续上升；Streaming UI 显示 Batch Duration 超过 Trigger Interval
排查步骤
  • 查 lastProgress：batchDuration vs triggerInterval 的比值
  • batchDuration 中最长步骤：State 操作 / Shuffle / 写出？
  • State 操作慢 → 切换 RocksDB State Store + 增量 Checkpoint
  • 写出慢 → 检查 Sink（Kafka 生产者 buffer/网络）
  • 临时缓解：降低 maxOffsetsPerTrigger 减少单批数据量
# 检查流进度 query.lastProgress # Python # 检查 State Store 大小 spark.sql("SELECT * FROM spark_streaming_state_info")
🚨
生产铁律：永远不要在不理解根因的情况下重启作业
盲目重启可能掩盖根本问题（数据损坏、磁盘满、网络分区），且流作业重启可能导致 Checkpoint 状态不一致。正确步骤：① 保存现场（日志、Heap Dump、Spark UI 截图）② 分析根因 ③ 修复后再重启 ④ 监控确认恢复正常 ⑤ 复盘写入 Runbook。
05 / Multi-Tenancy & Security

多租户资源隔离与安全配置

大规模生产集群通常服务多个业务团队，资源隔离和安全认证是稳定运行的基础。

YARN 队列
Capacity Scheduler
按比例分配集群容量给各业务队列，保证最低资源 + 允许弹性借用空闲容量
Fair Scheduler
作业间公平共享资源，支持按用户/组设置权重，适合多用户共享场景
K8s 命名空间
ResourceQuota
限制命名空间内 CPU/Memory 总量上限，防止单团队耗尽集群资源
LimitRange
设置 Pod 的默认 request/limit，防止无 resource 定义的 Pod 占用过多
PriorityClass
高优先级作业（实时报表）抢占低优先级资源（夜间批处理）
认证授权
Kerberos（YARN）
企业级 HDFS/YARN 认证，需配置 keytab 和 principal 自动续期
RBAC（K8s）
ServiceAccount + Role/ClusterRole 精细控制 Pod 操作权限
Spark ACL
控制 Spark UI 访问权限（spark.ui.acls.enable + spark.admin.acls）
数据安全
Shuffle 加密
spark.authenticate=true + AES 加密 Shuffle 数据传输
存储加密
S3 SSE-KMS / HDFS 透明加密区域，静态数据加密
列级权限（Ranger）
Apache Ranger 集成，实现列级别/行级别数据脱敏和访问控制

07 / Future Outlook

Spark 生态未来展望

Spark 4.0 和周边生态正在快速演进，了解技术趋势帮助你提前布局和做出更好的架构决策。

🚀
Spark 4.0：新一代引擎
统一批流 API（Connect 协议），Python-first 设计，改进的 ANSI SQL 兼容性，新的 DataFrame API（无 SparkContext 依赖），以及更强的 Python UDF 向量化支持（Arrow-based）。
2025 年发布
🔗
Apache Celeborn（Remote Shuffle）
解决 K8s 上 Shuffle 数据不持久的问题，将 Shuffle 数据集中写入专用 Shuffle 服务，Executor Pod 可随时重启而不丢失 Shuffle 数据，同时减少本地磁盘依赖。
K8s 场景 Shuffle 解决方案
🧊
Apache Iceberg 成为湖仓标准
AWS Glue、Snowflake、Databricks 相继支持 Iceberg，引擎中立的元数据层正在成为数据湖事实标准。Iceberg REST Catalog 让多引擎共享同一份元数据成为可能。
多云 · 多引擎融合
⚡
VELOX / Arrow DataFusion 加速
Meta 开源的 VELOX 执行引擎（C++ 原生，支持 SIMD），正在被 Spark（通过 Gluten 项目）和 Presto 集成，为算子密集型查询提供 2~5x 的 CPU 性能提升。
Native Execution · SIMD
🤖
AI/ML 与 Spark 深度融合
Spark + PyTorch/TensorFlow 分布式训练（通过 TorchDistributor），Spark ML 向量化特征工程，以及 LLM 推理在 Spark 集群上的分布式部署（通过 vLLM 集成）。
TorchDistributor · LLM on Spark
☁️
Serverless Spark
AWS Glue Serverless、Databricks Serverless、Google Dataproc Serverless 将资源管理完全托管，按实际使用量计费，消除集群运维负担。适合不规则工作负载。
按需弹性 · 零运维
