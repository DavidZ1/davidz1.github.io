01 / Architecture Overview

Spark 是一套多层次的统一计算引擎，从用户 API 到物理执行，每一层都有明确的职责划分。理解各层边界是调优的前提。

02 / DAG & Stage Model

DAG 调度与 Stage 划分原理

理解 Spark 如何将算子链路转化为物理执行阶段，是排查 OOM、数据倾斜和性能瓶颈的核心基础。

💡
核心机制
Stage 边界由 宽依赖（Wide Dependency） 决定——任何触发 Shuffle 的算子（groupByKey、reduceByKey、join on different keys）都会切割 Stage。窄依赖（map、filter、flatMap）则在同一个 Stage 内通过 Pipeline 执行，不产生磁盘 IO。
Phase 01 · Logical Plan
Action 触发，生成逻辑计划
用户调用 collect()、count()、save() 等 Action 时，SparkContext 开始从 RDD DAG 反向追溯所有依赖，构建有向无环图。转换操作（Transformation）是惰性的，在此之前不执行任何计算。
Lazy EvaluationDAGScheduler.runJob()
Phase 02 · Stage Splitting
宽依赖切割 Stage，生成 ShuffleMapStage
DAGScheduler 遍历 RDD 血缘（Lineage），遇到宽依赖则插入 Stage 边界。上游 Stage 被标记为 ShuffleMapStage，负责计算并写出 Shuffle 数据；最终消费结果的阶段为 ResultStage。
ShuffleMapStageResultStageLineage Graph
Phase 03 · Task Generation
每个 Partition 对应一个 Task
Stage 内的 Task 数量 = RDD 的分区数。ShuffleMapTask 写出 .index + .data 文件到本地磁盘；ResultTask 从上游拉取并最终聚合结果。Task 序列化后发送给 Executor。
ShuffleMapTaskResultTaskPartition = Task
Phase 04 · Task Local Scheduling
本地性优先调度（Data Locality）
TaskScheduler 按 PROCESS_LOCAL → NODE_LOCAL → RACK_LOCAL → ANY 优先级调度 Task。等待本地 Executor 最长 spark.locality.wait（默认 3s），超时才降级。生产环境数据倾斜时常需调整此参数。

stage_inspection.scala Scala 
// ✅ 查看 RDD 的分区数与依赖关系
val rdd = sc.textFile("hdfs://data/events")
            .flatMap(_.split(" "))
            .map(w => (w, 1))

// 查看分区数（决定 Task 数量）
println(rdd.partitions.length)

// 查看依赖类型（窄 vs 宽）
rdd.dependencies.foreach {
  case _: NarrowDependency[_] => println("窄依赖 - 同一 Stage")
  case _: ShuffleDependency[_, _, _] => println("宽依赖 - Stage 边界")
}

// ❌ 错误示范：用 groupByKey 而不是 reduceByKey
// groupByKey 会把所有相同 key 的 value 全量拉到一个 Executor，极易 OOM
val bad = rdd.groupByKey().mapValues(_.sum)

// ✅ 正确：reduceByKey 在 Map 端先聚合，大幅减少 Shuffle 数据量
val good = rdd.reduceByKey(_ + _)
03 / Unified Memory Management

统一内存管理模型

Spark 1.6 引入 UnifiedMemoryManager，彻底替代静态内存划分。理解 Execution Memory 与 Storage Memory 的动态边界，是解决 OOM 和 GC 问题的关键。

✓ Unified Memory Manager（1.6+）
动态边界，弹性共享
  • Execution 和 Storage 共享同一内存池，按需借用
  • 当 Execution 需要内存时，可驱逐 Storage 中的 Cache 数据
  • Storage 使用不超过 spark.memory.storageFraction 时，Execution 可借用
  • 大幅提升内存利用率，减少 OOM 发生概率
  • 适合工作负载动态变化的生产环境
旧 Static Memory Manager（已废弃）
静态割据，浪费严重
  • Execution / Storage / Other 三区域硬编码比例
  • 某一区域用满时无法借用其他区域
  • 大量 Cache 时 Execution 内存紧张易 OOM
  • 大量 Shuffle 时 Storage 内存大量闲置
  • Spark 3.x 中已完全移除
⚠️
内存区域计算公式
Executor 可用堆内存 = spark.executor.memory × (1 - spark.memory.fraction × 0.3)（Reserved 部分）
Unified Pool = 堆内存 × spark.memory.fraction（默认 0.6）
Storage Region = Unified Pool × spark.memory.storageFraction（默认 0.5）
即：Storage 初始占总堆的 30%，Execution 初始占 30%，两者可动态调整。
memory_tuning.conf Config 
-- 生产环境推荐内存配置模板（32GB Executor）--

spark.executor.memory            = 28g   # 留4g给系统
spark.executor.memoryOverhead    = 4g    # 堆外内存（容器总量=28+4=32g）
spark.memory.fraction            = 0.75  # Shuffle密集型作业适当提高
spark.memory.storageFraction     = 0.4   # Cache较少时可调低

# 启用堆外内存（Tungsten Off-Heap）减少 GC 压力
spark.memory.offHeap.enabled     = true
spark.memory.offHeap.size        = 8g

# GC 调优（G1GC for large heap）
spark.executor.extraJavaOptions  = "-XX:+UseG1GC \
  -XX:G1HeapRegionSize=16m \
  -XX:InitiatingHeapOccupancyPercent=35 \
  -XX:+PrintGCDetails"
04 / Shuffle Internals

Shuffle 机制深度解析

Shuffle 是分布式计算中最昂贵的操作。Spark 经历了多代 Shuffle 实现，现代版本以 Sort-Based Shuffle 为核心，配合 Bypass 优化和 Push-Based Shuffle。

shuffle_optimization.py PySpark 
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder \
    .config("spark.sql.shuffle.partitions", "400") \
    .config("spark.sql.adaptive.enabled", "true") \
    .config("spark.sql.adaptive.coalescePartitions.enabled", "true") \
    .getOrCreate()

# AQE (Adaptive Query Execution) 自动合并小分区
# 当 Shuffle 后某分区数据量 < targetPostShuffleInputSize(256MB) 时自动合并

orders = spark.read.parquet("hdfs://data/orders")
items  = spark.read.parquet("hdfs://data/items")

# ❌ 数据倾斜场景：某几个 key 数据量远超其他
bad_join = orders.join(items, "product_id")

# ✅ 方案1：AQE Skew Join 自动处理（Spark 3.0+）
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "5")

# ✅ 方案2：手动 salting 解决严重倾斜
import random
SALT_RANGE = 8
orders_salted = orders.withColumn(
    "salted_key",
    F.concat(F.col("product_id"), F.lit("_"),
            (F.rand() * SALT_RANGE).cast("int"))
)
🚨
Shuffle 文件数量爆炸
Sort-Based Shuffle 每个 Mapper 写出 1个 .data + 1个 .index 文件。当 M × R 极大时（M=Mapper数，R=Reducer分区数），文件元数据对 Driver 和 NodeManager 压力极大。生产中若 M × R > 100万，需考虑开启 Push-Based Shuffle（Spark 3.2+）或 External Shuffle Service。

Shuffle 实现演进对比

Shuffle 实现 版本区间 文件数量 内存效率 Sort 支持 当前状态
Hash-Based Shuffle 0.x – 1.1 M × R 个文件 低 ✕ 已移除
Sort-Based Shuffle 1.2 – 至今 2M 个文件 高 ✓ 默认实现
Bypass Sort（Fallback） 1.4 – 至今 2M 个文件 中 ✕ 分区数 < 200 时自动启用
Push-Based Shuffle 3.2 – 至今 更少（合并写） 极高 ✓ ⚠ 需 External Shuffle Service
05 / Key Configuration Knobs

核心调优参数详解

以下是生产中影响最大的参数，理解其背后机制比记住默认值更重要。

spark.sql.shuffle.partitions
默认值：200 · 推荐范围：数据量/200MB
决定 Shuffle 后的分区数，直接影响并行度。数据量 200GB 时推荐设为 1000，数据量 <10GB 时应降低至 20~50 避免小文件。AQE 开启后可自动调整。
并行度小文件问题AQE 可自动调整
spark.executor.cores
默认值：1（YARN）/ 全核（Standalone）
每个 Executor 并发 Task 数。建议设为 4~5（YARN 模式），过多核心共享内存会导致 GC 竞争，过少会降低 CPU 利用率。与 executor.memory 的比例决定了每 Task 可用内存。
并发度GC 压力内存/核比
spark.sql.adaptive.enabled
默认值：true（Spark 3.2+）
启用自适应查询执行（AQE）。运行时根据实际 Shuffle 数据动态调整分区数、自动处理数据倾斜、将 Sort-Merge Join 转为 Broadcast Join。3.x 必开。
AQE动态优化Spark 3.2+
spark.sql.autoBroadcastJoinThreshold
默认值：10MB · 推荐：10MB~500MB
当一侧表估计大小低于此值，自动改用 Broadcast Hash Join，完全消除 Shuffle。大幅提升小表 JOIN 大表的性能。注意：广播表序列化后需放入 Driver 内存，过大会 OOM。
Broadcast Join消除 ShuffleDriver 内存
spark.serializer
默认值：JavaSerializer · 推荐：KryoSerializer
序列化方式影响 Shuffle 数据大小和 CPU 消耗。Kryo 比 Java 序列化快 3~10 倍，数据量小 30~80%。但需手动注册类，否则退回 Java 序列化。
Kryo序列化性能Shuffle 数据量
spark.dynamicAllocation.enabled
默认值：false · 生产推荐：true
动态资源分配，根据待处理 Task 数自动伸缩 Executor 数量。空闲 Executor 60s 后释放，Task 积压时自动申请。需配合 External Shuffle Service 使用以防数据丢失。
弹性伸缩资源利用率需 ESS

关键配置的性能影响对比

AQE 开启 vs 关闭（典型 ETL 作业） 提速 35~60%
Kryo 序列化 vs Java 序列化（Shuffle 密集） 提速 40~70%
Broadcast Join vs Sort-Merge Join（小表 JOIN） 提速 5~20x
Off-Heap 内存 vs 纯堆内存（GC 影响） 减少 GC 停顿 50~80%
06 / Common Pitfalls

生产常见陷阱与避坑指南

这些坑大多数人都踩过，理解其原理能让你的 Spark 作业从"能跑"到"跑好"。

🪤
Driver OOM：collect() 滥用
df.collect() 将所有 Executor 数据拉回 Driver JVM。大数据集下必 OOM。应使用 df.limit(1000).collect() 或写入存储后再读取。
💀
数据倾斜：大 Key 问题
某个 partition 处理 80% 的数据，Job 卡在最后一个 Task 几小时。需通过 Spark UI Stage 页面查看各 Task 耗时分布来确诊，再用 Salting 或 AQE Skew Join 解决。
🔁
重复计算：未 Cache 中间结果
同一个 DataFrame 被多处 Action 触发，DAG 从头计算多次。应在 多次使用 的 RDD/DataFrame 上调用 .cache() 或 .persist(StorageLevel.MEMORY_AND_DISK)。
🧨
小文件地狱：分区过多
写出时分区数 = Shuffle 分区数，可能产生几千个几 KB 的小文件，HDFS NameNode 元数据暴涨。写出前用 coalesce(N) 或 AQE 合并小分区。
🌊
全表 Shuffle：误用 distinct()
df.distinct() 触发全量 Shuffle，在大表上极慢。若只需近似去重，使用 approx_count_distinct()；若需精确但数据已分区，使用 dropDuplicates(subset)。
⏰
Executor 心跳超时
单个 Task 耗时超过 spark.network.timeout（默认 120s），Executor 被 Driver 标记死亡并重启。GC 停顿、数据倾斜均可触发。需调大超时或从根本解决 GC/倾斜问题。
🛠
诊断黄金工具
Spark UI → Stages 页面：查看 Task 耗时分布（中位数 vs 最大值差距大 = 数据倾斜）
Spark UI → SQL 页面：查看物理执行计划，确认 BroadcastHashJoin 是否生效
df.explain("formatted")：输出带注释的物理计划，检查谓词下推和列裁剪是否生效
