一

概念定义 Concept Definition

算子（Operator）是 Apache Spark 中对分布式数据集（RDD / DataFrame / Dataset）进行操作的函数式编程接口，它定义了对数据"做什么"而非"怎么做"，由 Spark 运行时将其转化为分布式并行任务执行。

在整个 Spark 体系中，算子是构建数据处理管道的基本积木。用户通过链式调用算子描述计算逻辑，Spark 则通过 DAG（有向无环图，Directed Acyclic Graph）调度器将算子序列优化后翻译成 Stage 和 Task，分发到集群执行。

💡 直观类比
算子就像工厂流水线上的工序卡片：你先把所有工序卡片（Transformation 算子）依次排好，贴在看板上（构建 DAG），最后按下"开工"按钮（Action 算子）时，工厂才真正启动，自动并行地完成每道工序。整个过程的关键在于：描述计划（惰性求值） 与 真正执行 分开发生。
📌 地位

Spark 编程模型的核心接口，开发者与底层引擎沟通的唯一桥梁

⚙️ 作用

描述数据转换逻辑；触发分布式计算；控制数据流动与 Shuffle

🔑 核心特性

惰性求值（Lazy Evaluation）；不可变性；函数式组合；容错重算

3.1 Transformation 算子 — 惰性转换

Transformation（转换）算子对数据集进行描述性操作，不立即执行，而是将操作记录到 DAG 中。其返回值始终是新的 RDD 或 DataFrame。

窄依赖算子（Narrow Dependency）

每个输入 Partition 最多只影响一个输出 Partition，无需网络传输，可在同一 Stage 内流水线执行。

// Scala 示例：窄依赖算子链式调用
val rdd = sc.textFile("hdfs://logs/*.log")

val result = rdd
  .filter(line => line.contains("ERROR"))          // 过滤：窄依赖
  .map(line => (line.split(" ")(0), 1))            // 映射：窄依赖
  .flatMap(pair => Seq(pair, (pair._1 + "_total", 1))) // 展开：窄依赖
// 此时尚未执行任何计算，仅构建 DAG 节点

宽依赖算子（Wide Dependency / Shuffle）

输入 Partition 的数据需要跨节点重新分发（Shuffle），是 Stage 边界划分的依据，也是性能优化的核心关注点。

// Scala 示例：宽依赖算子触发 Shuffle
val wordCount = rdd
  .map(line => (line.split(" ")(0), 1))
  .reduceByKey(_ + _)    // 宽依赖！在 Map 端预聚合后 Shuffle
  .sortBy(_._2, ascending = false)  // 宽依赖！全局排序

// DataFrame API 等价写法（Catalyst 优化器会自动优化）
import org.apache.spark.sql.functions._
df.groupBy("word")
  .agg(count("*").as("cnt"))
  .orderBy(desc("cnt"))

3.2 Action 算子 — 触发执行

Action（行动）算子是计算的触发器。调用 Action 时，Spark 将构建好的 DAG 提交给 DAG Scheduler，划分 Stage，生成 TaskSet，提交给集群执行。

// Python (PySpark) 示例：常用 Action 算子
df = spark.read.parquet("/data/orders")
result = df.filter(df.amount > 1000).groupBy("region").sum("amount")

# 采集到 Driver（小数据量）
rows = result.collect()            # ⚡ 触发执行！返回 List[Row]
first_row = result.first()         # ⚡ 触发执行！返回第一行
top5 = result.take(5)            # ⚡ 取前 5 行

# 统计类（只返回数字，效率高）
total = result.count()             # ⚡ 统计行数

# 写出到外部存储
result.write.parquet("/output/region_sales")  # ⚡ 写 Parquet
result.write.jdbc(url, "table", props)         # ⚡ 写 JDBC

3.3 持久化算子（Persistence）

当一个 RDD/DataFrame 被多个 Action 复用时，应使用 cache() / persist() 将其缓存，避免重复计算。

// Scala：选择合适的存储级别
import org.apache.spark.storage.StorageLevel

val hotData = df.filter("is_active = true")
  .persist(StorageLevel.MEMORY_AND_DISK_SER) // 序列化后存内存+磁盘

hotData.count()    // ⚡ 第一次触发，同时填充缓存
hotData.show()     // 第二次直接从缓存读，无需重算

hotData.unpersist() // 使用完毕后释放

与其他概念的关联关系 Relationships

算子并不孤立存在，它与 Spark 体系中的以下核心概念紧密协作：

RDD / DataFrame / Dataset：算子的操作对象。RDD 是底层不可变分布式集合，DataFrame 是带 Schema 的结构化数据集，Dataset 兼具类型安全与 Catalyst 优化，算子在三者上的 API 形式略有不同，但语义一致。

Catalyst 优化器：DataFrame/Dataset 上的算子会经过 Catalyst 进行逻辑计划优化（谓词下推、列裁剪、常量折叠），RDD 算子则不经过此优化，这是推荐优先使用 DataFrame API 的核心原因。

Tungsten 执行引擎：在物理执行层，Tungsten 通过代码生成（Whole-Stage CodeGen）将多个算子合并为单一 JVM 字节码循环执行，极大减少虚函数调用和对象创建开销。

// 典型组合示例：算子 + DataFrame + 外部数据源
val orders = spark.read
  .option("header", "true")
  .csv("s3://bucket/orders/")        // 数据源读取

val products = spark.read.parquet("s3://bucket/products/")

// 算子链：Transformation（宽依赖 join + groupBy + agg）
val result = orders
  .join(products, orders("product_id") === products("id"), "inner") // 宽依赖
  .filter(col("order_date") >= "2024-01-01")                      // 窄依赖
  .groupBy("category", "region")                                  // 宽依赖
  .agg(
    sum("amount").as("total_gmv"),
    countDistinct("user_id").as("uv")
  )
  .orderBy(desc("total_gmv"))                                   // 宽依赖

// Action：触发执行并写出
result.write.mode("overwrite").parquet("s3://output/report/")  // ⚡

进阶特性与底层原理 Advanced Internals

7.1 惰性求值（Lazy Evaluation）的实现机制

每次调用 Transformation 算子，Spark 并不执行任何计算，而是在内部维护一个 RDD Lineage（血统）图。以 RDD 为例，每个 RDD 都记录了：① 父 RDD 引用 ② 生成该 RDD 的函数 ③ 分区数量。这个 Lineage 本质上是一棵 DAG 树，只有 Action 被调用时，DAGScheduler 才会从终点 Action 出发，反向遍历 Lineage，将其转化为 Stage 执行计划。

这样设计的原因在于：惰性求值允许 Spark 在实际执行前看到整个计算计划，从而实现全局优化（如谓词下推到数据源层，避免读取不需要的列和行）。

// 验证惰性求值：以下代码只构建 DAG，不执行
val rdd1 = sc.parallelize(1 to 1000000)   // 创建 RDD，不真正分发数据
val rdd2 = rdd1.map(x => x * x)            // 只记录"平方"操作到 Lineage
val rdd3 = rdd2.filter(_ > 100)           // 只记录"过滤"操作
println(rdd3.toDebugString)                 // 查看 Lineage 树（仍不执行）
val sum = rdd3.reduce(_ + _)               // ⚡ Action！此时才真正执行

7.2 Shuffle 内部实现（Sort-Based Shuffle）

Spark 2.0+ 默认使用 Sort-Based Shuffle，每个 Map Task 将数据写入一个单一排序文件（外加一个 Index 索引文件），Reduce Task 通过 HTTP 拉取对应分区的数据块。相比老版本的 Hash-Based Shuffle（每个 Map Task 产生 R 个文件），它将文件数从 M×R 降低到 2×M，大幅减少小文件数量和随机 I/O。

7.3 mapPartitions vs map：为什么粒度很重要

map(f) 对每条记录调用一次函数 f，mapPartitions(f) 则对每个 Partition 调用一次 f，传入一个迭代器。当函数 f 需要初始化重量级资源（如数据库连接、模型加载）时，mapPartitions 可将资源创建次数从 N（记录数）降低到 P（分区数），性能提升显著。

// 对比：map vs mapPartitions 处理数据库写入

// ❌ 低效：每条记录都创建一次连接
rdd.map { record =>
  val conn = DB.getConnection()   // 百万次连接创建！
  conn.insert(record)
  conn.close()
}

// ✅ 高效：每个 Partition 只创建一次连接
rdd.mapPartitions { records =>
  val conn = DB.getConnection()   // 只创建 partition 数次
  val result = records.map { record =>
    conn.insert(record)
    record
  }.toList
  conn.close()
  result.iterator
}

生产实践 / 调优指南 Production Best Practices

常见问题 根本原因 解决方案
数据倾斜（Skew） Key 分布不均，某些 Reduce Task 处理数据量远大于其他 ① 加盐（Salting）打散热点 Key
② 使用 skewHint() / AQE 自动倾斜处理
③ 广播小表替代 Shuffle Join
Driver OOM collect() 或 take() 拉取数据量超过 Driver 内存 改用 write() 写出；或先 limit() 再 collect()
Executor OOM groupByKey 将同 Key 所有数据加载到内存 改用 reduceByKey / aggregateByKey（Map 端预聚合）
小文件过多 repartition 数过大，每个 Partition 写出一个文件 写出前 coalesce(N)；或使用 AQE 自动合并小 Shuffle 分区
重复计算 同一 RDD/DataFrame 被多个 Action 多次触发重算 在第一个 Action 前调用 cache() / persist()
Stage 数过多 算子链中宽依赖过多，Shuffle 次数多 合并多次 groupBy 为一次 agg()；使用 repartition 一次性重分区

最佳实践建议

1

优先使用 DataFrame/Dataset API：相比 RDD，DataFrame 受 Catalyst 优化器保护，会自动执行谓词下推、列裁剪、连接重排等优化，性能通常高出数倍。

2

用 reduceByKey 替代 groupByKey：groupByKey 将所有数据 Shuffle 后才聚合，内存压力大；reduceByKey 在 Map 端预聚合，大幅减少网络传输量。

3

广播小表（Broadcast Join）：当一个表远小于另一个时（通常 <10MB），使用 broadcast(smallDF) 将其广播到每个 Executor，避免大规模 Shuffle Join。

4

合理设置 Shuffle 分区数：默认 spark.sql.shuffle.partitions=200 并非万能，应根据数据量调整（经验值：每个分区 128MB~256MB 数据）。开启 AQE（Adaptive Query Execution）可自动调整。

5

避免在 Action 中使用 collect 大结果集：collect() 会将所有数据拉到 Driver，生产环境应直接使用 write() 写出到 HDFS/S3，或用 limit()+collect() 只取样本。

关键配置参数

参数默认值说明

spark.sql.adaptive.enabledtrue (3.0+)启用 AQE 自适应查询执行

核心记忆要点

惰性求值是根本：Transformation 只构建计划，Action 才触发执行。每个 Action 对应一个 Job。
宽依赖划分 Stage：每遇到一个有 Shuffle 的宽依赖算子，就产生一个新 Stage 边界。
reduceByKey > groupByKey：前者 Map 端预聚合，后者全量 Shuffle，数据量差异可能达数十倍。
DataFrame > RDD（性能）：Catalyst 优化 + Tungsten 执行，同等逻辑性能通常高出 2~5 倍。
cache 要及时释放：persist() 后记得 unpersist()，否则长期占用 Executor 内存影响其他任务。
collect() 有 OOM 风险：生产环境大数据集应直接 write() 写出，不要 collect 后再处理。
开启 AQE（Spark 3.0+）：spark.sql.adaptive.enabled=true 可自动处理倾斜、动态调整分区数。
mapPartitions 比 map 更高效：初始化重量级资源（连接、模型）时，应选择按分区操作。
