01 / Catalyst Four-Phase Pipeline

Catalyst 优化器：四阶段管道

Catalyst 是 Spark SQL 的核心优化引擎。一条 SQL 或 DataFrame 操作从用户代码到物理执行，经过四个严格有序的阶段变换，每一阶段都是一棵树形结构（TreeNode）的转换。

1
Analysis
解析 · 绑定
  • 将 SQL / DataFrame API 解析为 Unresolved Logical Plan
  • 通过 Catalog 绑定表名、列名、数据类型
  • 隐式类型转换（如 INT → LONG）
  • 输出：Resolved Logical Plan
2
Logical Optimization
逻辑 · 优化
  • 应用 ~100 条基于规则的优化（Rule-based）
  • 谓词下推、列裁剪、常量折叠
  • 子查询消除、Limit 下推
  • 输出：Optimized Logical Plan
3
Physical Planning
物理 · 规划
  • 将逻辑算子映射为物理算子
  • 基于代价模型（CBO）选择 Join 策略
  • 分区裁剪、数据分布感知
  • 输出：Physical Plan（SparkPlan）
4
Code Generation
代码 · 生成
  • Whole-Stage Codegen 合并算子链
  • 动态生成 Java 字节码
  • 消除虚函数调用开销
  • 输出：可直接执行的 JVM 字节码
🔍
查看执行计划的正确方式
df.explain() — 只看物理计划（默认）
df.explain("extended") — 同时展示逻辑计划（解析前/后/优化后）+ 物理计划
df.explain("formatted") — Spark 3.0+ 新格式，带树形缩进和算子注释，可读性最强
df.explain("codegen") — 展示最终生成的 Java 源码（调试 Codegen 必用）
02 / Logical Optimization Rules

逻辑优化规则分类详解

Catalyst 的逻辑优化由约 100 条规则组成，分批（Batch）执行，每批固定点迭代直到计划不再变化。掌握关键规则类别，才能读懂 explain() 输出并判断优化是否生效。

⬇️ 谓词下推（Predicate Pushdown） 最高收益
PushPredicateThroughFilter PushPredicateThroughJoin PushDownPredicates PushFoldableIntoBranches InferFiltersFromConstraints
✂️ 列裁剪（Column Pruning） 减少 IO
ColumnPruning PruneFilters RemoveRedundantAliases RemoveNoopOperators
🔢 常量折叠与化简（Constant Folding） 减少运行时计算
ConstantFolding BooleanSimplification SimplifyConditionals NullPropagation SimplifyExtractValueOps
🔀 Join 重排序与消除（Join Reordering） 需开启 CBO
ReorderJoin EliminateOuterJoin PushPredicateThroughJoin ExtractLeftSemiOrAntiJoin
📦 子查询与集合操作优化 SQL 特定
RewriteCorrelatedScalarSubquery PullupCorrelatedPredicates ReplaceDistinctWithAggregate CombineUnions OptimizeSubqueries
predicate_pushdown_demo.py PySpark 
from pyspark.sql import SparkSession
import pyspark.sql.functions as F

spark = SparkSession.builder.getOrCreate()

# ── 谓词下推验证 ──────────────────────────────────────
# Parquet 文件：Catalyst 会将 filter 下推到 scan 层，
# 只读取满足条件的 row group，大幅减少 IO

df = spark.read.parquet("hdfs://data/events")

# ✅ 这个 filter 会被下推到 FileScan
result = df.filter(F.col("event_date") >= "2024-01-01") \
            .filter(F.col("country") == "CN") \
            .select("user_id", "event_type", "amount")

# 验证：PushedFilters 字段出现在 FileScan 节点中即为成功
result.explain("formatted")
# 输出示例：
# == Physical Plan ==
# *(1) Project [user_id, event_type, amount]
# +- *(1) Filter (event_date >= 2024-01-01 AND country = CN)
#    +- FileScan parquet [...]
#       PushedFilters: [GreaterThanOrEqual(event_date,2024-01-01), EqualTo(country,CN)]
#       ReadSchema: struct

# ── 列裁剪验证 ────────────────────────────────────────
# ReadSchema 中只包含 select 的列，宽表中其余列完全跳过

# ❌ 陷阱：UDF 会阻断谓词下推！
from pyspark.sql.functions import udf
from pyspark.sql.types import BooleanType

@udf(BooleanType())
def my_filter(country):
    return country == "CN"

# 此 filter 无法下推，Catalyst 无法分析 UDF 内部逻辑
bad = df.filter(my_filter(F.col("country")))  # ❌

# ✅ 替换为内置函数或 SQL 表达式
good = df.filter(F.col("country") == "CN")       # ✅
03 / Physical Planning & Join Strategies

物理计划生成与 Join 策略选择

物理规划阶段将逻辑算子映射为真实的执行算子，最关键的决策是 Join 策略的选择——这直接决定是否触发 Shuffle、数据分布代价和并行度。

Join 策略 触发条件 Shuffle Sort 适用场景 性能
Broadcast Hash Join 小表 < autoBroadcastJoinThreshold 无 无 大表 JOIN 小维度表 ★★★★★ 最快
Shuffle Hash Join 两表均需 Shuffle，小侧可放内存 有 无 一侧明显小于另一侧 ★★★☆☆ 中
Sort-Merge Join 两表均大，默认策略 有 有 大表 JOIN 大表 ★★★☆☆ 稳定
Cartesian Product Join 无 Join Key（cross join） 有 有 极少用，危险操作 ★☆☆☆☆ 极慢
Broadcast Nested Loop Join 非等值 JOIN，小表广播 无 无 范围条件 JOIN ★★☆☆☆ 慢
⚠ 未优化：Sort-Merge Join（触发双侧 Shuffle）
*(5) SortMergeJoin
:- *(2) Sort [user_id ASC]
+- Exchange hashpartitioning(user_id, 200)
+- *(1) FileScan orders
+- *(4) Sort [user_id ASC]
+- Exchange hashpartitioning(user_id, 200)
+- *(3) FileScan users [ALL COLUMNS]

// 双侧 Shuffle + Sort，代价极高
// users 表读取全部列（未裁剪）
✅ 优化后：Broadcast Hash Join（无 Shuffle）
*(2) BroadcastHashJoin
:- *(1) FileScan orders
PushedFilters: [IsNotNull(user_id)]
+- BroadcastExchange HashedRelationBroadcast
+- *(1) FileScan users [user_id, name]
ReadSchema: struct<user_id,name>

// 无 Exchange（无 Shuffle）
// 列裁剪：users 只读 user_id + name
join_hints.py PySpark 
# ── 手动指定 Join 策略 Hint ────────────────────────────

# ✅ 强制广播（当 Catalyst 估算失准时）
from pyspark.sql.functions import broadcast

result = orders.join(broadcast(dim_users), "user_id")

# ✅ SQL Hint 语法（等效）
spark.sql("""
    SELECT /*+ BROADCAST(u) */ o.*, u.name
    FROM orders o
    JOIN users u ON o.user_id = u.user_id
""")

# ✅ 强制 Sort-Merge Join（当自动广播不符合预期时）
spark.sql("""
    SELECT /*+ MERGE(o, u) */ o.*, u.name
    FROM orders o JOIN users u ON o.user_id = u.user_id
""")

# ── 开启 CBO（Cost-Based Optimizer）────────────────────
# CBO 依赖表统计信息，需手动收集
spark.sql("ANALYZE TABLE orders COMPUTE STATISTICS FOR ALL COLUMNS")
spark.sql("ANALYZE TABLE users COMPUTE STATISTICS FOR ALL COLUMNS")

spark.conf.set("spark.sql.cbo.enabled", "true")
spark.conf.set("spark.sql.cbo.joinReorder.enabled", "true")

# CBO 开启后，Catalyst 会根据行数/NDV/列分布选择最优 Join 顺序
# 多表 JOIN 时收益尤其显著（从指数复杂度降至近线性）
04 / Tungsten Execution Engine

Tungsten 引擎：三大核心技术

Tungsten（Spark 1.4 引入）是 Spark 执行层的底层革命，通过三项关键技术突破 JVM 限制，大幅提升 CPU 和内存效率。

🧠
堆外内存管理
使用 sun.misc.Unsafe 直接操作堆外内存，绕过 GC 管理。数据以二进制格式存储，避免 Java 对象头开销（通常节省 2~5x 空间）。紧凑的 UnsafeRow 格式让数据可直接在网络上传输而无需反序列化。
Off-Heap · UnsafeRow · GC 消除
⚡
Whole-Stage Codegen
将多个算子融合为单个 Java 函数动态生成字节码，消除虚函数调用、内存对象实例化和迭代器模型的开销。生成的代码利用 CPU 流水线和 SIMD 指令，实测比解释执行快 5~10 倍，接近手写 C 代码性能。
Codegen · JIT · CPU 流水线
🗄️
Cache-Aware 数据结构
传统 HashMap 中 key-value 散落堆内存各处，缓存命中率极低。Tungsten 的 BytesToBytesMap 将数据紧凑排列，大幅提升 L1/L2 缓存命中率。Sort 算法也经过重新设计，优化内存访问模式。
Cache-Friendly · BytesToBytesMap
📐
UnsafeRow 二进制格式
每行数据在内存中的布局：[null bitmap (8 bytes/列)] + [fixed-length values] + [variable-length data]
整数、长整型、浮点型直接原地存储；字符串存偏移量 + 长度指针指向变长区。
这意味着：无论 schema 多复杂，访问任意列的时间复杂度均为 O(1)，且数据可在 Executor 间零拷贝传输（Shuffle 写出时直接 memcpy）。
05 / Whole-Stage Codegen Internals

Whole-Stage Codegen 原理剖析

传统 Volcano 模型（迭代器模式）中每条记录都要经过无数次虚函数调用。Codegen 将多个算子"融合"成一个紧密循环，让 JIT 编译器大展身手。

❌ Volcano 迭代器模型（解释执行） 
// 每个算子独立迭代，每条记录
// 都要经历 N 次虚函数调用
// CPU 分支预测失败率高

class FilterIterator:
  def next():
    row = child.next()  ← 虚调用1
    if predicate(row):  ← 虚调用2
      return row

class ProjectIterator:
  def next():
    row = child.next()  ← 虚调用3
    return evaluate(row) ← 虚调用4

// 每行 = 4次虚调用 + 对象分配
// 1亿行 = 4亿次虚调用 ❌
Code
Gen
✅ Whole-Stage Codegen（生成字节码） 
// Catalyst 动态生成的 Java 代码：
// Filter + Project 融合为单一循环
// 无虚调用，JIT 可激进优化

void processPartition(Iterator rows) {
  while (rows.hasNext()) {
    UnsafeRow row = rows.next();
    // Filter 内联
    long age = row.getLong(2);
    if (age < 18) continue;
    // Project 内联
    long uid = row.getLong(0);
    result.append(uid, age);
  }
}
// 1亿行 ≈ 1亿次循环迭代
// 无对象分配，寄存器优化 ✅

06 / Adaptive Query Execution (AQE)

AQE：运行时动态重优化

AQE（Spark 3.0 正式发布）在每个 Shuffle 阶段完成后，利用真实统计数据重新规划后续执行，弥补静态 Catalyst 对数据分布估算不准的天然缺陷。

自动合并小分区
coalescePartitions.enabled = true
Shuffle 完成后，若某些 Reduce 分区数据量远小于 advisoryPartitionSizeInBytes（默认 64MB），AQE 自动将相邻小分区合并，避免产生大量小 Task。从 200 分区合并为 20 分区是常见场景。
小文件Task 调度开销
动态切换 Join 策略
canChangeBroadcastJoin = true
Shuffle 阶段完成前，Catalyst 仅能估算表大小；完成后 AQE 获得精确数据量，若某侧实际数据量低于广播阈值，可在运行时将 Sort-Merge Join 升级为 Broadcast Hash Join，无需重启作业。
动态 Broadcast消除 Shuffle
自动处理数据倾斜
skewJoin.enabled = true
检测到某个 Reduce 分区数据量超过中位数 × skewedPartitionFactor（默认5倍）且超过 skewedPartitionThresholdInBytes（默认256MB），自动将倾斜分区分裂为多个子分区并行处理。
Skew Join自动 Salting
动态分区裁剪（DPP）
dynamicPartitionPruning.enabled = true
当星型模型中维度表经过 filter 后，DPP 将 filter 结果广播到事实表的分区扫描中，只扫描实际匹配分区。Hive 分区表上效果尤其显著，可减少 90%+ 的 IO。Spark 3.0+ 自动开启。
分区裁剪星型模型IO 减少
aqe_config.py PySpark 
# ── AQE 完整配置参考 ──────────────────────────────────

spark = SparkSession.builder \
  # AQE 总开关（Spark 3.2+ 默认 true）
  .config("spark.sql.adaptive.enabled", "true") \

  # 自动合并小分区
  .config("spark.sql.adaptive.coalescePartitions.enabled", "true") \
  .config("spark.sql.adaptive.advisoryPartitionSizeInBytes", "128m") \  # 目标分区大小
  .config("spark.sql.adaptive.coalescePartitions.minPartitionNum", "1") \

  # 数据倾斜处理
  .config("spark.sql.adaptive.skewJoin.enabled", "true") \
  .config("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "5") \   # 超过中位数5倍触发
  .config("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256m") \

  # 局部 Shuffle 优化（Spark 3.3+）
  .config("spark.sql.adaptive.optimizeSkewsInRebalancePartitions.enabled", "true") \

  # 动态分区裁剪
  .config("spark.sql.optimizer.dynamicPartitionPruning.enabled", "true") \
  .getOrCreate()

# ── 验证 AQE 是否生效 ────────────────────────────────
# 执行计划中出现 AdaptiveSparkPlan 节点即为生效
# Spark UI → SQL 页面 → 点击查询 → 观察执行计划变化
⚠️
AQE 的局限性与注意事项
① 流式计算不支持：AQE 依赖 Shuffle 边界的物化统计，Structured Streaming 中无法使用。
② DPP 需要等值 Join：动态分区裁剪仅适用于等值 Join，范围 Join 无效。
③ 与 Hint 冲突：显式指定 /*+ BROADCAST */ 会覆盖 AQE 的动态 Join 策略选择。
④ 调试复杂度增加：AQE 下执行计划在运行时变化，需在 Spark UI 中查看最终实际执行计划。
07 / Pitfalls & Tuning Checklist

常见陷阱与优化器调优清单

Catalyst 虽然强大，但有若干典型场景会让优化器"失灵"，导致性能远低于预期。

🧱
UDF 阻断谓词下推
Python UDF 对 Catalyst 不透明，任何包含 UDF 的 filter 均无法下推至 FileScan。始终用内置函数或 Pandas UDF（向量化）替代逐行 Python UDF。
📊
统计信息过期导致 CBO 失效
CBO 依赖 ANALYZE TABLE 收集的统计，数据更新后不会自动刷新。大量写入后需重新执行 ANALYZE，否则 Join 策略选择可能严重偏差。
💥
Codegen 64KB 限制
JVM 单方法字节码不能超过 64KB。宽表（数百列）的聚合/JOIN 常触发此限制，Codegen 自动退化为解释执行，性能骤降。可通过 spark.sql.codegen.hugeMethodLimit 调整分割阈值。
🔄
count(distinct) 的代价
count(distinct col) 在 Spark 中需要两阶段 Shuffle，代价极高。多列 distinct count 更是指数级。使用 approx_count_distinct() 或 HyperLogLog 在 99%+ 精度下快 5~10 倍。
🪞
笛卡尔积隐患
SQL 中忘写 ON 条件，或 Join key 包含 NULL（NULL ≠ NULL，等值 JOIN 不匹配），导致隐式笛卡尔积。spark.sql.crossJoin.enabled=false（默认）可保护，但某些框架会绕过此保护。
🐢
过度嵌套子查询
复杂 SQL 中多层嵌套子查询有时无法被 Catalyst 完全展开，生成次优物理计划。建议通过 df.explain("extended") 验证优化后的逻辑计划，必要时手动重写为 JOIN 或 CTE 形式。

优化器效果量化对比

谓词下推 + 列裁剪（Parquet 宽表，扫描 IO 减少） 减少 IO 60~95%
Whole-Stage Codegen vs 解释执行（CPU 密集型算子） 提速 5~10x
AQE Skew Join vs 手动 Salting（实现成本对比） 效果相当，开发成本降低 90%
CBO Join 重排序（4表以上 JOIN，典型 ETL） 提速 2~8x
approx_count_distinct vs count(distinct)（精度 >99%） 提速 5~10x
✅
Catalyst 调优黄金法则
1. 优先使用内置函数——任何能替代 UDF 的内置函数都应替代，以保证优化器透明度
2. 先看计划再优化——所有性能问题先 explain("formatted")，确认问题根因再动手
3. 让 AQE 先跑——大多数数据倾斜和分区问题 AQE 能自动处理，不要过早手动干预
4. 收集统计信息——多表 JOIN 作业，每次大批量写入后执行 ANALYZE TABLE
5. Codegen 验证——关键路径确认物理计划中出现 *(N) 标记
